## Bug Report: FAIL

### BUG-1: `dz info --json` not implemented

**Section:** §2.1
**Severity:** FAIL (checklist expected behavior not present)
**Command:** `dz info core:find --json`

**Observed:**
```
usage: dz [-h] [--version]
dz: error: unrecognized arguments: --json
```
Exit code 2.

**`dz info --help` flags present:**
```
options:
  -h, --help            show this help message and exit
  --raw                 Show the manifest as declared, without conditional-dispatch resolution.
  --platform SPEC       Preview runtime resolution for a specific platform
  --as {tool,kit,aggregator}
                        Force the level when the name matches more than one of tool/kit/aggregator
```

**Diagnosis:** The `--json` flag is not in the `dz info` argument parser. The `--raw` flag exists but produces the same human-readable format with an `(raw, unresolved)` annotation for conditional fields — it is NOT equivalent to structured JSON output.

The checklist says "`--json` mirrors the card with a `state` object." This behavior is not implemented. Either:
(a) The `--json` flag was planned as part of SD-A but not yet shipped in this arc — checklist is ahead of the implementation.
(b) The checklist was written against a planned design that was deferred.

Either way: the flag does not work. If this feature is intentionally deferred, the checklist item should be updated to MANUAL or marked as a follow-up slice. If it was supposed to ship with this arc, it is a missing implementation.

**Do NOT fix:** diagnose-and-report only. Decision for the implementer.

## Review Items (human judgment needed)

### REVIEW-1: `dz enable <tool>` error message quality

**Section:** §3.2
**Command:** `dz enable core:find`
**Output:** `'core:find' did not resolve to a kit for 'enable'.`

The error is clear (not a no-op, not a stack trace) and exits non-zero. However, it does not guide the user toward the correct action. A message like "'core:find' is a tool, not a kit. Use 'dz kit enable core' to enable the core kit." would be more actionable. This is a UX quality finding, not a correctness bug. Mark as REVIEW or file a follow-up.

### REVIEW-2: `wtf` label inconsistency between tree and info

**Section:** HV.3 (also §2.1)
**Issue:** `dz tree` labels `wtf` as `[aggregator]` but `dz info wtf` shows `Kind: kit`. The `wtf.kit.json` registers wtf as a kit; the tree renderer infers aggregator-like behavior because it contains sub-kits (`wtf:core`).

If this is intentional (wtf is registered as a kit but rendered as an aggregator in the tree because of its nesting), no action needed. If it should report `Kind: aggregator` for consistency, the kit manifest or the info renderer needs an update. Human decision.
