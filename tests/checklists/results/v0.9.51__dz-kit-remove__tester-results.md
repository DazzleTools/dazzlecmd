## Item-by-Item Results

### HV.1 -- `--dry-run` prints the plan, changes nothing

**Result: FAIL**

**Command:**
```
dz kit remove ztestdummy --dry-run
```

**Observed output:**
```
Dry run -- `dz kit remove ztestdummy` would:
  - deregister kits/ztestdummy.kit.json (membership ungroup)
  - safedel projects/ztestdummy/ -> recoverable trash
  - drop 'ztestdummy' from active_kits / disabled_kits
```

**Expected:** plan should include `untrack the submodule (git submodule deinit + git rm projects/ztestdummy)` as the first step, since ztestdummy IS a git submodule.

**Observed:** the git untrack step was ABSENT from the dry-run plan. Files were unchanged (PASS for the no-op part), but the plan was materially incomplete -- it did not disclose the git surgery that a real run would need to perform.

**Root cause (see HV.3 for full analysis):** `parse_gitmodules()` in `dazzlecmd_lib/mode.py` only captures 3-part paths (`projects/<namespace>/<tool>`) and explicitly skips 2-part paths (`projects/<kit>`). Since `ztestdummy` is registered at `projects/ztestdummy` (2-part), `is_submodule = False` at plan-build time, so the git step was omitted from the plan.

**Impact:** The dry-run preview is inaccurate for any kit added via `dz kit add` -- it does not warn the user that git surgery will happen.

**Expected post-remove state:**

- `kits/ztestdummy.kit.json` gone -- PASS

**Observed post-remove state:**

```python
relative = path[len(prefix):]   # "ztestdummy" (for projects/ztestdummy)
parts = relative.split("/")
if len(parts) != 2:             # 1 != 2, so SKIP

```

It requires `<tools_dir>/<namespace>/<tool>` (3 parts). A top-level kit at `projects/ztestdummy` has only 1 part after the prefix. The docstring explicitly says: *"2-part kit-level submodule paths (an entire kit registered as a submodule) are skipped here and handled separately by the aggregator engine's discover_kits logic."*

Result: `is_submodule = False` for any kit added via `dz kit add`, so the `git submodule deinit + git rm` block (lines 2314-2327 of `src/dazzlecmd/cli.py`) is never executed.

**Left-over git state:** The `AD` status and `.gitmodules` entry were cleaned up manually by running `git submodule deinit -f -- projects/ztestdummy && git rm -f -- projects/ztestdummy` in the test session. The manual `git rm` successfully removed both the gitlink from the index and the `.gitmodules` entry, confirming the commands themselves work -- they just were not called by `dz kit remove`.

**Repro (100% reproducible):**
1. `dz kit add file:///<local-bare>.git --name ztestdummy`
2. `dz kit remove ztestdummy --yes`
3. `git status` shows `AD projects/ztestdummy`; `.gitmodules` has stale entry

### 1.1 -- dirty submodule worktree refused without `--force`

**Result: FAIL (downstream of HV.3 root cause)**

**Setup:** `dz kit add ztestdummy` then created `projects/ztestdummy/dirty_test.txt` (untracked file inside the submodule worktree). `git -C projects/ztestdummy status --short` confirmed `?? dirty_test.txt`.

**Command:**
```
dz kit remove ztestdummy --yes
```

**Expected:** dirty-tree refusal message; nothing removed.

**Observed:**
```
Removed kit: ztestdummy
  Files -> trash (recover with `dz safedel recover last`)
  Re-add with: dz kit add ...
```

Exit code: 0. The removal proceeded silently, trashing `projects/ztestdummy/` including the dirty untracked file.

**Root cause:** Same as HV.3. The dirty-guard at line 2279 of `cli.py` is gated on `is_submodule`:

```python
if is_submodule and os.path.isdir(target_dir):
    dirty = _check_dirty_tree(target_dir)
    if dirty and not getattr(args, "force", False):
        ...
        return 1
```

Since `is_submodule = False` for 2-part paths, the dirty check is never reached. The `--force` flag path was not tested since the non-force path already bypassed the guard.

**Impact:** A user with uncommitted work inside a submodule kit will lose that work silently (it goes to the trash, but without warning). This is exactly the class of data-loss the dirty-guard exists to prevent.

## HOLD-Blocker Bugs

### Bug 1 (FAIL): `dz kit remove` does not run git surgery for top-level kit submodules

**Severity:** HIGH -- data-integrity issue. After removing a submodule kit, the git index is left in an `AD` state (gitlink staged as Added, worktree deleted) and `.gitmodules` retains the removed submodule section.

**Affected checklist items:** HV.1 (plan omits git step), HV.3 (git surgery skipped), 1.1 (dirty-guard bypassed)

**Root cause:** `parse_gitmodules()` in `packages/dazzlecmd-lib/src/dazzlecmd_lib/mode.py` only captures 3-part paths (`projects/<ns>/<tool>`). Top-level kits at `projects/<name>` have a 1-part relative path after the prefix and are filtered out by `len(parts) != 2`. This sets `is_submodule = False` in `_cmd_kit_remove()` for any kit added via `dz kit add`, disabling all git surgery.

**Location of defect:**
- `parse_gitmodules()` in `dazzlecmd_lib/mode.py` (the filter `len(parts) != 2`)
- `_cmd_kit_remove()` in `src/dazzlecmd/cli.py` relies on `is_submodule` from `parse_gitmodules` to gate git surgery AND the dirty-guard

**Repro:**
```
git init --bare %TEMP%\tk.git
cd %TEMP%\tk_work && git clone %TEMP%\tk.git . && echo x > README.md && git add . && git commit -m init && git push origin HEAD:main
cd C:\code\dazzlecmd\github
dz kit add file:///%TEMP%/tk.git --name testkit
dz kit remove testkit --yes
git status   # shows AD projects/testkit
cat .gitmodules   # still has [submodule "projects/testkit"]
```

**Expected fix direction (diagnosis only -- do NOT apply):** `_cmd_kit_remove()` needs an alternative submodule detection path that works for 2-part (top-level) kit submodules. One approach: use `git ls-files --error-unmatch --stage -- projects/<name>` or check `git submodule status -- projects/<name>` to detect submodule registration. Alternatively, extend `parse_gitmodules` to also return 2-part kit-level paths (the comment says they are "handled separately" -- kit_remove needs to consult that source too).

---

### Bug 2 (FAIL): Dirty-guard bypassed for all `dz kit add` submodule kits

**Severity:** MEDIUM -- silent data loss of uncommitted work in submodule worktree.

**This is the same root cause as Bug 1** (is_submodule = False) but has distinct impact: a user's uncommitted changes in a kit submodule worktree are trashed without warning. The `--force` flag intended to override this guard is also unreachable.
