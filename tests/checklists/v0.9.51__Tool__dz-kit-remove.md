## What this is

`dz kit remove <name>` is the strong-remove pole of the kit lifecycle: deregister (git untrack + registry `ungroup`) + `safedel`-trash the files (recoverable) + deactivate. The **unit tests cover the local-only path** (no git). This checklist covers what mocks can't: **real `git submodule deinit`/`git rm` surgery, the interactive confirm, the dirty-submodule guard, and actual `safedel` recovery** — the exact behavior whose mis-scoping caused the original detach rewind, so verify it honestly.

## Prerequisites

1. This build (`dz --version` -> `0.9.51`), git installed.
2. **Work in a throwaway clone or sandbox aggregator** — `dz kit remove` deletes files (to the recoverable trash) and runs `git rm`. NEVER run it against a repo whose state you care about. Use a scratch aggregator dir.
3. Isolate config so you don't touch your real `~/.dazzlecmd/config.json`:

   **cmd.exe**: `set DAZZLECMD_CONFIG=%TEMP%\dzrm.json`
   **PowerShell**: `$env:DAZZLECMD_CONFIG = "$env:TEMP\dzrm.json"`
   **POSIX**: `export DAZZLECMD_CONFIG=/tmp/dzrm.json`

4. Reset between sections: `dz safedel recover last` to restore a trashed kit, or re-`dz kit add` it.

## High-Value Verification (~8 minutes)

### HV.1 — `--dry-run` prints the plan, changes nothing

- [ ] **Steps:** in a scratch aggregator with a removable kit `K`: `dz kit remove K --dry-run`
- [ ] **Expected:** a "Dry run -- `dz kit remove K` would:" block listing the steps (untrack / deregister / safedel / drop config refs). Afterward `projects/K/`, `kits/K.kit.json`, and `git status` are **unchanged**.
- [ ] **Why this matters:** dry-run is the safety preview for a destructive, git-mutating op.

### HV.2 — interactive confirm guards the delete

- [ ] **Steps:** `dz kit remove K` (NO `--yes`), then answer `n` at the prompt.
- [ ] **Expected:** prompt `Remove kit 'K'? Its files go to the recoverable trash. [y/N]`; answering `n` (or empty) prints `Aborted.` and changes nothing.
- [ ] **Why this matters:** no silent destruction; the default is no.

### HV.3 — remove a real SUBMODULE kit (the git surgery)

Validates: the from-scratch `git submodule deinit` + `git rm` path the unit tests don't cover.

- [ ] **Steps:** `dz kit add <some-git-url>` (creates a submodule kit `S`); then `dz kit remove S --yes`.
- [ ] **Expected:** stdout `Removed kit: S` + a trash hint + a `Re-add with: dz kit add <url>` hint. Then verify:
  - `projects/S/` is gone (trashed)
  - `kits/S.kit.json` is gone
  - `.gitmodules` no longer has the `[submodule "projects/S"]` section
  - `git status` shows the gitlink + `.gitmodules` change staged by `git rm` (no leftover gitlink)
  - `git config --file .git/config --get-regexp submodule.projects/S` returns nothing (deinit cleared it)
- [ ] **Why this matters:** this is the exact multi-substrate git surgery whose mis-scope caused the rewind — it must leave a clean index.

### HV.4 — the files are RECOVERABLE (safedel, not raw delete)

- [ ] **Steps:** after HV.3, `dz safedel list` (the trash shows `S`), then `dz safedel recover last`.
- [ ] **Expected:** `projects/S/` is restored intact (its files back on disk). (The registry/git are NOT auto-restored — re-`dz kit add` for that; recovery is the *files* safety net.)
- [ ] **Why this matters:** "remove" must never mean irreversible data loss — the deletion-scope policy.

### HV.5 — constitutional / always_active refusal (C3)

- [ ] **Steps:** `dz kit remove core` (or any `always_active` kit).
- [ ] **Expected:** `Refused: 'core' is constitutional (always_active) -- it may not be removed (C3)...`, exit code 1, nothing changed.
- [ ] **Why this matters:** dz must not let you remove a kit it depends on.

### HV.6 — config refs are dropped (deactivate)

- [ ] **Steps:** `dz kit enable K` (puts K in `active_kits`); `dz kit remove K --yes`; inspect the config.
- [ ] **Expected:** `K` is gone from `active_kits` (and `disabled_kits`) — no dangling reference.

  View config — **cmd.exe**: `type %DAZZLECMD_CONFIG%` · **PowerShell**: `Get-Content $env:DAZZLECMD_CONFIG` · **POSIX**: `cat "$DAZZLECMD_CONFIG"`

## Section 1: Guards & edge cases

### 1.1 dirty submodule worktree refused without `--force`

- [ ] **Steps:** in submodule kit `S`, make an uncommitted edit inside `projects/S/`; then `dz kit remove S --yes`.
- [ ] **Expected:** refused with a dirty-tree message (same family as `dz mode switch`); nothing removed. Re-run with `--force` → proceeds.

### 1.2 not-found

- [ ] **Steps:** `dz kit remove nonexistent-kit`
- [ ] **Expected:** `Error: no kit 'nonexistent-kit' found ...`, exit 1.

### 1.3 local-only (untracked) kit

- [ ] **Steps:** a kit present as `projects/L/` + `kits/L.kit.json` but NOT a git submodule (e.g. manually added); `dz kit remove L --yes`.
- [ ] **Expected:** removed (registry gone, files trashed, deactivated) with NO git errors (no submodule to deinit).

## What the automated tests DON'T cover (this checklist's job)

- Real `git submodule deinit` / `git rm` / `.gitmodules` mutation (unit tests mock the trash + use local-only kits).
- The interactive y/N confirm (stdin).
- Actual `safedel` recovery round-trip (`dz safedel recover last` restoring the dir).
- The dirty-submodule guard against a real dirty worktree.
- Windows path/codepage behavior of the git output + the trash hint.
- That the git index is left clean (no orphan gitlink / stale `.git/config` submodule entry).
