## What this is

A hand-runnable smoke + UX verification for v0.7.40's `dz new` redesign. Covers the breaking change from flat `dz new <name>` to `dz new <type> <name>`, the planned-shape stubs for `kit` and `aggregator`, the user-config defaults integration, and the `long_description` end-to-end pipeline (scaffold via `dz new tool --long-description` → render via `dz info`).

The 28 automated tests cover the dispatcher and rendering paths. This checklist catches what mocks miss: actual CLI invocation, real argparse error messages, terminal-rendered output, multi-shell behavior, real-world `dz info` display, and edge cases around the user-config schema area.

## Prerequisites

1. Working `dz` install — verify with `dz --version` (should show `dazzlecmd PREALPHA 0.7.40` or higher)
2. Clean working tree OR willingness to `dz safedel` scratch tools created during the checklist
3. A terminal capable of TTY behavior (Windows Terminal, cmd, PowerShell, bash) — color output requires TTY unless `FORCE_COLOR=1` is set
4. **Backup the user config** if you have a non-empty `~/.dazzlecmd/config.json`:

   **cmd.exe:**
   ```cmd
   if exist %USERPROFILE%\.dazzlecmd\config.json copy %USERPROFILE%\.dazzlecmd\config.json %USERPROFILE%\.dazzlecmd\config.json.bak
   ```

   **PowerShell:**
   ```powershell
   if (Test-Path $env:USERPROFILE\.dazzlecmd\config.json) { Copy-Item $env:USERPROFILE\.dazzlecmd\config.json $env:USERPROFILE\.dazzlecmd\config.json.bak }
   ```

   **POSIX:**
   ```bash
   [ -f ~/.dazzlecmd/config.json ] && cp ~/.dazzlecmd/config.json ~/.dazzlecmd/config.json.bak
   ```

5. Cleanup at the end of the checklist — restore the backup if you made one, and `dz safedel` any scratch tools.

## High-Value Verification (~5 minutes)

If you only have 5 minutes, run these 6 tests. They cover the most important user-visible behavior.

### HV.1 — Breaking change is in effect

Validates: bare `dz new <name>` no longer scaffolds; users see the sub-parser surface.

- [ ] **Steps**: `dz new --help`
- [ ] **Expected:** Help text shows three sub-types (`tool`, `kit`, `aggregator`) under "entity types". Exit code 0.
- [ ] **Why this matters:** v0.7.40 is a breaking change; the new surface must be discoverable.

### HV.2 — `dz new tool <name>` scaffolds correctly

Validates: the fully-implemented path produces the expected file structure with a `long_description` field.

- [ ] **Steps:**
  1. `dz new tool hv2-checklist --namespace core --description "HV test" --long-description "Long-form body."`
  2. Verify file structure (see Section 1.1 for shell-specific commands)
- [ ] **Expected:**
  - `projects/core/hv2-checklist/.dazzlecmd.json` exists; contains `"long_description": "Long-form body."`
  - `projects/core/hv2-checklist/hv2_checklist.py` exists with a `main()` function
- [ ] **Why this matters:** core scaffolding correctness — if this breaks, the whole feature is broken.

### HV.3 — `dz info` renders the `Details:` block

Validates: end-to-end pipeline — what was scaffolded gets displayed.

- [ ] **Steps:** Register the tool in a kit first (manual edit OR via `--kit` flag on the scaffold), then `dz info hv2-checklist`
- [ ] **Expected:** Output includes a `Details:` line followed by `Long-form body.` indented two spaces.
- [ ] **Why this matters:** Closes #61. If the field doesn't render, users won't know it exists.

### HV.4 — Stubs print planned-shape messages

Validates: the not-yet-implemented sub-types don't confuse users.

- [ ] **Steps:** `dz new kit foo` and `dz new aggregator bar`
- [ ] **Expected:** Both print "not yet implemented (v0.7.40)" + planned-shape preview to stderr; exit code 2.
- [ ] **Why this matters:** Without the stubs, users see argparse "invalid choice" errors that don't explain what's planned.

### HV.5 — User-config defaults apply

Validates: the new `new` config schema area works.

- [ ] **Steps:** Set `~/.dazzlecmd/config.json` to `{"new": {"default_namespace": "myns"}}` and run `dz new tool hv5-config-check`
- [ ] **Expected:** Tool lands in `projects/myns/hv5-config-check/`, NOT `projects/dazzletools/`.
- [ ] **Why this matters:** New config schema area; verifies the precedence chain.

### HV.6 — Bare `dz new` gives a helpful usage hint

Validates: clean migration path for users hitting the breaking change.

- [ ] **Steps:** `dz new` (no arguments)
- [ ] **Expected:** Stderr prints a usage hint listing the three sub-types, with explanatory help. Exit code 2.
- [ ] **Why this matters:** Users running old `dz new <name>` get argparse "invalid choice" today, which is okay; but bare `dz new` should be a clean migration signal.

### HV.7 — `--language rust` (or other non-python) is rejected with coming-soon message

Validates: v0.7.40 guard against internally-inconsistent manifests.

- [ ] **Steps:** `dz new tool fake-rust --language rust`
- [ ] **Expected:** Stderr shows `Error: language 'rust' is not yet supported (from --language flag).` plus a coming-soon paragraph naming v0.7.44 (4d-3) and the supported languages list. Exit code 2. No `projects/dazzletools/fake-rust/` directory is created.
- [ ] **Why this matters:** Without the guard, users get a confusing tool that says `language: "rust"` in the manifest but has a Python `.py` script and `runtime.type: "python"`. The guard is removed in v0.7.44 when real Rust scaffolding lands.

### HV.8 — `--kit <name>` writes to the kit's in-repo manifest (not the registry pointer)

Validates: the `_register_in_kit` fix lets `dz new tool --kit X` actually surface the tool in `dz list` without manual manifest edits.

- [ ] **Steps:**
  ```
  dz new tool hv8-register-check --kit dazzletools --description "Verify --kit fix"
  ```
- [ ] **Expected:**
  - Console shows `Registered in kit: dazzletools (in-repo manifest)` (NOT `(registry pointer)`)
  - `projects/dazzletools/.kit.json` `tools` list contains `"dazzletools:hv8-register-check"`
  - `kits/dazzletools.kit.json` is UNCHANGED (no `tools` array pollution)
  - `dz list` shows the tool in the dazzletools section without any manual `.kit.json` edit
- [ ] **Why this matters:** Pre-fix, `--kit core/dazzletools/...` silently wrote to the registry pointer where the loader's merge order made the entry invisible. Users had to edit `.kit.json` by hand. The fix makes `--kit` actually work for kits with in-repo manifests.

## Section 3: `dz info` rendering of `long_description`

To exercise `dz info`, the scaffolded tools must be discovered. The simplest path is to add them to a kit's tools list manually, or to use a namespace whose kit has `tools_dir: "."` and is open (e.g., dazzletools).

### 3.1 Tool with `long_description` renders `Details:` block

- [ ] **Setup:** Use a tool that's discoverable (e.g., add `dazzletools:checklist31` to `projects/dazzletools/.kit.json` `tools` list, or use `--kit dazzletools` on the scaffold to auto-register).
- [ ] **Steps:**
  ```
  dz new tool checklist31 --kit dazzletools --long-description "A test of the Details block."
  dz info checklist31
  ```
- [ ] **Expected:** Output includes:
  ```
  Description: A new dazzlecmd tool: checklist31

  Details:
    A test of the Details block.
  ```
  (The blank line before `Details:` and the 2-space indent on the body are the format.)

### 3.2 Tool without `long_description` has no `Details:` block

- [ ] **Steps:**
  ```
  dz new tool checklist32 --kit dazzletools
  dz info checklist32
  ```
- [ ] **Expected:** Output has standard fields but NO `Details:` line.

### 3.3 Long body wraps to terminal width

- [ ] **Steps:**
  - Resize terminal to ~50 columns OR set `COLUMNS=50` env var
  - Scaffold a tool with `--long-description` containing 200+ characters
  - Run `dz info`
- [ ] **Expected:** Body lines wrap; no line exceeds the terminal width. Continuation lines maintain the 2-space indent.

### 3.4 Color on TTY: `Details:` header is BOLD

- [ ] **Steps:** Run `dz info checklist31` in a TTY (no pipe, no redirection)
- [ ] **Expected:** `Details:` rendered with BOLD ANSI escape (`\033[1m`). If your terminal supports color, the word "Details:" appears visually bolder than surrounding text.

### 3.5 Color OFF when piped or `NO_COLOR=1`

- [ ] **Steps:** `dz info checklist31 | cat` (pipe) OR `NO_COLOR=1 dz info checklist31`
- [ ] **Expected:** No ANSI escape codes in output; `Details:` rendered as plain text.
