# Human Test Checklist: `--fix` Converges

**Target version:** 0.12.15-alpha
**Ships with commit:** TBD
**Companion automated tests:** 6 in `dazzle-update/tests/test_query.py::TestFixConverges`; full suite 2393. Every automated test fakes the subprocess runner — **nothing automated has performed a real convergent write.** That gap is the reason this checklist exists.

## What this is

`--fix` used to apply one pass and stop. Fixes cascade — a `git pull` rewrites the source tree, which makes the editable install stale, which is a *new* finding — so a single pass structurally could not converge, and the user had to re-run the same command until it went quiet.

It now applies, **re-measures the repo from a fresh read**, and repeats. Bounded three ways: a cap of 3 passes, stopping the moment a pass applies nothing, and deriving each pass's findings by measuring rather than predicting.

Also here: the tracked-source guard runs ~50x faster (one `git ls-files` instead of one subprocess per file), and `-v` reports read-vs-apply timing on the fix path.

**This checklist exercises a write path.** Every step that writes is marked **WRITES**. Use a repo you are willing to change.

## Prerequisites

1. dazzlecmd 0.12.15 editable; `gh` authenticated; a warm scan cache.
2. **A repo that is genuinely behind and editable-installed** — that is the only state that exercises the cascade. `dz dazzle-update --cached --only behind` will find one.
3. Know how to undo: `git reflog` for the pull, `pip show <dist>` for the install.

## High-Value Verification (~5 minutes)

### HV.1 — The cascade converges in ONE command — **WRITES**

- [ ] **Setup:** a repo that is behind upstream AND editable-installed.
- [ ] **Steps:** `dz dazzle-update <name> --fix`
- [ ] **Expected:** pull is proposed and confirmed; then `re-checking <name> after pass 1...`; then either a reinstall proposed (because the pull moved the source version) or `nothing left to fix`. **One invocation, not two.**
- [ ] **Verify:** `dz dazzle-update <name>` afterward shows no `behind-upstream` and no `stale-install-metadata`.
- [ ] **Why this matters:** the entire change. Before, this took two identical commands.

### HV.2 — A clean repo does not loop — **WRITES (no-op expected)**

- [ ] **Steps:** run `dz dazzle-update <name> --fix` again immediately.
- [ ] **Expected:** the card, then nothing applied. No re-check line, no second pass — a pass that applies nothing stops the loop.
- [ ] **Why this matters:** the stop condition. A loop that keeps going on a converged repo would confirm-prompt forever.

### HV.3 — Dry run does not pretend to converge — SAFE

- [ ] **Steps:** `dz dazzle-update <name> --fix --dry-run`
- [ ] **Expected:** one pass shown, then the note that applying may reveal follow-on work. **No** `re-checking` line — nothing changed for a second pass to observe.
- [ ] **Why this matters:** a dry run that implied convergence would be claiming a result it never measured.

### HV.4 — Declining stops everything — **WRITES (decline expected)**

- [ ] **Steps:** on a repo with a finding, run `--fix` and answer `n` (or bare Enter).
- [ ] **Expected:** nothing applied, no re-check, no second pass.
- [ ] **Why this matters:** declining must not be read as progress.

### HV.5 — The guard is fast again — SAFE

- [ ] **Steps:** `python -m pytest tests\test_sources_are_tracked.py -q`
- [ ] **Expected:** 2 passed, in about a second of test time (was ~28s on a Defender-heavy machine).
- [ ] **Why this matters:** a guard that is slow to run is a guard people skip.

## Section 1: Bounds and honesty (~5 min)

### 1.1 `--yes` composes with the loop — **WRITES**
- [ ] `<name> --fix --yes` on a cascading repo applies both passes without prompting, and still stops when nothing is left.

### 1.2 `--no-fetch` still refuses the pull half — SAFE
- [ ] `<name> --fix --dry-run --no-fetch` on a behind repo: pulls skipped with the reason; a stale-install finding on the same repo is still planned.

### 1.3 Timing attribution — SAFE
- [ ] `<name> --fix --dry-run -vv` prints `[timing] total N (read N, apply N)`. Run it for real once and confirm the `apply` figure reflects pip's cost, not the tool's.

### 1.4 The cap is real
- [ ] Not directly reproducible by hand. Confirm by reading: `MAX_FIX_PASSES = 3` and the `stopped after N passes` message exists.

## What the automated tests DO cover

Apply-count reporting, dry-run reporting zero applied, stopping on a no-progress pass, the pass cap and its message, the nothing-left message, and that a dry run never re-measures.

## What the automated tests DON'T cover

- **Any real write.** Every test fakes `subprocess.run`.
- Real pip timing and whether the loop feels acceptable when each pass costs 10–40s.
- The interactive prompt across two passes — whether being asked again after a pull reads as sensible or as a bug.
- A repo that genuinely will not converge (the cap path).

## Reporting issues found

Include the full command output, plus `git reflog -3` and `pip show <dist>` for any repo written to.

## Cleanup

`git reflog` to identify pre-pull state; `pip install -e <path>` to restore an install if needed.
