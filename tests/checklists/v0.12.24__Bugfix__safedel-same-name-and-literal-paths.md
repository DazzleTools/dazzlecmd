# Human Test Checklist: safedel same-name batches and literal paths (hotfix)

**Target version:** dazzlecmd 0.12.24, with dazzlecmd-lib 0.10.36-alpha
**Ships with commit:** TBD (pre-commit)
**Companion automated tests:**
- dazzlecmd-lib: 21 in `tests/test_core_safedel_hotfix.py`, 2 in `tests/test_package_data.py`; full suite 640 passed on Windows and on Linux (WSL)
- dazzlecmd: safedel tool suite 128 (121 pass + 7 skip on Windows; 101 pass + 27 skip on Linux), root suite 1,698 on both platforms

## What this is

A 15-minute hand run of the real `dz safedel` CLI against throwaway folders, covering what the automated tests cannot: the console output a person reads, real exit codes, Windows rename behaviour on real files, and the template set inside the installed wheel. It verifies two fixes:

- **Same-named items in one call no longer overwrite each other.** Before this release, `dz safedel a\x.json b\x.json` staged both at one trash path; the second replaced the first and the batch still reported success. Now the second is refused and left in place with an error. (Staging both under distinct paths comes in a later release.)
- **Paths are taken literally.** `dz safedel "~"` used to target the home folder. Now it targets a folder literally named `~`.

Plus one packaging fix: `dz new aggregator <name> --with ci` now finds its workflow templates in an installed wheel.

## Prerequisites

1. **dazzlecmd-lib 0.10.36a0 must be the installed copy.** `dz` imports the *installed* library, not a source tree. Either install the release, or build from a dev checkout with a regular (non-editable) install:
   ```
   python -m pip install C:\code\dazzlecmd-lib
   python -c "import dazzlecmd_lib; print(dazzlecmd_lib.__version__)"
   ```
   Expected: a version starting `0.10.36`. Prefer this over `pip install -e`: an editable install makes every `dz safedel` on the machine run whatever is in the working tree, including half-finished edits.
2. **Use a scratch folder, never a real project or your home folder.** Every step below runs inside it.

   **cmd.exe:**
   ```cmd
   mkdir %TEMP%\sd-check && cd /d %TEMP%\sd-check
   ```
   **PowerShell:**
   ```powershell
   New-Item -ItemType Directory -Force "$env:TEMP\sd-check" | Out-Null; Set-Location "$env:TEMP\sd-check"
   ```
   **POSIX:**
   ```bash
   mkdir -p /tmp/sd-check && cd /tmp/sd-check
   ```
3. Trash batches land in your normal trash store (on Windows usually `C:\Users\<you>\.safedel-trash`). That is fine; they are small and recoverable. Do not run `dz safedel clean`.

**Reset between sections:** delete and recreate the scratch folder (Cleanup, below), then `cd` back into it.

## High-Value Verification (~5 minutes)

### HV.1 -- Same-named files: nothing is lost

Validates: the second and third same-named items are refused, not overwritten.

- [ ] **Steps** (pick your shell):

  **cmd.exe:**
  ```cmd
  mkdir a b c
  echo AAAA> a\x.json
  echo BBBB> b\x.json
  echo CCCC> c\x.json
  dz safedel --yes a\x.json b\x.json c\x.json
  echo exit=%ERRORLEVEL%
  type b\x.json c\x.json
  ```
  **PowerShell:**
  ```powershell
  New-Item -ItemType Directory a,b,c | Out-Null
  "AAAA" > a\x.json; "BBBB" > b\x.json; "CCCC" > c\x.json
  dz safedel --yes a\x.json b\x.json c\x.json
  "exit=$LASTEXITCODE"
  Get-Content b\x.json, c\x.json
  ```
  **POSIX:**
  ```bash
  mkdir a b c
  echo AAAA > a/x.json; echo BBBB > b/x.json; echo CCCC > c/x.json
  dz safedel --yes a/x.json b/x.json c/x.json
  echo "exit=$?"
  cat b/x.json c/x.json
  ```
- [ ] **Expected:**
  - `Staged with errors: <timestamp>` on stderr.
  - Two `ERROR: Failed to stage ...\b\x.json: an item named 'x.json' is already staged in this batch; left in place so it is not overwritten` lines (b and c).
  - `exit=1`.
  - `b\x.json` still holds `BBBB` and `c\x.json` still holds `CCCC`. `a\x.json` is gone (staged).
- [ ] **Why this matters:** this is the data-loss bug. Before the fix all three were gone and only one file's bytes survived.

### HV.2 -- The staged one recovers with its own bytes

- [ ] **Steps:** `dz safedel recover last`, then view `a\x.json` (`type` / `Get-Content` / `cat`).
- [ ] **Expected:** `Recovered: ...\a\x.json`, and the file holds `AAAA`.
- [ ] **Why this matters:** proves the refused items did not corrupt the batch that did stage.

### HV.3 -- A folder literally named `~` is targeted, not your home folder

Validates: literal paths.

- [ ] **Steps** (pick your shell -- note PowerShell must use `.\~`, because a bare `~` there means home):

  **cmd.exe:**
  ```cmd
  mkdir "~"
  echo literal> "~\junk.txt"
  dz safedel --dry-run "~"
  ```
  **PowerShell:**
  ```powershell
  New-Item -ItemType Directory -Path '.\~' | Out-Null
  "literal" > '.\~\junk.txt'
  dz safedel --dry-run '~'
  ```
  **POSIX:**
  ```bash
  mkdir '~' && echo literal > '~/junk.txt'
  dz safedel --dry-run '~'
  ```
- [ ] **Expected:** the dry-run classifies `<scratch>\~` (your scratch folder plus `~`) as a regular directory. It must **not** show `C:\Users\<you>` (or `/home/<you>`).
- [ ] **Why this matters:** before the fix this targeted the entire home folder.
- [ ] **Then:** `dz safedel --yes "~"` (PowerShell/POSIX: `'~'`). Expected: staged; the scratch `~` folder is gone; your home folder is untouched. `dz safedel recover last` brings it back with `junk.txt` inside.

### HV.4 -- Distinct names still work normally (control)

- [ ] **Steps:** create `p\one.txt` and `q\two.txt`, then `dz safedel --yes p\one.txt q\two.txt`.
- [ ] **Expected:** `Staged to trash: <timestamp>`, both listed `[OK]`, exit 0, both originals gone. `dz safedel recover last` restores both.
- [ ] **Why this matters:** the fix must not affect ordinary batches.

### HV.5 -- `--with ci` scaffolds workflow files from the installed wheel

- [ ] **Steps:** `dz new aggregator CiCheck --with ci`, then list `CiCheck\.github\workflows` (`dir` / `Get-ChildItem` / `ls`).
- [ ] **Expected:** `test.yml` and `release.yml` exist. The `--with summary` line reads `ok: ci`, and does **not** say `skipped: ci (template dir missing ...)`.
- [ ] **Why this matters:** the published wheel used to leave the `ci` templates out.

## Section 1: Same-name edge cases

### 1.1 Same-named folders

- [ ] **Steps:** create `m\d\one.txt` and `n\d\two.txt`, then `dz safedel --yes m\d n\d`.
- [ ] **Expected:** `m\d` staged; `n\d` refused with the "already staged in this batch" error and still present with `two.txt`; exit 1.

### 1.2 One file per call is unaffected

- [ ] **Steps:** `dz safedel --yes a\x.json` (after HV.2's recovery), then `dz safedel --yes b\x.json` as a second, separate call.
- [ ] **Expected:** both succeed; each call is its own batch, so the same name in two batches is fine. `dz safedel list` shows two batches.

### 1.3 JSON output reports the refusal

- [ ] **Steps:** recreate two same-named files, then `dz safedel --yes --json r\x.json s\x.json`.
- [ ] **Expected:** `"success": false`, one entry per item, and an `errors` array naming the refused path. Exit 1.

## Section 2: Literal-path edge cases

### 2.1 Folders named after environment variables

- [ ] **Steps** (cmd.exe expands `%VAR%` even inside quotes, so escape it with `^`):

  **cmd.exe:**
  ```cmd
  mkdir ^%USERPROFILE^%
  dz safedel --dry-run ^%USERPROFILE^%
  ```
  **PowerShell:**
  ```powershell
  New-Item -ItemType Directory -Path '.\%USERPROFILE%','.\$HOME' | Out-Null
  dz safedel --dry-run '%USERPROFILE%'
  dz safedel --dry-run '$HOME'
  ```
  **POSIX:**
  ```bash
  mkdir '$HOME' && dz safedel --dry-run '$HOME'
  ```
- [ ] **Expected:** each dry-run shows the literal folder inside the scratch folder (`<scratch>\%USERPROFILE%`, `<scratch>\$HOME`), never your real profile or home path.

### 2.2 Ordinary relative and forward-slash paths still resolve

- [ ] **Steps:** `dz safedel --dry-run p/one.txt` (forward slash on Windows) and `dz safedel --dry-run .\p\..\p\one.txt`.
- [ ] **Expected:** both resolve to `<scratch>\p\one.txt`.

## Section 3: Unchanged behaviour

### 3.1 `status` and `list`

- [ ] **Steps:** `dz safedel status`, `dz safedel list`.
- [ ] **Expected:** same layout as before this release. Note: the `Trash store:` line still names the central store even when batches went to the per-volume store. That label is fixed in the next safedel release (DazzleLib/dazzlecmd-lib#7); the totals already count every store.

## Section 4: Linux (developers)

### 4.1 Both suites pass natively under WSL

- [ ] **Steps** (from Git Bash on the Windows host, in each checkout):

## What the automated tests DON'T cover

- Real console wording and stderr/stdout split as a person reads it
- Real exit codes through the `dz` launcher
- Windows rename semantics on real files outside a temp sandbox; cmd.exe's own `%VAR%` expansion before `dz` sees the argument
- The template set inside the **installed** wheel (tests check the packaging patterns, not an installed copy)
- Recovery of a refused batch end to end through the CLI

## Cleanup

**cmd.exe:**
```cmd
cd /d %TEMP% && rmdir /s /q %TEMP%\sd-check
```
**PowerShell:**
```powershell
Set-Location $env:TEMP; Remove-Item -Recurse -Force "$env:TEMP\sd-check"
```
**POSIX:**
```bash
cd /tmp && rm -rf /tmp/sd-check
```

The trash batches created above stay in your trash store and age out normally; recover any you want with `dz safedel recover`.
