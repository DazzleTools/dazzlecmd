## What this is

Foundational refactor for Phase 4e virtual-kit support. v0.7.25 ships the data structures, collision invariants, and resolve API that v0.7.26+ build on. Per project rules a 910-LOC refactor across 9 files with API-shape change warrants a human test artifact; this checklist is the backfill.

The refactor is pure-API-and-data-structure: no user-visible feature alone (those arrive in v0.7.26+). The verification surface is therefore primarily regression — that existing dispatch paths (canonical FQCN, kit-qualified shortcut, short name, favorite, precedence) all still work after the rename `insert → insert_canonical`, the index split (`fqcn_index → canonical_index + alias_index + shortcut_candidates`), and the `(project, ResolutionContext)` tuple return from `resolve()`.

What can only be human-verified beyond pytest:
- **Real subprocess dispatch** continues to work end-to-end via the new resolve API (mocks pass; production process flow needs eyes)
- **Error messages** for rule 9b violations and dangling alias pointers read clearly
- **`.fqcn_index` removal regression**: any caller that stored a reference to the old single-dict surface now fails with `AttributeError` rather than silent miss — confirm no such callers leaked into production code paths
- **Performance feel** of the new O(1) `shortcut_candidates` lookup vs. the old O(n) list comprehension on a real-sized project list (subjective, but a noticeable lag at scale would point to a bug)

### Tester guidance: temp copies, not real data

**Always work against a temp copy when possible.** This checklist's commands are mostly read-only inspection of an existing dazzlecmd install, but where any test mutates state (config writes, manifest edits, dispatch with side effects) the tester MUST direct the mutation to a temp location. Specifically:

- Use `DAZZLECMD_CONFIG` env var → temp path. Never write to your real `~/.dz/config.json`.
- For dispatch tests that take filesystem-altering actions (none in this checklist, but as a rule): redirect to `%TEMP%` / `$env:TEMP` / `/tmp`.
- For manifest-edit tests: copy the manifest to a temp dir and point `DAZZLECMD_PROJECT_ROOT` (or run from the temp dir) at the copy.
- If a step explicitly says "modify `kits/claude.kit.json`" — copy first, modify the copy, point `DAZZLECMD_PROJECT_ROOT` at the temp dir.

## Section 1: FQCNIndex three-index split

The single `fqcn_index` dict was split into three:
- `canonical_index` — `{fqcn: project}` for real on-disk tools
- `alias_index` — `{alias_fqcn: canonical_fqcn}` for virtual-kit aliases
- `shortcut_candidates` — `{(kit_first, tool_last): [canonical_fqcn, ...]}` precomputed shortcut lookup

### 1.1 — `canonical_index` populated by all real projects

- [ ] **Steps**:
  ```
  python -c "from dazzlecmd_lib.engine import AggregatorEngine; e = AggregatorEngine(); print(len(e.fqcn_index.canonical_index))"
  ```
- [ ] **Expected**: positive integer matching the count of real on-disk tools (no aliases). Typical value: 15-25 depending on which kits are loaded.
- [ ] **Verifies**: discovery populates the canonical index correctly.

### 1.2 — `alias_index` populated only via virtual kits

- [ ] **Steps**:
  ```
  python -c "from dazzlecmd_lib.engine import AggregatorEngine; e = AggregatorEngine(); print(len(e.fqcn_index.alias_index))"
  ```
- [ ] **Expected**: positive integer if virtual kits are loaded (`kits/claude.kit.json` adds 4). Zero if no virtual kits in scope.
- [ ] **Verifies**: aliases are stored separately from canonicals.

### 1.3 — `shortcut_candidates` is a dict, not a list

- [ ] **Steps**:
  ```
  python -c "from dazzlecmd_lib.engine import AggregatorEngine; e = AggregatorEngine(); print(type(e.fqcn_index.shortcut_candidates).__name__)"
  ```
- [ ] **Expected**: `dict`
- [ ] **Verifies**: the precomputed structure is a dict (O(1) lookup), not a list (O(n) scan).

## Section 3: Rule 9b enforcement

**Rule 9b**: an alias FQCN must NEVER equal a canonical FQCN. A virtual kit cannot shadow a real tool. Mirrored: a canonical cannot be inserted into a slot already claimed by an alias.

### 3.1 — `insert_canonical` rejects when alias already claimed the FQCN (rule 9b mirror)

- [ ] **Steps** (this is a code-level invariant; tested via pytest, but visible by reading the test output):
  ```
  pytest -v tests/test_fqcn_index_alias.py::TestInsertAlias::test_alias_shadowing_canonical_raises_9b -x
  ```
- [ ] **Expected**: `TestInsertAlias::test_alias_shadowing_canonical_raises_9b` passes — the test exercises both directions of rule 9b (alias-claimed-then-canonical and canonical-claimed-then-alias).
- [ ] **Verifies**: rule 9b mirror enforcement (canonical-side) is tested via the bidirectional rule 9b test.

### 3.2 — `insert_alias` rejects when canonical already exists at the same FQCN (rule 9b primary)

- [ ] **Steps**:
  ```
  pytest -v tests/test_fqcn_index_alias.py::TestInsertAlias -x
  ```
- [ ] **Expected**: tests pass; one test name references rule 9b enforcement on the alias side.
- [ ] **Verifies**: the alias-side rule 9b enforcement is tested.

### 3.3 — Idempotent re-registration of same alias→target

- [ ] **Steps**:
  ```
  pytest -v tests/test_fqcn_index_alias.py -k "idempotent" -x
  ```
- [ ] **Expected**: idempotency test passes (same `(alias_fqcn, canonical_fqcn)` re-registration does not raise).
- [ ] **Verifies**: re-loading a kit doesn't crash the engine.

### 3.4 — Different-target conflict raises

- [ ] **Verifies**: ambiguous alias declarations fail loud, not silently coalesce.

## Section 6: `.fqcn_index` removal regression check

The old single-dict surface was removed. Any caller that stored a reference to `engine.fqcn_index` and treated it as a flat dict now fails with AttributeError when accessing methods it expects (e.g., `engine.fqcn_index["foo:bar"]` would have worked when fqcn_index was a dict; now `fqcn_index` is a `FQCNIndex` object whose dict-like access is on `canonical_index`).

### 6.1 — Production code has no `engine.fqcn_index["..."]` patterns

- [ ] **Steps** (cross-shell — read-only grep):

  **cmd.exe**:
  ```cmd
  findstr /spn "fqcn_index\[" src\dazzlecmd\*.py packages\dazzlecmd-lib\src\dazzlecmd_lib\*.py
  ```

  **PowerShell**:
  ```powershell
  Select-String -Pattern 'fqcn_index\[' -Path src/dazzlecmd/*.py,packages/dazzlecmd-lib/src/dazzlecmd_lib/*.py
  ```

  **POSIX**:
  ```bash
  grep -rn 'fqcn_index\[' src/dazzlecmd/ packages/dazzlecmd-lib/src/
  ```
- [ ] **Expected**: no matches (or only matches inside test fixtures / commented examples).
- [ ] **Verifies**: no production caller is treating the new `FQCNIndex` object as a flat dict.

### 6.2 — `.canonical_index["..."]` and `.alias_index["..."]` are the new patterns

- [ ] **Steps**:
  ```bash
  # POSIX example; cross-shell equivalent: see HV pattern
  grep -rn 'canonical_index\[' packages/dazzlecmd-lib/src/dazzlecmd_lib/ | head -5
  grep -rn 'alias_index\[' packages/dazzlecmd-lib/src/dazzlecmd_lib/ | head -5
  ```
- [ ] **Expected**: matches in `engine.py`, `loader.py`, etc. — the new index access surface.
- [ ] **Verifies**: callers were migrated, not just removed.

## Section 7: CLI integration sanity

The CLI `_cmd_info`, `_cmd_kit_favorite`, `_cmd_setup`, etc. consume `find_project` / `resolve()`. Spot-check that the integration is clean.

### 7.1 — `dz info <fqcn>` works for canonical, alias, kit-shortcut, qualified-alias

- [ ] **Steps** (run all four):
  ```
  dz info dazzletools:claude-cleanup
  dz info claude:cleanup
  dz info wtf:locked
  dz info dazzletools:claude:cleanup
  ```
- [ ] **Expected**: all four return info banners. Banner content references the same underlying tool (claude-cleanup) for the first two; wtf-locked for the third; claude-cleanup for the fourth (qualified-alias form).
- [ ] **Verifies**: `_cmd_info` consumes `find_project` correctly across all resolution kinds.

### 7.2 — `dz kit favorite <short> <fqcn>` works against canonical AND alias FQCN

The `dz kit favorite` command takes TWO arguments: a short name (the user-chosen alias) and the target FQCN. The target FQCN can be either a canonical FQCN or a virtual-kit alias FQCN. The favorite-target check must consult both `canonical_index` and `alias_index`.

- [ ] **Steps** (set canonical-target favorite, set alias-target favorite, unset both — same syntax across shells):

  ```
  dz kit favorite cleanup dazzletools:claude-cleanup
  dz kit favorite mycleanup claude:cleanup
  dz kit unfavorite cleanup
  dz kit unfavorite mycleanup
  ```
- [ ] **Expected**: all four commands return success. First two output `Favorite set: <short> -> <fqcn>` (or equivalent). Both target forms accepted (canonical FQCN and alias FQCN).
- [ ] **Verifies**: cli.py favorite path was migrated to alias-aware lookup. If the alias-form `dz kit favorite mycleanup claude:cleanup` is rejected, the favorite-target check is canonical-only and needs fixing.
- [ ] **Cleanup**: the unfavorite calls leave the temp config in original state (or you can reset it via the cleanup section below).

## What the automated tests DON'T cover

- **Real subprocess dispatch** through the new tuple-return API on Windows codepage 437/1252 (mocks pass; real PATH resolution + interpreter spawn is human-eyes territory)
- **Performance feel** of the new O(1) shortcut lookup at scale (mocks don't time anything)
- **Error-message clarity** for rule 9b violations — does the rendered message tell a real user what they did wrong and how to fix it? (Currently raises with a message; subjective whether it's good UX)
- **`AttributeError` regression detection** for any production code path that stored a reference to `engine.fqcn_index` from before the split. Section 6 grep is a proxy but doesn't exercise actual call sites.
- **Performance under load**: a kit with 50+ tools triggers the precomputed-vs-list-comprehension difference visibly. Manually creating a synthetic 50-tool kit and timing `dz list` would catch a regression.
- **`dz info` across all six resolution kinds** end-to-end: Section 7.1 covers four of six (canonical, alias, kit_shortcut, qualified_alias). The remaining two (`favorite`, `precedence`) need a non-trivial setup with `dz kit favorite` plus a colliding short name, respectively.
