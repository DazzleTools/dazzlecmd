**Target version:** 0.13.14 - 0.13.16 (shipped together in the v0.13.16-alpha release)
**Ships with commits:** `0af7199` v0.13.14 (dzr on Linux), `28124b9` v0.13.15 (decline releases, session names, dzr.cmd hand-over), `c68d7e9` v0.13.16 (add-by-name, swap)
**Companion automated tests:** relaunch suite 218 -- new in this span: `test_relaunch_dzr_sourced.py` (8), `test_relaunch_decline_releases.py` (9), `test_relaunch_session_names.py` (5), `test_relaunch_handover.py` (+2), `test_relaunch_add_pending.py` (8), `test_relaunch_swap.py` (11, plus the per-verb help test for `swap`). Red-green checked: each feature's key test was shown to fail with its behaviour removed.

## What this is

What a person runs to check, in real shells and real tabs, the relaunch changes that followed the v0.13.8 checklist (`v0.13.8__Tool__dz-relaunch.md`). It covers what the tests cannot: a real bash sourcing `dzr`, cmd's "Terminate batch job (Y/N)?" after Ctrl+C, how the questions read, and what a person sees in the roster.

## Prerequisites

1. dazzlecmd 0.13.16 or newer: `dz --version`.
2. **Use a throwaway store** for every step except the real-tab ones marked **[real tab]**. Set it in each terminal you use:

   **cmd.exe**:
   ```cmd
   set DZ_RELAUNCH_HOME=%TEMP%\relaunch-checklist
   ```
   **PowerShell**:
   ```powershell
   $env:DZ_RELAUNCH_HOME = "$env:TEMP\relaunch-checklist"
   ```
   **POSIX**:
   ```bash
   export DZ_RELAUNCH_HOME=/tmp/relaunch-checklist
   ```
3. Two empty folders to use as members (any two; examples below use `%TEMP%\rl-a` and `%TEMP%\rl-b`, `/tmp/rl-a` and `/tmp/rl-b` on POSIX).
4. **Never run `claim -o` on a Claude session that is open right now** -- it would attach a second client to it. Claude steps here use sessions that are closed.
5. To reset between sections: `dz relaunch <set> release --all`, or delete the throwaway store folder (`rmdir /s /q %DZ_RELAUNCH_HOME%`, `Remove-Item -Recurse $env:DZ_RELAUNCH_HOME`, `rm -rf "$DZ_RELAUNCH_HOME"`).

## High-Value Verification (~5 minutes)

### HV.1 -- bash `dzr` changes the shell's folder

- [ ] **Steps (POSIX, or Git Bash):**
  ```bash
  dz relaunch shell-init bash --install
  dz relaunch new hv && dz relaunch hv add /tmp/rl-a --label a
  cd / && . dzr hv claim && pwd
  ```
- [ ] **Expected:** the install says where it wrote `dzr` (beside `dz`; `~/bin` under Git Bash) and prints the line `alias dzr='. dzr'`; `pwd` prints `/tmp/rl-a`.
- [ ] **Why this matters:** without it, `dzr` on Linux cannot move the terminal at all.

### HV.2 -- answering "no" gives the member back

- [ ] **Steps (any shell; cmd shown):**
  ```cmd
  dz relaunch new hv2 && dz relaunch hv2 add --label py -- python -c "print(1)"
  dzr hv2 claim -o        (answer n)
  dz relaunch hv2
  ```
- [ ] **Expected:** `not run -- released hv2:1 py`; the roster shows member 1 `free  [never opened]`.
- [ ] **Why this matters:** a declined question used to leave the tab holding the member.

### HV.3 -- Claude members show the session name

- [ ] **Steps:** add a closed Claude session by its id: `dz relaunch hv2 add --claude <session-id> --label s`, then `dzr hv2 claim -o s` and answer `n`.
- [ ] **Expected:** `will run: csb resume <session-id>  (<session name>)`.
- [ ] **Why this matters:** a bare id gives no way to decide whether to say yes.

### HV.4 -- adding a session csb cannot see asks once

- [ ] **Steps:** `dz relaunch hv2 add --claude NO_SUCH_SESSION_xyz --label ghost`, answer `y`; then `dz relaunch hv2`.
- [ ] **Expected:** one explanation line and `add it by name anyway? ... [y/N]` -- no wait first; the roster shows `csb session NO_SUCH_SESSION_xyz  (not found yet)`.
- [ ] **Why this matters:** the alternative was re-running the command until csb caught up.

### HV.5 -- swap keeps the numbers in order

- [ ] **Steps:** `dz relaunch hv2 swap 1 2`, then `dz relaunch swap 1 2 hv2`, viewing the roster after each.
- [ ] **Expected:** after the first, member 1 is the former member 2 and vice versa, and the numbers still read 1, 2, 3...; the second swaps them back.
- [ ] **Why this matters:** reordering a set used to mean deleting and re-adding members.

## Section 1: `dzr` on bash (Linux, macOS, Git Bash)

### 1.1 Install, current, uninstall
- [ ] `dz relaunch shell-init bash --install` twice: the second says `already current`.
- [ ] The file has LF line endings only: `python -c "print(open('PATH','rb').read().count(b'\r'))"` prints `0` (use the path the install printed).
- [ ] `dz relaunch shell-init bash --uninstall` moves it to the safedel trash; on Git Bash, `~/bin` stays if it held anything else.

### 1.2 Sourced vs executed
- [ ] `. dzr hv claim` moves the shell (HV.1).
- [ ] Running it without the dot -- `bash "$(command -v dzr)" hv claim` -- prints `dzr: source it ...` and exits 2; the shell does not move.
- [ ] After `. dzr nosuchset claim`, the shell is still open, `echo $?` is non-zero, and `type __dzr_main` says not found (nothing left defined).

### 1.3 The optional alias
- [ ] `alias dzr='. dzr'` then `dzr hv release --all` and `dzr hv claim` move the shell like the dotted form.

### 1.4 Git Bash only
- [ ] The installed file is in `~/bin`, not beside `dz.exe`. In a **new cmd** tab (not started from Git Bash), `where dzr` lists only `dzr.cmd`.

## Section 2: `dzr.cmd` and Ctrl+C (Windows cmd)

### 2.1 Reinstall picks up the new form
- [ ] `dz relaunch shell-init cmd --install` reports `wrote ...\dzr.cmd` (replacing relaunch's older copy) or `already current`.
- [ ] `type` the file: it contains `--cd-file="%DZR_TMP%\cd.txt" --cd-format=cmd` and no `set "DZ_RELAUNCH_CD_FILE=%DZR_TMP%` line.

### 2.2 "Terminate batch job? Y" leaves nothing behind  [real tab]
- [ ] In a new cmd tab: `dzr hv2 claim -o`, press **Ctrl+C** at the question.
- [ ] Expected: `not run -- released ...`, then cmd's `Terminate batch job (Y/N)?` -- answer **Y**.
- [ ] Then `echo [%DZ_RELAUNCH_CD_FILE%]` prints `[%DZ_RELAUNCH_CD_FILE%]` (not set) -- nothing lingers in the tab.
- [ ] A later plain `dz relaunch hv2 claim` prints a `cd /d ...` line to paste rather than claiming "this tab moves to ...".

## Section 3: `claim -o` decline

### 3.1 Each kind of "no" releases
For each of: `n`, a bare Enter, Ctrl+C --
- [ ] `dzr hv2 claim -o` then the answer: prints `not run -- released hv2:<n> <label>`, exit code 3 (`echo %ERRORLEVEL%` / `$LASTEXITCODE` / `$?`), and `dz relaunch hv2` shows the member free and `[never opened]`.

### 3.2 Yes keeps; already-held is kept
- [ ] Answer `y`: the member stays claimed by this tab (the program runs; exit it).
- [ ] In the same tab, `dzr hv2 claim -o` again and answer `n`: `not run -- this tab still holds hv2:<n> ... (it had it before)`; still claimed.

### 3.3 No extra session after a decline
- [ ] With no other claims alive, decline once, then claim with `y`: the `session N started ...` line appears once, and N is the next number -- not two higher.

## Section 4: session names

- [ ] A member added by name shows `(name)` after `csb resume <id>` in `claim -o` and in plain `claim` output.
- [ ] A member added by id before 0.13.15 (no name recorded) shows the name at its next claim; afterwards the roster shows the name too.
- [ ] With csb removed from PATH, the line shows the id alone and nothing errors.

## Section 5: add-by-name when csb cannot see the session

- [ ] `n` at the question: nothing added, exit 3.
- [ ] `-y`: added with no question.
- [ ] With input redirected (no console) -- `echo. | dz relaunch hv2 add --claude NOPE2 --label x` -- refuses and says `--yes` adds it anyway.
- [ ] Resolution **[real tab]**: name a brand-new Claude session, add it by name immediately (answer `y`), wait a minute, run `dz relaunch <set>`: `(not found yet)` is gone and `claim -o` shows `csb resume <id>  (<name>)`.
- [ ] Still unknown at `claim -o`: the line reads `csb resume <name>`; csb's own error says so if the name is wrong.

## Section 6: swap

- [ ] `dz relaunch hv2 swap 1 2`, `dz relaunch swap 1 2 hv2`, `dz relaunch swap hv2 1 2` and a by-label form (`swap py s hv2`) all work.
- [ ] Claim follows: claim member 1 in a tab, `swap 1 2` from another tab, then `dz relaunch hv2` shows the first tab now holding number 2 (the same member).
- [ ] Approval follows: `claim -o -y` on a command member that was swapped still runs without the "not the command relaunch recorded" warning.
- [ ] Refusals: `swap 1 1` and `swap 1` change nothing and say why.

## What the automated tests DON'T cover

- cmd's real "Terminate batch job (Y/N)?" after a Ctrl+C (needs a person at the keyboard)
- Terminal rendering of the questions and roster in Windows Terminal, Git Bash and a Linux terminal
- zsh and macOS (the bash path is expected to work there; not run)
- csb's real timing when a session is brand new (the tests stub csb)
- `claim -o` with real Claude sessions (POC-3 in the v0.13.8 checklist)

## Reporting issues found

1. Note the section and step number.
2. Capture the exact command, its output and the exit code.
3. Copy the set file from the throwaway store (`<store>/sets/<set>.json`).
4. File an issue referencing this checklist and #125.
