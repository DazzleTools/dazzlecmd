# Human Test Checklist: dz efs-recover -- owner-authorized offline EFS recovery

**Target version:** v0.12.5-alpha (dazzlecmd); tool `efs-recover` 0.1.0 (dazzletools kit), on dpapick3 0.7.1 + cryptography.
**Ships with commit:** TBD (pre-commit checklist)
**Companion automated tests:** 21 unit tests in `src/dazzlecmd/projects/dazzletools/efs-recover/tests/test_efs_recover.py` -- run in the tool's OWN .venv (`.venv\Scripts\python -m pytest tests -q`); they skip cleanly under the dazzlecmd main suite (no dpapick3 there). They cover encoding-robust password reading, the literal-password guard, the KDF-equivalence proof, PFX round-trip, and CLI dry-run/exit-codes against a synthetic tree.

## What this is

`dz efs-recover` rebuilds a lost EFS certificate's private key from an OLD backup profile -- including the hard case where that backup's account SID differs from the current machine (a "defunct / cross SID") -- then imports it and strips EFS from the affected files. The automated tests can't touch real DPAPI: this checklist covers the end-to-end recovery that needs **your own** backup key material and account password, plus the Windows-specific behavior (legacy CSP import, `cipher /d`).

**Owner-authorized use only:** it requires your own backup profile's key material AND your own account password. It reuses dpapick3 (no mimikatz), runs offline, and never puts a password on a command line.

## Prerequisites

1. Windows (the import + `cipher /d` steps are Windows-only). `dz` on PATH; the tool set up (`dz setup dazzletools:efs-recover` -> its own `.venv` with dpapick3 + cryptography).
2. A **backup profile** you own that contains, under `…\Users\<name>\AppData\Roaming\Microsoft\`: `SystemCertificates\My\Certificates\<thumbprint>`, `Crypto\RSA\<SID>\`, `Protect\<SID>\` (master keys), and ideally `Protect\CREDHIST`.
3. One or more **candidate account passwords** from that profile's era, each in its own text file (never on a command line).
4. A **copy** of the encrypted target files to decrypt (work on a copy; keep the originals until verified).
5. Know the **backup profile's SID** and the **cert thumbprint** (`cipher /c <encrypted-file>` names the thumbprint that can decrypt it).

State-isolation: the tool is dry-run by default; nothing is written or imported without `--apply`.

## High-Value Verification (~10 minutes, needs real key material)

### HV.1 -- Dry-run validates key material and writes nothing

- [ ] **Steps:** `dz efs-recover --backup-profile <profile> --sid <backupSID> --cert <thumbprint> --targets <copy-of-encrypted-dir>` (no `--apply`).
- [ ] **Expected:** prints `key material : OK`, `MODE : DRY-RUN`, the plan (would recover / import / decrypt N files), exit code 2. Nothing imported, no PFX written.
- [ ] **Why:** the default must never mutate anything.

### HV.2 -- Recovery unlocks the key and saves a PFX

- [ ] **Steps:** add `--password-file <pw1>` (repeat for several candidates), `--pfx-out <dir>\<cert>.pfx`, `--apply`.
- [ ] **Expected:** progress shows `KDF=standard` then (if needed) `KDF=faithful`; `recovered key from container …`; `saved recovered .pfx -> …`. If none of the passwords work it fails cleanly (exit 1) telling you to check the SID / add the era password.
- [ ] **Why:** proves the offline master-key unwrap + CAPI-container decrypt + PFX assembly across a defunct SID.

### HV.3 -- Legacy CAPI CSP import + EFS strip

- [ ] **Steps:** same command as HV.2 (import + decrypt happen in the same `--apply` run).
- [ ] **Expected:** `imported recovered key into Cert:\CurrentUser\My`, then `decrypt+strip: OK; N/N now plaintext`.
- [ ] **Check:** `cipher /c <a decrypted file>` no longer lists it as encrypted; `(attributes -band 0x4000) == 0`.
- [ ] **Why this matters:** XP/2003-compat EFS files need the key in a legacy **CAPI** provider; a CNG import silently fails ("Key information cannot be retrieved"). This verifies the `certutil -csp` path.

### HV.4 -- Password privacy (never echoed)

- [ ] **Steps:** capture the full run output; search it for your password string.
- [ ] **Expected:** **zero** occurrences. Passwords are read from files in-process only.
- [ ] **Also:** `dz efs-recover --password foo …` is refused (exit 1) -- literal passwords are never accepted.

### HV.5 -- Fast-path reuse: import the saved PFX directly

- [ ] **Steps:** on more files later encrypted to the same cert:
  ```
  certutil -user -f -p "" -csp "Microsoft Enhanced Cryptographic Provider v1.0" -importpfx My "<saved>.pfx" NoChain,NoRoot
  cipher /d /s:"<folder>"
  ```
- [ ] **Expected:** files decrypt with no re-recovery needed.
- [ ] **Why:** the saved PFX is the "never do the archaeology again" payoff.

## Section 1: robustness (~5 min)

### 1.1 Multi-password + KDF fallback
- [ ] Provide several `--password-file` candidates where only one is correct (and, if you have such a profile, one that only the "faithful" KDF unlocks). Expected: the tool tries each password under standard then faithful, and succeeds on the right one.

### 1.2 Wrong SID fails cleanly
- [ ] Run with the CURRENT machine's SID instead of the backup's. Expected: no master key unlocks; clear failure telling you to use the backup profile's SID.

### 1.3 Passwordless-by-default PFX
- [ ] With no `--pfx-password-file`, the saved `.pfx` is passwordless (rely on the storage location's protection). Confirm no random/ephemeral password is generated. `--pfx-password-file <f>` adds a wrapper if wanted.

### 1.4 Archive the raw key material
- [ ] Add `--save-keymaterial <dir>`. Expected: the cert(s), `Crypto\RSA\<SID>`, `Protect\<SID>`, and `CREDHIST` are copied there for deep-archival recovery of other certs later.

## What the automated tests DON'T cover

- **Real DPAPI master-key unwrap** with a real password + SID (needs real key material).
- **Cross/defunct-SID** recovery end to end.
- **Legacy CAPI CSP import** + `cipher /d` (Windows-only, real EFS files).
- **Performance** of the KDF against real (high-iteration) master keys.
- **The standard-vs-faithful KDF selection** on a real profile.

## Reporting issues found

Section + step, exact command (password files redacted), output; file against DazzleTools/dazzlecmd. The engine's crypto lives in dpapick3 (upstream) -- KDF perf issues go there.

## Cleanup

- **Securely zero** the candidate password files (do NOT recycle/safedel -- secrets need real deletion).
- Keep the encrypted originals until you've verified the decrypted copies.
- The saved PFX + key-material archive belong in an already-protected location.
