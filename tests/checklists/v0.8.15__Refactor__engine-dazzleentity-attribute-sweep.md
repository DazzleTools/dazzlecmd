# Human Test Checklist: engine.py DazzleEntity attribute sweep (dispatch core)

**Target version:** dazzlecmd 0.8.15 / dazzlecmd-lib 0.7.12 (alias dazzle-dz 0.8.15)
**Ships with commits:** `1d47ef0` (v0.8.14 — engine discovery-pipeline sweep), `0a77835` (v0.8.15 — FQCN-index core + fixture migration)
**Companion automated tests:** the full suite (1254 passed / 14 skipped) covers engine.py heavily — notably `tests/test_engine_fqcn.py`, `tests/test_fqcn_index_alias.py`, `tests/test_path_form_convergence.py`, `tests/test_engine_recursive.py`, `tests/test_stale_favorites_warning.py`, `tests/test_env_var_injection.py` (≈236 engine/fqcn/discover/recursive tests). Byte-gate (`tests/one-offs/run_byte_gate.py`) = 10 OK / 0 FAIL against the v0.7.54 baselines.

## What this is

This is the verification companion to the **engine.py attribute sweep** — the sixth and final production file migrated from dict access to typed `DazzleEntity` attribute access. `engine.py` is the dispatch core: discovery, the FQCN index, cross-aggregator recursion, and tool dispatch all live here.

The automated suite + byte-gate already prove the **read** commands (`dz list`/`info`/`tree`/`mode status`) are byte-identical to 0.7.54. This checklist deliberately targets the gap those leave: **WRITE/MUTATE and real-dispatch paths** that the byte-gate does not exercise end-to-end. This is the exact blind spot that hid the `cache_manifest` crash on `dz mode switch` earlier in the 0.8.x line (the byte-gate covered `mode status`, not `switch`). The sweep touched: the set-once `project.fqcn = …` write, `project.kit_active = …` propagation, `kit.tools = […]`, the auto-realpath alias writes (`alias_project.auto_realpath_alias`/`.canonical_fqcn`), the `"_fqcn" not in project` → `project.fqcn is None` membership check, and the dispatch path itself.

## Prerequisites

1. **OS**: Windows (primary) — also valid on POSIX. Some sections (auto-realpath junctions) are Windows-specific and flagged.
2. **Install**: an editable install of this working tree (`pip install -e .` from repo root) so `dz` resolves to 0.8.15. Confirm with `dz --version` → should show `0.8.15`.
3. **State isolation — REQUIRED**: never run against your real `~/.dz/config.json`. Every section sets an isolated `DAZZLECMD_CONFIG` pointing at a throwaway file in the temp dir. The real config has `list_view:"all"` and personal `active_kits`, which will make outputs differ — that is config drift, not a regression.
4. **Reset between sections**: delete the throwaway config (or re-point `DAZZLECMD_CONFIG` at a fresh path). Each section is independent.

> **Deletions**: if any step asks you to remove a file/dir, prefer `dz safedel <path>` (recoverable) over `rm`/`del`/`Remove-Item`.

**Set up an isolated config** (do this once at the start; reuse for read-only sections):

- [ ] **Steps** (pick your shell):

  **cmd.exe**:
  ```cmd
  set DAZZLECMD_CONFIG=%TEMP%\dz_checklist.json
  echo {"list_view":"default","_schema_version":1,"active_kits":["wtf"],"disabled_kits":[]}> %DAZZLECMD_CONFIG%
  type %DAZZLECMD_CONFIG%
  ```

  **PowerShell**:
  ```powershell
  $env:DAZZLECMD_CONFIG = "$env:TEMP\dz_checklist.json"
  '{"list_view":"default","_schema_version":1,"active_kits":["wtf"],"disabled_kits":[]}' | Out-File -Encoding utf8 $env:DAZZLECMD_CONFIG
  Get-Content $env:DAZZLECMD_CONFIG
  ```

  **POSIX**:
  ```bash
  export DAZZLECMD_CONFIG=/tmp/dz_checklist.json
  echo '{"list_view":"default","_schema_version":1,"active_kits":["wtf"],"disabled_kits":[]}' > "$DAZZLECMD_CONFIG"
  cat "$DAZZLECMD_CONFIG"
  ```

## High-Value Verification (~5 minutes)

If you only have 5 minutes, run these six. They exercise the write/dispatch paths the byte-gate can't.

### HV.1 — A real tool actually dispatches and runs

Validates: the end-to-end dispatch path (`_run_tool` → `RunnerRegistry.resolve(project)` → run), which the byte-gate never executes.

- [ ] **Steps** (same across shells, `dz` only):
  ```
  dz find --help
  dz safedel --help
  ```
- [ ] **Expected:** each prints the tool's own help/usage and exits 0. No Python traceback, no `AttributeError`, no `'dict' object has no attribute …` / `'Tool' object has no attribute …`.
- [ ] **Why this matters:** if attribute access broke the dispatch path, the tool wouldn't run at all — this is the single most important user-facing behavior.

### HV.2 — Exact-FQCN dispatch resolves to the right tool

Validates: FQCN-index resolution (`insert_canonical`/`resolve`) now reading `project.fqcn`/`.short_name`/`.kit_import_name`.

- [ ] **Steps:**
  ```
  dz core:find --help
  dz info core:safedel
  ```
- [ ] **Expected:** `dz core:find --help` runs the `find` tool; `dz info core:safedel` shows safedel's info block with the correct FQCN. No collision warnings printed to stderr that weren't there in 0.7.54.
- [ ] **Why this matters:** confirms the index build (`_build_fqcn_index`) and `insert_canonical` produce a correct canonical map after the sweep.

### HV.3 — `dz mode switch` does not crash (the historical bug)

Validates: the write/publish path that crashed in 0.8.1 (`cache_manifest`), through engine discovery now returning entities.

- [ ] **Steps:**
  ```
  dz mode status
  ```
  Then a dry-run / no-op switch on a tool you do NOT mind touching, or use `--dry-run` if available:
  ```
  dz mode switch core:find --dry-run
  ```
- [ ] **Expected:** `mode status` lists each tool's mode; the dry-run switch prints what it *would* do and exits 0 — no `AttributeError: 'DazzleEntity' object has no attribute 'items'` or similar.
- [ ] **Why this matters:** this is the exact path that broke once already; it must survive the engine sweep. **Do not run a real (non-dry-run) switch against a live submodule** — see Section 2 for the sandboxed full-switch procedure.

### HV.4 — Cross-aggregator recursion (wtf enabled) resolves and dispatches

Validates: `_rewrite_virtual_kit` / `_apply_virtual_kits` / nested `_kit_active` propagation reading entity attributes.

- [ ] **Steps:** with `active_kits` including `wtf` (the prereq config does):
  ```
  dz list
  dz info wtf:core:restarted
  dz wtf:core:restarted --help
  ```
- [ ] **Expected:** `dz list` shows wtf's tools nested under the `wtf` kit; `dz info wtf:core:restarted` resolves the 3-segment FQCN; the dispatch runs wtf's tool. No "could not resolve" error, no duplicated entries.
- [ ] **Why this matters:** the recursive/fractal path is the most complex in engine.py and is barely touched by the byte-gate.

### HV.5 — `dz kit disable`/`enable` flips tool visibility

Validates: `project.kit_active` write propagation in `_discover_aggregator` and the active/all partition in `discover()`.

- [ ] **Steps:**
  ```
  dz list
  dz kit disable wtf
  dz list
  dz kit enable wtf
  dz list
  ```
- [ ] **Expected:** after `disable wtf`, wtf's tools disappear from `dz list`; after `enable wtf`, they return. Exit 0 throughout.
- [ ] **Why this matters:** confirms `kit_active` (a promoted bool field, written in several places in the sweep) drives the active partition correctly.

### HV.6 — `dz tree` banner shows 0.8.15 and the tree body is unchanged

Validates: the whole discovery → annotation → render pipeline, byte-identical except the version banner.

- [ ] **Steps:**
  ```
  dz tree
  ```
- [ ] **Expected:** line 1 reads `dz (dazzlecmd PREALPHA 0.8.15)`; every line below it is identical to the 0.7.54 baseline structure (same tools, same nesting, same markers).
- [ ] **Why this matters:** a structural tree diff would mean discovery/annotation drifted.

## Section 1: Real dispatch (the `_run_tool` path)

### 1.1 Dispatch by short name, exact FQCN, and alias

- [ ] **Steps:**
  ```
  dz find --help
  dz core:find --help
  dz safedel status
  ```
- [ ] **Expected:** all three run their tool; short-name and exact-FQCN resolve to the same tool; no resolution error.
- [ ] **Check:** stderr has no new collision/ambiguity warnings vs. a 0.7.54 run.

### 1.2 Unresolvable command gives a clean error (not a traceback)

- [ ] **Steps:**
  ```
  dz this-tool-does-not-exist
  ```
- [ ] **Expected:** a friendly "command not found"/suggestion message and non-zero exit — NOT a Python traceback referencing `engine.py`, `.fqcn`, or `.name`.
- [ ] **Why:** confirms the dispatch error paths (`Error: could not resolve runtime for {project.name}`) format correctly with attribute access.

## Section 2: `dz mode switch` write path (SANDBOXED)

> **Skip the full switch unless you can sandbox it.** A real `mode switch` mutates a git submodule (publish ↔ embedded/dev). Only run the non-dry-run form against a throwaway tool/aggregator you created for testing — **never** against the repo's real submodules.

### 2.1 Dry-run switch (safe everywhere)

- [ ] **Steps:**
  ```
  dz mode status
  dz mode switch core:find --dry-run
  ```
- [ ] **Expected:** dry-run prints the intended actions and exits 0; `cache_manifest` runs without `AttributeError` (it iterates the discovered tool entity via the shim's `.items()`).

### 2.2 Full switch on a throwaway tool (optional, sandboxed)

- [ ] **Steps:** in a scratch aggregator/tool you control, run `dz mode switch <throwaway> publish` then `dz mode switch <throwaway> dev` (or the modes your tool supports).
- [ ] **Expected:** both directions complete, the manifest is cached/restored correctly, and `dz mode status` reflects the new mode. No crash, no half-written manifest.
- [ ] **Check:** the cached manifest file is valid JSON and round-trips (`python -m json.tool <cached-manifest>` succeeds).

## Section 3: Cross-aggregator recursion (wtf embedded)

### 3.1 Nested FQCN resolution and dispatch

- [ ] **Steps:** (wtf enabled)
  ```
  dz list
  dz info wtf:core:restarted
  dz info wtf:core:locked
  dz wtf:core:restarted --help
  ```
- [ ] **Expected:** 3-segment FQCNs resolve; the tools dispatch; `dz list` shows them nested under `wtf` with no duplication.

### 3.2 Virtual-kit aliases (if wtf ships any)

- [ ] **Steps:**
  ```
  dz kit list
  dz why-locked --help
  ```
  (substitute the real virtual-kit alias if `why-locked` isn't present in your build)
- [ ] **Expected:** virtual-kit aliases (from `_apply_virtual_kits` / `name_rewrite`) resolve to their canonical target and dispatch. No "shares its name with a canonical kit" warning unless one was expected in 0.7.54.

## Section 4: Kit activation (`kit_active` writes)

### 4.1 Disable / enable round-trip

- [ ] **Steps:**
  ```
  dz kit list
  dz kit disable wtf
  dz list
  dz kit status
  dz kit enable wtf
  dz list
  ```
- [ ] **Expected:** disable removes wtf's tools from the active list and `dz kit status` marks wtf inactive; enable restores both. The config file's `active_kits`/`disabled_kits` update accordingly (inspect the isolated config).
- [ ] **Check** (inspect isolated config):

  **cmd.exe**: `type %DAZZLECMD_CONFIG%`
  **PowerShell**: `Get-Content $env:DAZZLECMD_CONFIG`
  **POSIX**: `cat "$DAZZLECMD_CONFIG"`

## Section 5: Edge paths

### 5.1 Auto-realpath dedup (#65) — Windows junction scenario (optional)

> Only if you can reproduce a junction/symlink that makes the same on-disk tool reachable via two FQCNs.

- [ ] **Steps:** create a junction so a tool dir is reachable twice (per CLAUDE.md, **PowerShell only** for junctions), then `dz list --show all`.
- [ ] **Expected:** the tool appears once as canonical (shortest FQCN) and the duplicate is marked as an auto-realpath alias (`[+]` marker), not a collision error. This exercises the `alias_project.auto_realpath_alias = True` / `.canonical_fqcn = …` writes in `_build_fqcn_index`.
- [ ] **Cleanup:** remove the junction (`dz safedel` or `Remove-Item` the junction pointer — never the target).

### 5.2 Deeply-nested reroot hint

- [ ] **Steps:** with a tool at 4+ FQCN segments reachable (e.g. a doubly-nested aggregator), run `dz list` (ensure `DZ_QUIET` is unset).
- [ ] **Expected:** a single stderr hint suggesting rerooting the deeply-nested tool, naming the deepest FQCN. Setting `DZ_QUIET=1` suppresses it.
- [ ] **Note:** this is best-effort; skip if no 4-segment tool is reachable in your build.

## What the automated tests DON'T cover (this checklist's job)

- **Real tool dispatch** — the byte-gate never runs a tool; tests mock runners. HV.1, 1.1.
- **Real `mode switch` write path on disk** — atomicity, manifest round-trip under real conditions. Section 2.
- **Cross-aggregator dispatch with real submodules** — wtf actually resolving + running end-to-end. HV.4, Section 3.
- **Junction/symlink auto-realpath dedup** — environment-specific, Windows codepage/FS behavior. Section 5.1.
- **Shell rendering** — banner/version string, tree alignment, stderr hint formatting on Windows codepage 437/1252.
- **Error message quality** — is "could not resolve" actually helpful? Section 1.2.
