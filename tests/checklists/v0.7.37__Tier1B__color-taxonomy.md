# Human Test Checklist: v0.7.37 — Terminal Color Taxonomy

**Target version:** v0.7.37 (dazzlecmd-lib 0.6.0; dazzlecmd 0.7.37)
**Ships with commit:** v0.7.37 feat(lib): phase 4e v0.7.37 -- terminal color taxonomy across display surfaces (closes #49)
**Companion automated tests:** 1012 passed / 13 skipped (up from 979 in v0.7.36). +33 new in `tests/test_colors.py`. Existing render-function tests cover the engine=None / no-color code paths.

## What this is

Tier 1 final commit of the dazzlecmd 0.7.x master closeout plan. Adds a new `dazzlecmd_lib.colors` module (8-color ANSI palette + `should_use_color()` env-aware TTY probe + `colorize(text, *codes)` + `colorize_for(stream, text, *codes)` convenience wrapper + semantic stderr wrappers `warn(text)` and `error(text)`) and wires color emphasis into every meta-command render surface (`render_list` / `render_info` / `render_tree` / `render_kit_list` / `render_kit_status`) plus the user-facing stderr warning paths in `default_meta_commands.py`, `cli_helpers.py`, and dazzlecmd's `_cmd_setup`. dazzlecmd is a thin instance of dazzlecmd-lib for these surfaces (post-v0.7.34 collapse), so amdead and wtf-windows inherit color automatically.

Slim by design: 8 ANSI codes (`RESET`/`BOLD`/`DIM`/`RED`/`GREEN`/`YELLOW`/`CYAN`/`BRIGHT_RED`). No truecolor, no 256-color, no rich dependency. Optional `dazzlecmd-lib[color]` extra pulls in `colorama` for legacy cmd.exe on Windows; modern Windows 1511+ handles ANSI natively via VT processing.

Color detection precedence (per `should_use_color(stream)`):
1. `NO_COLOR` set (any value, including empty) → no color (community standard).
2. `DZ_COLOR=always` OR `FORCE_COLOR=1` → color on (overrides isatty).
3. `DZ_COLOR=never` → no color.
4. Fallback: `stream.isatty()`.

## High-Value Verification (~5 minutes)

If you only have 5 minutes, run these 5 tests. They cover the highest-impact color paths.

### HV.1 — Plain output when piped (no env override)

Validates: default behavior. Color stays off when the user redirects to a file or pipes through `cat -v`, so ANSI bytes never leak into log files or grep output.

- [ ] **Steps** (POSIX/bash-WSL):
  ```bash
  dz list | cat -v | head -20
  ```
- [ ] **Expected:** Output is plain text. No `^[[` sequences anywhere. Section headers (`core:`, `dazzletools:`, etc.) print without ANSI codes.
- [ ] **Why this matters:** Piped output is the most common case people hit. If color leaks into pipes by default, every `dz list | grep claude` output becomes garbled.

### HV.2 — Color emerges in a real TTY

Validates: color emission gated on isatty. Run interactively (no pipe).

- [ ] **Steps** (any shell):
  ```
  dz list
  ```
- [ ] **Expected:** Section headers (e.g., `core:`, `dazzletools:`) render in BOLD. The total at the bottom (`N tool(s)`) is plain. If you have a `[*]` shadow marker on any tool, it renders BOLD+RED. Cross-aggregator `[+]` markers render CYAN.
- [ ] **Why this matters:** This is what 95% of users see. If the TTY path is broken, the whole feature is invisible.

### HV.3 — `NO_COLOR=1` wins absolutely

Validates: community-standard override. NO_COLOR must suppress color even when forced.

- [ ] **Steps** (POSIX):
  ```bash
  NO_COLOR=1 DZ_COLOR=always dz list | head -10
  ```
  (PowerShell)
  ```powershell
  $env:NO_COLOR = "1"; $env:DZ_COLOR = "always"; dz list | Select-Object -First 10; Remove-Item Env:\NO_COLOR; Remove-Item Env:\DZ_COLOR
  ```
- [ ] **Expected:** Plain output. NO_COLOR overrides DZ_COLOR=always per the documented precedence.
- [ ] **Why this matters:** NO_COLOR is the cross-tool community standard (https://no-color.org/). Users add it to their shell profile to disable color across every tool they run.

### HV.4 — `DZ_COLOR=always` forces color through a pipe

Validates: force-on path including Windows colorama strip=False fix. Without `strip=False`, colorama strips ANSI on piped output even when the user asked for color.

- [ ] **Steps** (POSIX/bash-WSL):
  ```bash
  DZ_COLOR=always dz list 2>/dev/null | cat -v | head -10
  ```
  (PowerShell):
  ```powershell
  $env:DZ_COLOR = "always"; dz list | Select-Object -First 10; Remove-Item Env:\DZ_COLOR
  ```
- [ ] **Expected:** `^[[1m...^[[0m` sequences visible in the piped output. Section headers are BOLD-wrapped. On Windows, colorama is told `strip=False` for forced paths so the ANSI bytes survive the pipe.
- [ ] **Why this matters:** Users who run `dz list | less -R` or `dz list > log.txt && cat log.txt` need an opt-in to preserve color. The forced path's strip=False handling is the subtle Windows-specific bug fix.

### HV.5 — `dz info <shadowed-tool>` shows BOLD+YELLOW "Shadow status:"

Validates: the new banner styling. Pick any tool whose short name conflicts with a reserved meta-command (e.g., the safedel project may have a tool whose name shadows).

- [ ] **Steps:** find a shadowed tool — first try `dz list --show all` and look for `[*]` markers; pick the first short name and run:
  ```
  dz info <shortname>
  ```
- [ ] **Expected:** Output includes a "Shadow status:" block. In a TTY, the literal text "Shadow status:" is BOLD+YELLOW. The two bullet lines describing the conflict are plain.
- [ ] **Why this matters:** Shadow conflicts are subtle and easy to miss; the BOLD+YELLOW banner is what catches a user's eye when they're scanning info output looking for "why isn't this tool working when I type its short name."

## Section 1: Color detection precedence

### 1.1 NO_COLOR overrides FORCE_COLOR

- [ ] **Steps** (POSIX):
  ```bash
  NO_COLOR= FORCE_COLOR=1 dz list 2>&1 | head -5 | cat -v
  ```
- [ ] **Expected:** Plain output. NO_COLOR is set (empty string still counts per spec).

### 1.2 DZ_COLOR=never suppresses TTY color

- [ ] **Steps** (any shell, interactively, no pipe):
  ```
  DZ_COLOR=never dz list
  ```
- [ ] **Expected:** Plain output despite the TTY. DZ_COLOR=never is the project-specific opt-out.

### 1.3 DZ_COLOR=never loses to FORCE_COLOR (documented precedence)

- [ ] **Steps:** the FORCE_COLOR branch is checked BEFORE the `DZ_COLOR=never` branch in `should_use_color()`. Setting both forces color on.
  ```bash
  DZ_COLOR=never FORCE_COLOR=1 dz list 2>/dev/null | cat -v | head -3
  ```
- [ ] **Expected:** ANSI codes visible. Matches `test_dz_color_never_loses_to_force_color` in `tests/test_colors.py`.

### 1.4 Unknown DZ_COLOR values fall through to isatty

- [ ] **Steps:**
  ```bash
  DZ_COLOR=purple dz list | head -3 | cat -v   # piped: no color
  DZ_COLOR=purple dz list                       # TTY: color
  ```
- [ ] **Expected:** Plain when piped, color when TTY. Garbage values don't break detection.

### 1.5 Case-insensitive DZ_COLOR

- [ ] **Steps:**
  ```bash
  DZ_COLOR=Never dz list                # suppresses TTY color
  DZ_COLOR=ALWAYS dz list 2>/dev/null | head -3 | cat -v   # forces color through pipe
  ```
- [ ] **Expected:** Both behave as documented (lowercase canonical forms).

## What the automated tests DON'T cover

Things only a human can verify:

- **Terminal rendering fidelity** — does BOLD actually render bold in PuTTY? Does DIM render visibly in Windows Terminal? Does YELLOW look right on a dark-theme cmd.exe?
- **Colorama on legacy cmd.exe** — the auto-detection path uses `colorama.init()` (strips on pipes); the forced path uses `colorama.init(strip=False)`. Visual verification on a real cmd.exe with the codepage 437 default is the only real test.
- **Cross-shell column-width math** — the plain/styled label split keeps column widths correct in the presence of ANSI codes, but rendering at extreme terminal widths (40 cols, 250 cols) needs a human eye.
- **Color blindness considerations** — RED+YELLOW shadow markers may be invisible to red-green color blindness. The BOLD emphasis is the redundant cue. Verify the [*] marker is still readable without color (test by piping or `NO_COLOR=1`).
- **NO_COLOR / DZ_COLOR / FORCE_COLOR semantics in CI environments** — env-var precedence is unit-tested, but CI runners may default isatty differently than interactive shells.
- **Discoverability** — does the user know to set `NO_COLOR=1`? The CHANGELOG documents it; the `colors.py` module docstring documents it; whether a person scanning `dz --help` would find their way to it is a different question.
