# Human Test Checklist: DazzleEntity object model (Phase 0)

**Target version:** v0.8.1 (dazzlecmd) / v0.7.0 (dazzlecmd-lib)
**Ships with commit:** v0.8.1 -- DazzleEntity foundational redesign (Stages 2-5; Stage 1's standalone model shipped as v0.8.0)
**Companion automated tests:** `packages/dazzlecmd-lib/tests/test_entity.py` (29 tests: construction, discriminated union, shim transparency, round-trip, set-once C1, Groupable MRO, reserve-dot, detect_type) + the ported `test_aggregator_config.py` (frozen-Pydantic safety net) + the full regression suite (1241 passed / 14 skipped at `tests/ packages/`).

## What this is

The 0.8.x DazzleEntity redesign replaces the anonymous `dict`s that represented tools / kits / aggregators with a typed `DazzleEntity` object model (Pydantic v2), with the {grouping, ungrouping} primitive expressed as a capability mixin (`Groupable`). This is a **foundational redesign with no intended user-visible change**: a backward-compat shim keeps the ~252 existing dict-access call sites working, and the migration boundary is the top-level entity only (nested blocks like `runtime` / `_vars` / `setup` stay plain dicts). The quality bar is therefore **byte-identical output** vs the 0.7.54 baseline across every `dz` / `wtf` / `amdead` surface, with the version string as the only permitted difference. This checklist is the human half of that gate: it confirms the migration is invisible in real use, the new module boundaries hold, and the reserved `.` axis rejects bad input.

## Prerequisites

1. Windows or POSIX host with the repo installed editable (`pip install -e .` at the repo root and in `packages/dazzlecmd-lib`). Pydantic v2 must be importable.
2. **Config isolation is mandatory** -- the default `dz` view depends on `~/.dz/config.json` (`list_view`, `active_kits`). To reproduce the baselines you MUST point `DAZZLECMD_CONFIG` at a throwaway file; never edit your real config. The baseline `dz list` was captured with `list_view: default`, `active_kits: ["media", "wtf"]`.
3. Reset between sections by deleting the throwaway config (it is recreated by each section that needs it).

Create the throwaway config (matches the captured baseline state):

- [ ] **Steps** (pick your shell):

  **cmd.exe**:
  ```cmd
  set DAZZLECMD_CONFIG=%TEMP%\dz_v080_test.json
  > %DAZZLECMD_CONFIG% echo {"list_view":"default","_schema_version":1,"active_kits":["media","wtf"],"disabled_kits":[]}
  ```

  **PowerShell**:
  ```powershell
  $env:DAZZLECMD_CONFIG = "$env:TEMP\dz_v080_test.json"
  '{"list_view":"default","_schema_version":1,"active_kits":["media","wtf"],"disabled_kits":[]}' | Set-Content -Encoding utf8 $env:DAZZLECMD_CONFIG

  ```

## High-Value Verification (~5 minutes)

If you only have 5 minutes, run these. They cover the byte-identical guarantee and the new module boundaries.

### HV.1 -- `dz --version` reports 0.8.1

Validates: the version finalize landed (PHASE dropped, all four version sites bumped).

- [ ] **Steps:** `dz --version`
- [ ] **Expected:** `dazzlecmd PREALPHA 0.8.1 (0.8.1_main_...)` -- base version `0.8.1`, no `-alpha` suffix.
- [ ] **Why this matters:** if it still shows an `-alpha` suffix the `PHASE` marker wasn't cleared and the release isn't final.

### HV.2 -- `dz list` is unchanged from 0.7.x behavior

Validates: the loader now builds `DazzleEntity` objects but the rendered list is identical.

- [ ] **Steps:** with the throwaway config active, `dz list`
- [ ] **Expected:** the usual sectioned output (`core:`, `core:f:` virtual kit, `dazzletools:`, `media:`, `wtf:core:`) with the **default** footer `34 tool(s) (23 canonical + 11 virtual-kit alias(es)). Use --show all ...`. No `[+]` markers in the default view, no tracebacks, no Pydantic warnings on stderr.
- [ ] **Why this matters:** the list command exercises discovery -> FQCN index -> virtual-kit projection end-to-end on entities; if the migration leaked, this is where it shows.

### HV.3 -- `dz info` on a real tool still resolves and dispatches

Validates: the shim (`entity["field"]`) keeps the ~252 dict-access call sites working.

- [ ] **Steps:** `dz info core:safedel` then `dz safedel --help`
- [ ] **Expected:** info prints the tool's metadata block; `--help` dispatches into the real tool and prints its usage. No `KeyError`, no `AttributeError`.
- [ ] **Why this matters:** info + dispatch are the densest dict-access paths; a broken shim surfaces here immediately.

### HV.4 -- `core.links` re-export identity holds

Validates: link primitives relocated to `dazzlecmd_lib.core.links`, re-exported from `paths` with identity preserved.

- [ ] **Steps:**
  ```
  python -c "import dazzlecmd_lib.paths as p, dazzlecmd_lib.core.links as l; assert p.is_linked_project is l.is_linked_project and p.create_link is l.create_link and p.get_link_target is l.get_link_target and p.remove_link is l.remove_link; print('OK')"
  ```
- [ ] **Expected:** prints `OK`. The four names in `paths` ARE the `core.links` objects (not copies).
- [ ] **Why this matters:** downstream callers (`mode.py`, `importer.py`, wtf-windows) import from `paths`; if identity broke, link-aware behavior (mode switching, "Linked to:" status) silently diverges.

### HV.5 -- the reserved `.` axis rejects a dotted name

Validates: `reserve_field_axis` is wired at the single enforcement point.

- [ ] **Steps:**
  ```
  python -c "from dazzlecmd_lib.entity import reserve_field_axis; reserve_field_axis(name='find.recipe')"
  ```
- [ ] **Expected:** raises `ValueError` mentioning the field-access axis (the `.` is reserved). A clean name like `reserve_field_axis(name='claude-cleanup', namespace='dazzletools')` does NOT raise.
- [ ] **Why this matters:** `.` is reserved now for the future two-axis FQCN (`:` hierarchy, `.` field descent); if enforcement is missing, a tool named with a `.` would corrupt later field-access parsing.

### HV.6 -- cross-aggregator surfaces unchanged

Validates: the library migration is transparent to other consumers.

- [ ] **Steps:** `wtf list` and `amdead list`
- [ ] **Expected:** both print their tool lists with no tracebacks. (These read the same library code dazzlecmd does.)
- [ ] **Why this matters:** dazzlecmd-lib is the product; wtf / amdead prove the migration didn't couple anything to dazzlecmd specifically.

## Section 2: Entity model surface (~3 min)

### 2.1 Discriminated union + hard-fail

- [ ] **Steps:**
  ```
  python -c "from dazzlecmd_lib.entity import build_entity, AmbiguousEntityTypeError, Tool; t=build_entity({'name':'x','namespace':'core'}, entity_type='tool'); print(type(t).__name__, t.name)"
  python -c "from dazzlecmd_lib.entity import build_entity, AmbiguousEntityTypeError; build_entity({'name':'x'})"
  ```
- [ ] **Expected:** first prints `Tool x`; second raises `AmbiguousEntityTypeError` (no `type`, no `entity_type` -> hard fail, never a silent guess).

### 2.2 Shim transparency + set-once FQCN (C1)

- [ ] **Steps:**
  ```
  python -c "from dazzlecmd_lib.entity import Tool; t=Tool.model_validate({'name':'rn','namespace':'core','runtime':{'type':'python'}}); assert t['name']==t.name=='rn'; assert t['runtime']=={'type':'python'}; t.fqcn='core:rn'; assert t.fqcn=='core:rn'; \nimport pytest" 2>NUL || python -c "from dazzlecmd_lib.entity import Tool; t=Tool.model_validate({'name':'rn','namespace':'core','runtime':{'type':'python'}}); assert t['name']==t.name=='rn'; assert t['runtime']=={'type':'python'}; t.fqcn='core:rn'; assert t.fqcn=='core:rn'; print('shim+C1 read OK')"
  ```
  (Simpler cross-shell form -- run this one-liner):
  ```
  python -c "from dazzlecmd_lib.entity import Tool; t=Tool.model_validate({'name':'rn','namespace':'core','runtime':{'type':'python'}}); assert t['name']==t.name=='rn'; assert t['runtime']=={'type':'python'}; t.fqcn='core:rn'; assert t.fqcn=='core:rn';\ntry:\n t.fqcn='core:hacked'; print('FAIL: set-once not enforced')\nexcept RuntimeError: print('shim transparent + C1 set-once OK')"
  ```
- [ ] **Expected:** prints `shim transparent + C1 set-once OK`. The shim returns typed fields and nested dicts identically; reassigning `fqcn` to a different value raises `RuntimeError` (canonical identity is set-once).

### 2.3 Round-trip strips computed keys

- [ ] **Steps:**
  ```
  python -c "from dazzlecmd_lib.entity import Tool; t=Tool.model_validate({'name':'rn','namespace':'core'}); t['_fqcn']='core:rn'; t['_kit_active']=True; m=t.to_manifest(); print('clean' if not any(k.startswith('_') for k in m) else 'LEAK', m.get('name'))"
  ```
- [ ] **Expected:** prints `clean rn` -- `to_manifest()` drops the computed `_`-prefixed keys but keeps the real manifest fields.

## What the automated tests DON'T cover

- **Shell rendering**: the byte-identical gate is run by a script, but a human should eyeball `dz list` / `dz tree` in a real terminal (codepage, wrapping, no stray `[+]`).
- **Real cross-aggregator dispatch**: `wtf <tool>` / `amdead <tool>` invoking actual subprocesses on a real machine.
- **Config drift awareness**: the most likely false alarm (a real `~/.dz/config.json` with `list_view: all`) -- a human knows to isolate the config; a mock does not.
- **Pydantic import-time stderr**: only visible when the module is imported in a fresh process with warnings unsuppressed.
- **Performance feel**: discovery should feel as snappy as 0.7.54 (the probe measured ~1.8ms/500 incl I/O -- a non-issue, but confirm nothing stalls).
