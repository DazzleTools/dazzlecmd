# Human Test Checklist: `dz find` -- ignore-rules default flip (`--no-ignore` by default, `--gitignore` opt-in)

**Target version:** v0.12.2-alpha
**Companion automated tests:** 11 in `tests/test_find_ignore_defaults.py` (command-build defaults: 5, contradiction guard: 1, real-fd integration: 5) + the existing 13 in `tests/test_find_passthrough.py`.

## What this is

`dz find` used to inherit fd's code-search default: anything matched by `.gitignore`/`.ignore`/`.fdignore` was silently filtered out, so the finder could report "No matches" for a file plainly visible in `dir /s`. Ignore rules are now **bypassed by default** (fd always gets `--no-ignore`); the new `--gitignore` flag opts back into fd's filtering; the legacy `--no-ignore` flag stays accepted as the now-default spelling; zero-result output hints at the applicable blind spot (`-H`, or dropping `--gitignore`).

The automated tests verify command-building and `.fdignore` behavior in a temp dir. This checklist covers what they can't: real `.gitignore` semantics inside an actual git repo, the `-o`/`-l` action surface (launching real applications), and how the hints render in a real terminal.

## Prerequisites

1. `fd` on PATH (`dz find --check`).
2. A git repo whose `.gitignore` hides real files. The original reproduction case is ideal if you have it: `C:\code\Dazzle-Locate32` (its `.gitignore` excludes `*.exe` and the vendored build tree). Otherwise create one:

   **POSIX:** `mkdir /tmp/igtest && cd /tmp/igtest && git init -q && echo "*.exe" > .gitignore && touch tool.exe visible.txt`
   **PowerShell:** `ni -ItemType Directory $env:TEMP\igtest; cd $env:TEMP\igtest; git init -q; sc .gitignore "*.exe"; ni tool.exe,visible.txt`

## High-Value Verification (~2 minutes)

### HV.1 -- the original bug: gitignored file is found by default

Validates: the locate32.exe regression is dead.

- [ ] **Steps:** in the git repo, `dz find tool.exe` (or in Dazzle-Locate32: `dz find locate32.exe`)
- [ ] **Expected:** the absolute path prints; exit code 0. In Dazzle-Locate32, `dz find "*.exe" --count` prints `5` -- the same total `dir /s /w *.exe` reports.
- [ ] **Why this matters:** a finder that denies an existing file fails its one job; this was the shipped behavior through 0.12.1.

### HV.2 -- `--gitignore` restores fd's filtering, with a hint

- [ ] **Steps:** `dz find tool.exe --gitignore`
- [ ] **Expected:** `No matches for: tool.exe` plus the hint line `(ignore-rules filtering is on; drop --gitignore to search ignored paths)`, both on **stderr**; exit code 1.
- [ ] **Why this matters:** the minority (code-search) workflow must remain one flag away, and its zero-result dead end must explain itself.

## Section 1: default-mode details

### 1.1 non-git directory behaves identically
- [ ] Copy `tool.exe` + `.gitignore` to a dir with no `.git`; `dz find tool.exe` finds it there too (pre-0.12.2, results differed between git and non-git dirs).

### 1.2 legacy `--no-ignore` still accepted
- [ ] `dz find tool.exe --no-ignore` -> same output as bare `dz find tool.exe`; no warning, no error.

### 1.3 contradiction guard
- [ ] `dz find tool.exe --gitignore --no-ignore` -> usage + `error: --gitignore and --no-ignore are contradictory`; exit code 2.

### 1.4 hidden files remain the documented blind spot
- [ ] `dz find no-such-file.xyz` -> `No matches` + `(hidden files/dirs are not searched; add -H to include them)`.
- [ ] `dz find no-such-file.xyz -H` -> `No matches` with **no** hint line.

## Section 2: actions on previously-hidden results (mocks can't cover)

### 2.1 `-o` opens a gitignored file
- [ ] In Dazzle-Locate32: `dz find locate32.exe -o` -> locate32 actually launches (the user's original intent). Close it afterwards.

### 2.2 `-l` selects the file in the file manager
- [ ] `dz find locate32.exe -l` -> Explorer (or platform equivalent) opens `...\x64 - Release\bin` with `locate32.exe` selected -- note the path contains a space, which must survive the `explorer /select,` invocation.

### 2.3 `-c` copies the path
- [ ] `dz find locate32.exe -c` -> paste somewhere; the full absolute path arrives intact.

## Section 3: interaction with other surfaces

### 3.1 help text reads correctly
- [ ] `dz find -h` -> `--gitignore` listed under search options with the "pre-0.12 default" note; `--no-ignore` marked "(default; kept for backward compatibility)"; the examples block shows the `--gitignore` example aligned with its neighbors.

### 3.2 passthrough still layers on top
- [ ] `dz find tool.exe -- --no-ignore` -> works (duplicate `--no-ignore` is harmless to fd).

### 3.3 `--count` / `-0` respect the new default
- [ ] `dz find "*.exe" --count` counts ignored files; `dz find "*.exe" -0 | xargs -0 -n1 echo F:` emits them NUL-delimited.

## Cleanup

- [ ] Remove the scratch repo: `dz safedel /tmp/igtest` (POSIX) / `dz safedel $env:TEMP\igtest` (PowerShell).
- [ ] Close anything `-o`/`-l` opened.

## What the mocks don't cover (why this checklist exists)

- Real `.gitignore` semantics inside a git repo (the automated integration test uses `.fdignore` because gitignore rules only apply inside repos; this checklist closes that gap).
- `os.startfile` / `explorer /select,` actually launching things, including a target path with an embedded space (`x64 - Release`).
- stderr-vs-stdout separation and hint rendering in a real terminal (cmd, PowerShell, WSL).
- Whether the flipped default *feels* right in daily use -- watch for noise complaints on broad patterns in big repos (`venv`, `node_modules` reappearing); that feedback feeds the deferred config-default decision.
