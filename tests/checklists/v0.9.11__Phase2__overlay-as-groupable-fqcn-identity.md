# Human Test Checklist: Phase 2 — Overlay as a Groupable grouping transition

**Target version:** v0.9.11 (dazzlecmd) / 0.8.13 (dazzlecmd-lib)
**Ships with commit:** `1ed178d` v0.9.11 feat(lib,tests): Phase 2 overlay body -- constitutional home is a real FQCN-index entry (refs #180, #179) (contract slice: `e997fc2` v0.9.10)
**Companion automated tests:** `tests/test_constitutional_identity.py` (16 tests, +3 for the overlay: real-index entry, overlay provenance, alias-row exclusion); `tests/test_states.py` (PROJECTION axis); byte-gate `tests/one-offs/run_byte_gate.py` (10 surfaces).

## What this is

A human-runnable verification of the **overlay** primitive: a constitutional tool's true home identity (`dazzlecmd_lib:core:safedel`, the "bones") is now a real, dispatchable entry in the FQCN index, surfaced on this aggregator under its prefixless projection (`core:safedel`, the "skin") via an `overlay` alias. Overlay is the inverse of a virtual kit — both are the `{group, ungroup}` naming primitive in opposite directions. This checklist covers the human/real-terminal gap the byte-gate and mocks can't: real dispatch of the absolute home name, the overlay-provenance banner wording, and the `[lib]`-vs-`[+]` marker distinction as actually rendered.

1. Windows / macOS / Linux with the repo checked out at `1ed178d` (or later) and dazzlecmd installed editable (`pip install -e .` + the lib).
2. Use an **isolated config** so your real dotfiles don't skew `dz list` (a real `list_view: "all"` config adds `[+]` markers and changes spacing):

   ```cmd

## High-Value Verification (~3 minutes)

### HV.1 — The absolute home name dispatches through the real index

Validates: the overlay alias is real (not a string shim) — `dz <home-fqcn>` actually runs the tool.

- [ ] **Steps** (cross-shell safe, `dz` only):
  ```
  dz dazzlecmd_lib:core:safedel --help
  ```
- [ ] **Expected:** the safedel CLI help prints (`usage: dz safedel ...`). Exit 0.
- [ ] **Why this matters:** if this fails, the overlay alias isn't registered and the absolute home identity is unreachable — the core promise of "a real path is always resolvable" is broken.

### HV.2 — `dz info <home-fqcn>` shows overlay provenance

Validates: resolution traversed the overlay alias and reports it honestly.

- [ ] **Steps:**
  ```
  dz info dazzlecmd_lib:core:safedel
  ```
- [ ] **Expected:** first line is the dim banner `(overlay: 'dazzlecmd_lib:core:safedel' is the constitutional home in dazzlecmd_lib; surfaced here as 'core:safedel')`, then `Name: safedel`, `FQCN: core:safedel`, `Absolute: dazzlecmd_lib:core:safedel   (constitutional; overlaid from dazzlecmd_lib)`.
- [ ] **Why this matters:** confirms the banner says *overlay*, not "virtual-kit alias" — the wording must reflect the real relationship.

### HV.3 — `dz info core:safedel` is unchanged (no banner)

Validates: typing the prefixless projection resolves directly to the canonical (no alias traversal), so the common path is untouched.

- [ ] **Steps:**
  ```
  dz info core:safedel
  ```
- [ ] **Expected:** NO `(overlay: ...)` banner; starts at `Name: safedel`; still shows the `Absolute: dazzlecmd_lib:core:safedel   (constitutional; ...)` line.
- [ ] **Why this matters:** the overlay must be dispatch-additive — it cannot change the everyday prefixless experience.

### HV.4 — `[lib]` marker, not `[+]`, for an overlay-only tool

Validates: an overlay alias does NOT make its canonical look like it "has aliases" (`[+]`). `links` has only the overlay alias (no virtual-kit alias in a clean config).

- [ ] **Steps:**
  ```
  dz list --show all
  ```
- [ ] **Expected:** `links` is marked `[lib]` and NOT `[+]`. (`safedel` is also `[lib]`. It additionally shows `[+]` **iff a virtual kit aliases it** — e.g. a local `kits/f.kit.json` with `f:rm -> core:safedel`. Note `f` may carry `"always_active": true`, so it shows up even with `active_kits: []`; in a clean public checkout without that kit, `safedel` shows only `[lib]`. The point: `[+]` reflects a *virtual-kit* alias, never the overlay alias.)
- [ ] **Why this matters:** `[+]` means "virtual-kit overlay"; `[lib]` means "constitutional engine." Conflating them would mislead users about how the tool is reachable. The overlay alias must never trigger `[+]`.

### HV.5 — The overlay alias is dispatch-only (absent from `--show alias`)

Validates: the home FQCN does not clutter the alias enumeration (display stays byte-identical to pre-overlay).

- [ ] **Steps** (filter for the absolute form):

  **cmd.exe**: `dz list --show alias | findstr dazzlecmd_lib`
  **PowerShell**: `dz list --show alias | Select-String dazzlecmd_lib`
  **POSIX**: `dz list --show alias | grep dazzlecmd_lib`
- [ ] **Expected:** no output (the overlay alias is not listed as a virtual-kit alias row).
- [ ] **Why this matters:** the overlay is shown via `[lib]` + the epilogue legend, not as an alias row — keeping the list legible.

## Section 1: Self-prefix vs cross-home dispatch

### 1.1 Native tool absolute (self-prefix) still resolves

- [ ] **Steps:**
  ```
  dz info dazzlecmd:core:find
  dz dazzlecmd:core:find --help
  ```
- [ ] **Expected:** both resolve to `find` (the self-prefix `dazzlecmd:` is string-stripped). `dz info` shows NO overlay banner (it's a native tool, not overlaid) and `Absolute: dazzlecmd:core:find`.
- [ ] **Check:** the self-prefix path is a pure string normalization — distinct from the cross-home overlay (HV.1/HV.2).

### 1.2 A non-constitutional lib-prefixed name does NOT resolve

- [ ] **Steps:**
  ```
  dz info dazzlecmd_lib:core:nope
  ```
- [ ] **Expected:** `Tool 'dazzlecmd_lib:core:nope' not found.` (only the real constitutional names — safedel, links — get an overlay alias).

## Section 2: links parity

### 2.1 The links home dispatches + shows provenance

  dz info dazzlecmd_lib:core:links
  ```
- [ ] **Expected:** the links CLI help prints; `dz info` shows the `(overlay: ...surfaced here as 'core:links')` banner and `Name: links`.
