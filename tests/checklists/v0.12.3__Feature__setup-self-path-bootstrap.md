# Human Test Checklist: setup-self PATH bootstrap (`dz setup dz`)

**Target version:** v0.12.3 (dazzlecmd) + the paired dazzlecmd-lib release carrying `self_setup`
**Ships with commit:** TBD (issue #103)
**Companion automated tests:** 38 tests in dazzlecmd-lib `tests/test_self_setup.py` (normalization, scheme detection, registry-seam fix flow, orchestration, hints); 8 tests in `tests/test_setup_self.py` here (app-side routing, engine-None resilience, flag flow)

## What this is

`setup` aimed at the aggregator itself (`dz setup dz`, `dz setup dazzlecmd`, `python -m dazzlecmd setup dazzlecmd`) diagnoses whether `dz` is reachable and repairs the Windows user-scheme trap: a non-elevated `pip install` on an all-users Python lands launchers in `%APPDATA%\Python\Python3XY\Scripts`, which is never on PATH. The automated tests exercise every branch through monkeypatched registry seams -- this checklist verifies the parts only a real machine can: the actual `HKCU\Environment` write, `WM_SETTINGCHANGE` propagation to genuinely fresh shells, TTY prompt behavior, and the first-run hint in real terminals. Anyone verifying a release runs this; the Windows sections need a Windows box.

## Prerequisites

1. **Windows 10/11 box** for Sections 1-3 (the registry/broadcast reality); any Linux/macOS box for Section 4.
2. dazzlecmd + the paired dazzlecmd-lib installed via pip (the real wheel, not editable) into a **user-scheme** install if you want the full broken-state experience -- see 1.1 for how to induce it safely.
3. **Back up your user PATH before anything else** (the tool also backs up on every write, but belt and suspenders):

   **cmd.exe**:
   ```cmd
   reg query HKCU\Environment /v Path > %TEMP%\path-before-checklist.txt
   ```

   **PowerShell**:
   ```powershell
   reg query HKCU\Environment /v Path | Out-File "$env:TEMP\path-before-checklist.txt"
   ```

4. Reset between sections: restore the user PATH from the tool's own backup (`%USERPROFILE%\.dazzlecmd\path-backup-<ts>.txt` holds the raw value and kind) or from step 3's export, using `reg add HKCU\Environment /v Path /t REG_EXPAND_SZ /d "<raw value>" /f`. Open a fresh terminal after any restore.

**State isolation note**: the only mutating step is the PATH append (1.3/HV.2). Everything else is read-only. There is no config-file surface in this feature.

## High-Value Verification (~5 minutes)

**If you only have 5 minutes**, run these. Any failure here means the feature didn't ship.

### HV.1 -- Self-target routes to diagnosis, not tool lookup

Validates: the self-name special case ahead of tool resolution.

- [ ] **Steps** (cross-shell, dz commands only):
  ```
  dz setup dz
  ```
- [ ] **Expected:** A "Self-setup diagnosis for dz <version>" block (python path, install scheme, scripts dir, launcher/[OK]/[X] lines) -- NOT "Tool 'dz' not found."
- [ ] **Why this matters:** if routing fails, the entire feature is unreachable and the README's recovery instruction is a lie.

### HV.2 -- The fix actually lands in the registry, kind preserved

Validates: `fix_windows` end-to-end (the seam-mocked part, for real).

- [ ] **Steps** (PowerShell, on a box where the scripts dir is NOT yet on the persisted user PATH -- see 1.1 to induce):
  ```powershell
  reg query HKCU\Environment /v Path   # note the value TYPE (usually REG_EXPAND_SZ) and content
  python -m dazzlecmd setup dazzlecmd --yes
  reg query HKCU\Environment /v Path
  ```
- [ ] **Expected:** scripts dir appended; value TYPE unchanged (REG_EXPAND_SZ stays REG_EXPAND_SZ); any `%USERPROFILE%`-style entries still unexpanded; a backup file reported under `%USERPROFILE%\.dazzlecmd\`; message says to open a NEW terminal.
- [ ] **Why this matters:** a flattened REG_EXPAND_SZ or truncated PATH is worse than the bug we're fixing.

### HV.3 -- A genuinely fresh shell finds dz

Validates: WM_SETTINGCHANGE + persisted PATH -> real-world reachability.

- [ ] **Steps:** after HV.2, open a NEW terminal from the Start menu / Windows Terminal "+" (NOT a child of the old shell), then:
  ```
  dz --version
  ```
- [ ] **Expected:** version banner. `where dz` shows the user-scheme Scripts path.
- [ ] **Why this matters:** this is the user-visible definition of "fixed"; nothing mocked can prove it.

### HV.4 -- Idempotent re-run

Validates: normalized membership check against the just-written value.

- [ ] **Steps** (in that new terminal):
  ```
  dz setup dz
  ```
- [ ] **Expected:** all-[OK] diagnosis, "Everything is in order.", exit 0, NO prompt, NO registry write, NO new backup file in `%USERPROFILE%\.dazzlecmd\`.
- [ ] **Why this matters:** a non-idempotent fixer grows PATH forever.

### HV.5 -- First-run hint appears exactly when useful

Validates: `__main__` hint wiring, silence when healthy.

- [ ] **Steps:**
  ```
  python -m dazzlecmd list
  ```
- [ ] **Expected (healthy box):** normal listing, NO hint on stderr. **Expected (broken box, pre-fix):** one stderr line pointing at `python -m dazzlecmd setup dazzlecmd`.
- [ ] **Why this matters:** the hint is the only breadcrumb a stranded user gets after pip's install-time warning scrolls away.

### HV.6 -- Ordinary tool setup is untouched

Validates: no regression in the tool path of the same verb.

- [ ] **Steps:**
  ```
  dz setup
  dz setup find -- --dry-run
  ```
- [ ] **Expected:** listing shows tools with setup declared (with a leading PATH-health warning ONLY if the box is broken); `dz setup find` runs the fd installer's dry-run as before.
- [ ] **Why this matters:** the self-case is spliced ahead of tool resolution -- this proves the splice didn't bleed.

## Section 1: The broken-install scenario, end to end (~15 min, Windows)

### 1.1 Induce the user-scheme broken state safely

- [ ] **Steps** (PowerShell): temporarily REMOVE the user-scheme Scripts dir from the user PATH if present (note it first!), using the raw value from `reg query HKCU\Environment /v Path`, then `reg add HKCU\Environment /v Path /t REG_EXPAND_SZ /d "<value without the Scripts entry>" /f`. Open a fresh terminal.
- [ ] **Check:** `dz` -> "'dz' is not recognized..."; `python -m dazzlecmd list` works AND emits the stderr hint.

### 1.2 Diagnose-only run (no flags), decline the prompt

- [ ] **Steps** (fresh interactive terminal):
  ```
  python -m dazzlecmd setup dazzlecmd
  ```
  Answer `n` at the `[Y/n]` prompt.
- [ ] **Expected:** diagnosis shows [X] on both PATH lines; prompt renders cleanly (no codepage garbage -- ASCII only); after `n`: "Not changed", mention of `--yes`, exit code 1 (`echo %ERRORLEVEL%` / `echo $LASTEXITCODE`), registry untouched.

### 1.3 Dry-run, then accept

- [ ] **Steps:**
  ```
  python -m dazzlecmd setup dazzlecmd --dry-run
  python -m dazzlecmd setup dazzlecmd
  ```
  Answer `Y` (and once, just press Enter -- default is yes).
- [ ] **Expected:** dry-run prints the would-be value, exit 0, no write. Accept path: writes, reports backup file, broadcast happens (no error), exit 0.
- [ ] **Check:** backup file exists and contains the PRE-write raw value and kind line.

### 1.4 Non-interactive refusal

- [ ] **Steps** (any shell; piping kills the TTY):
  ```
  echo. | python -m dazzlecmd setup dazzlecmd
  ```
  (POSIX: `echo | python -m dazzlecmd setup dazzlecmd`)
- [ ] **Expected:** no hang, no write; prints the exact `--yes` command to run; exit 1.

### 1.5 The "stale shell" state heals the CURRENT shell

- [ ] **Steps:** in the SAME (old) terminal where the fix was applied:
  ```
  dz setup dz
  ```
  (via `python -m dazzlecmd setup dazzlecmd` if `dz` is still unreachable there)
- [ ] **Expected:** "[X] ... (this shell)" but "[OK] ... persisted"; then "To fix THIS shell right now (<your shell>), run:" with the correct invocation for the shell you are actually in (cmd -> `"%TEMP%\dz-path.cmd"`; PowerShell -> `. "$env:TEMP\dz-path.ps1"`; git-bash -> `source "$TEMP/dz-path.sh"`) and a "that line is now on your clipboard" note. Exit 0, no prompt.
- [ ] **Then:** paste/run the line IN THAT SHELL -> `[dz] PATH updated for this session.` -> `dz --version` works WITHOUT opening a new terminal.
- [ ] **Negative (PowerShell only):** run the ps1 the WRONG way (`powershell -File $env:TEMP\dz-path.ps1`) in a fresh stripped PS -> `dz` is still NOT found (child scope) -- this is why the instruction prints the dot-source form.
- [ ] **Machine channel:** `dz setup dz --emit-shell-fix` prints EXACTLY one line on stdout (pipe to a file to verify nothing else lands there).

### 1.6 venv installs get activation guidance, never a PATH offer

- [ ] **Steps** (PowerShell): `python -m venv $env:TEMP\dzvenvtest; & $env:TEMP\dzvenvtest\Scripts\pip install dazzlecmd; & $env:TEMP\dzvenvtest\Scripts\python -m dazzlecmd setup dazzlecmd` (do NOT activate first).
- [ ] **Expected:** diagnosis shows `install: venv scheme`; output says to ACTIVATE the venv (with the activate path) and exits 1; NO `Append this directory to your user PATH?` prompt appears; registry untouched. Cleanup: `Remove-Item -Recurse -Force $env:TEMP\dzvenvtest`.

## Section 2: Self-name spellings and shadowing (~5 min)

### 2.1 All self-spellings route identically

- [ ] **Steps:** `dz setup dz`, `dz setup dazzlecmd`, `python -m dazzlecmd setup dazzlecmd` -- all three.
- [ ] **Expected:** identical diagnosis block from each.

### 2.2 A tool named like the aggregator is surfaced, self-setup still wins

- [ ] **Steps:** temporarily add a trivial tool named `dz` (or `dazzlecmd`) to a kit (a one-line `.dazzlecmd.json` in a scratch kit dir), then run `dz setup dz`.
- [ ] **Expected:** stderr carries `note: 'dz' is also a tool (<fqcn>) -- running the aggregator's self-setup; use 'dz setup <fqcn>' for the tool.`; the self-diagnosis still runs; `dz setup <fqcn>` reaches the tool's setup. Remove the scratch tool afterward.

### 2.3 Shadow copies are surfaced

- [ ] **Steps:** on a box with more than one Python that has dazzlecmd installed (or after `pip install dazzlecmd` into a second interpreter), run `dz setup dz`.
- [ ] **Expected:** `[!] another copy on PATH: <path>` line(s) naming the other launcher(s).

## Section 3: Help and discoverability (~3 min)

### 3.1 Help text mentions the self-target

- [ ] **Steps:** `dz setup -h` and `dz -h`.
- [ ] **Expected:** setup help names the aggregator-self usage and the `--yes` / `--dry-run` flags with target-generic wording (`--dry-run` shows the resolved command for a tool / the would-be PATH change for self; `--yes` skips prompts wherever they occur); columns aligned in both cmd.exe and Windows Terminal.
- [ ] **Also:** `dz setup find --dry-run` prints the resolved invocation + working dir and runs NOTHING (the verb's preview).
- [ ] **Forwarding (the v0.7.46 promise, wired via #104):** `dz setup find -- --dry-run` FORWARDS `--dry-run` into `dz_setup.py` -- the script runs in its own dry-run mode (prints installer plan, installs nothing) and the invocation line shows the appended arg. Verify an arg with spaces survives quoting on the `setup.command` path of any command-form tool: it must arrive as ONE argument.
- [ ] **Self-target reserved tail:** `dz setup dz -- anything` warns that trailing args are reserved and proceeds normally.

### 3.2 README recovery section is followable cold

- [ ] **Steps:** hand the README "dz not found after install?" section to someone (or role-play it) on a broken box; do ONLY what it says.
- [ ] **Expected:** they reach a working `dz` without touching this checklist. Note any wording that confused them.

## Section 4: POSIX behavior (~5 min, Linux or macOS)

### 4.1 Advice, not action

- [ ] **Steps** (a user-scheme or otherwise off-PATH install; `bash`):
  ```bash
  python3 -m dazzlecmd setup dazzlecmd
  ```
- [ ] **Expected:** diagnosis; then the exact `export PATH="...:$PATH"` line and the right rc file for `$SHELL` (`~/.bashrc` for bash, `~/.zshrc` for zsh, `fish_add_path` for fish); exit 1; NO file was edited (`ls -l ~/.bashrc` mtime unchanged).

### 4.2 Healthy POSIX box is quiet

- [ ] **Steps:** on a healthy install: `python3 -m dazzlecmd list` and `dz setup dz`.
- [ ] **Expected:** no hint line; "Everything is in order."; exit 0.

## What the automated tests DON'T cover

- The REAL `HKCU\Environment` write on a live registry (seams are mocked) -- value kind, ACLs, interaction with other software watching PATH
- `WM_SETTINGCHANGE` actually reaching Explorer so genuinely fresh shells inherit the new PATH (HV.3 is the only proof)
- TTY detection + prompt rendering in real cmd.exe / PowerShell / Windows Terminal (codepage 437/1252 -- output is ASCII-only by design; verify no garbage)
- pip's real user-scheme fallback on an all-users Python (the inducing scenario itself)
- Interaction with `setx`-mangled or >2048-char PATHs already on the box
- The stderr hint's visibility/ordering when the main command also writes output
- README instructions actually working for a cold reader (3.2)
- Performance feel: the first-run hint check must be imperceptible on every `python -m dazzlecmd` run

## Reporting issues found

1. Note the section and step number.
2. Capture the exact command, full output, and `reg query HKCU\Environment /v Path` before/after.
3. Preserve the `%USERPROFILE%\.dazzlecmd\path-backup-*.txt` files.
4. File a GitHub issue referencing this checklist and #103.

## Cleanup

- [ ] Restore your original user PATH if any induced-broken state remains: raw value is in `%TEMP%\path-before-checklist.txt` (step 3 of Prerequisites) and in `%USERPROFILE%\.dazzlecmd\path-backup-<earliest-ts>.txt`; write it back with `reg add HKCU\Environment /v Path /t REG_EXPAND_SZ /d "<raw>" /f` and open a fresh terminal.
- [ ] Delete checklist scratch files: `%TEMP%\path-before-checklist.txt`.
- [ ] Optionally prune `%USERPROFILE%\.dazzlecmd\path-backup-*.txt` files created during the run (keep at least the earliest).
