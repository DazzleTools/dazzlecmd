**Target version:** v0.7.45
**Ships with commit:** TBD
**Companion automated tests:** `tests/test_cmd_new_tool_languages.py::TestLanguageBash` (3) + `TestLanguageCmd` (3) + `TestLanguageBinary` (2) + updated `TestAvailableLanguagesError` (1). Total suite: 1104 passed, 14 skipped.

## What this is

v0.7.44 (Tier 2A.2) shipped per-language scaffolding for seven languages (python, rust, node, powershell, c_cpp, docker, generic). User feedback after v0.7.44 surfaced two gaps:

1. bash and cmd scripts are common scaffolding targets. #35's acceptance criteria listed "shell" as a supported language; v0.7.44 only covered the shell case via PowerShell.
2. `binary` was explicitly listed in #35's acceptance criteria but v0.7.44 conflated it with `generic` (which is broader -- the generic README mentions runtime could end up shell, node, docker, etc.).

v0.7.45 fills both gaps with three additive template directories: `bash`, `cmd`, `binary`. No engine change; the shell runner and binary runner already support these via existing fields. Pure template-creation work.

The v0.7.44 checklist (`v0.7.44__Tier2A__multi-language-templates.md`) covers the underlying template-dispatch mechanism. This checklist focuses on the bash/cmd specifics.

### HV.1 -- Automated tests green

- [ ] **Steps**: `python -m pytest tests/test_cmd_new_tool_languages.py::TestLanguageBash tests/test_cmd_new_tool_languages.py::TestLanguageCmd -v`
- [ ] **Expected**: `6 passed`.

### HV.2 -- bash scaffold produces a valid POSIX shell script

- [ ] **Steps**: `dz new tool --language bash bashtest`
- [ ] **Expected output**:
  ```
  Created project: dazzletools/bashtest
    <tool_dir>/
    - .dazzlecmd.json
    - bashtest.sh
  ```
- [ ] **Check `bashtest.sh`**:
  - Line 1: `#!/usr/bin/env bash`
  - Contains `set -euo pipefail`
  - Contains `Arguments: $*` reference
- [ ] **Check `.dazzlecmd.json`**:
  - `language: "bash"`
  - `runtime.type: "shell"`, `runtime.shell: "bash"`
  - `platforms: ["linux", "macos"]` (NOT `"windows"`)
- [ ] **Why this matters**: bash is POSIX-only at the platform metadata level. Windows users can still run it via WSL/Git Bash but the manifest reflects the native-target convention.

### HV.3 -- cmd scaffold produces a valid Windows batch file

- [ ] **Steps**: `dz new tool --language cmd cmdtest`
- [ ] **Expected output**:
  ```
  Created project: dazzletools/cmdtest
    <tool_dir>/
    - .dazzlecmd.json
    - cmdtest.cmd
  ```
- [ ] **Check `cmdtest.cmd`**:
  - Line 1: `@echo off`
  - Contains `setlocal` and `endlocal`
  - Contains `%*` for argument passthrough
  - Ends with `exit /b 0`
- [ ] **Check `.dazzlecmd.json`**:
  - `language: "cmd"`
  - `runtime.type: "shell"`, `runtime.shell: "cmd"`
  - `platforms: ["windows"]` (cmd.exe is Windows-only)

### HV.4 -- binary scaffold produces a manifest-only setup

- [ ] **Steps**: `dz new tool --language binary bintest`
- [ ] **Expected output**:
  ```
  Created project: dazzletools/bintest
    <tool_dir>/
    - .dazzlecmd.json
    - README.md
  ```
  No source file (no `.py`, `.sh`, `.cmd`, `Cargo.toml`, etc.).
- [ ] **Check `.dazzlecmd.json`**:
  - `language: "binary"`
  - `runtime.type: "binary"`, `binary_path: "bintest"` (drop-in default)
  - `platforms: ["windows", "linux", "macos"]` (cross-platform)
  - `build_hint` mentions both drop-in (`bintest` / `bintest.exe`) and PATH-lookup patterns
- [ ] **Check `README.md`**: explains drop-in vs PATH-lookup vs absolute-path scenarios and when to pick `binary` over `generic`.

### HV.5 -- Unknown-language error now lists all ten

- [ ] **Steps**: `dz new tool --language fortran foo`
- [ ] **Expected** stderr: `Error: language 'fortran' not supported (from --language flag).` plus `Available: bash, binary, c_cpp, cmd, docker, generic, node, powershell, python, rust.` (sorted alphabetically)
- [ ] **Why this matters**: confirms the validation set is derived from the directory layout, not a hardcoded list. The three new directories (bash, cmd, binary) are picked up automatically.
