# Human Test Checklist: `dz github <repo>#<issue>` cross-repo issue references

**Target version:** v0.12.18-alpha
**Ships with commit:** `feat(github): cross-repo issue references -- <repo>#<N>` (TBD at writing)
**Companion automated tests:** 70 tests in `src/dazzlecmd/projects/dazzletools/github/tests/test_github_resolution.py` (33 new: parse table, resolver isolation, dispatch, two real-CLI subprocess tests, and 7 mutation-audit anchors -- see `tests/mutation/v0.12.18__sweep__github-issue-refs.md` for the sweep that motivated them)

## What this is

`dz github dazzlecmd#112` opens issue 112 of another project from wherever you are standing. The repo part is a bare name resolved through your orgs' cache (or `OWNER/REPO` verbatim); the part after `#` takes the whole issue grammar. This checklist covers what the mocks cannot: real browser launch, the ambiguity prompt with your real cache, shell-comment behavior across shells, and whether the miss message reads well.

Run time: ~5 minutes.

## High-Value Verification

### HV.1 -- The headline: another repo's issue, from anywhere

- [ ] From any directory (repo or not): `dz github dazzlecmd#112`
- [ ] **Expected:** browser opens `https://github.com/DazzleTools/dazzlecmd/issues/112`; terminal shows `  DazzleTools/dazzlecmd` on stderr.
- [ ] **Must NOT happen:** a repo search, a prompt, or any cwd dependence.

### HV.2 -- `OWNER/REPO#N` verbatim

- [ ] `dz github -n DazzleLib/dazzle-lib#3`
- [ ] **Expected:** `.../DazzleLib/dazzle-lib/issues/3` -- instant, no cache activity, no announcement (you named it fully).

### HV.3 -- Bare `#N` is the current project, shell caveat and all

- [ ] Inside a project: `dz github -n "#112"` (quoted). In **cmd.exe** also try it unquoted.
- [ ] **Expected:** current project's issue 112. From inside `private/`, the parent project's -- with the `Resolved via parent repo:` line.
- [ ] **Also verify the failure shape:** in bash/PowerShell, unquoted `dz github #112` silently degrades to `dz github` (the shell ate the argument) and opens the repo home. Confirm that is what happens -- mildly wrong, not destructive -- and that the quoted form is the habit to build.

### HV.4 -- Semantic keyword in the other repo

- [ ] `dz github -n dazzlecmd#roadmap`
- [ ] **Expected:** resolves the repo, then label-then-title lookup **in dazzlecmd**, printing the matched issue title -- regardless of what repo you are standing in.

### HV.5 -- The miss is honest

- [ ] `dz github -n zzznope#5`
- [ ] **Expected:** exit 1; `No repo matching 'zzznope' in your orgs.` and the `OWNER/REPO#5` tip. **No global-GitHub search, no candidate list of strangers' repos.**

### HV.6 -- Ambiguity prompt (judgment call)

- [ ] Pick a prefix matching several of your repos **with no exact hit**. (Verify first with `dz github -n repo <prefix>` -- an exact-name match auto-selects and skips the prompt. On the 2026-08-10 tester run, `dazzle#1` auto-selected because the live cache had gained an exact `dazzle` repo; `dazzle-clau#1` exercised the prompt.)
- [ ] **Expected:** the familiar numbered prompt, listing candidates; your choice opens **that repo's issue 1**. The prompt names the repo part (`dazzle`), not the whole `dazzle#1` string.
- [ ] **Judgment:** does prompting feel right mid-issue-jump, or would you rather it fail fast like HV.5? (Ledger has a config-alias alternative if prompts grow annoying.)

## Non-regression spot-checks

- [ ] `dz github 112` (no `#`) -- unchanged
- [ ] `dz github roadmap` inside a project -- still an issue keyword, no change
- [ ] `dz github repo <ambiguous-prefix>` -- still prompts with global fallback intact (pick a prefix with no exact-name match in your cache; see HV.6's note)
- [ ] `dz github pr` / `release` / `.` -- unchanged

## What the automated tests DON'T cover

- Real browser launch (every test uses `-n`)
- The ambiguity prompt against your real 100+-repo cache (fixtures use 3)
- Shell-comment swallowing of unquoted `#112` (GT-verified once; worth seeing in your own shells)
- Cache staleness mid-jump: if the cache is >24h old, the first `proj#N` prints `Updating repo cache...` and takes ~5s -- confirm that reads as expected, not as a hang
- Whether the miss/tip wording reads well
