# Human Test Checklist: `--with` components + RepoKit integration (4d-5 + 4d-6)

**Target version:** v0.9.29 (dazzlecmd) / 0.8.29 (dazzlecmd-lib)
**Ships with commits:** `d611039` (v0.9.28 framework) + `1b9bf12` (v0.9.29 common/template)
**Companion automated tests:** `tests/test_cli_new_scaffold.py::TestWithComponents` + `::TestRepoKitComponents` (7 of the 16 scaffold tests): parse/expand/dedup/pre-write-failure, docker/ci file sets + substitution, local-remote subtree round-trip, local-path template + no-clobber, offline `all` fallback.

## What this is

`dz new aggregator <name> --with <C1,C2|all>` layers opt-in components onto a scaffold: `docker-test`, `docker-deploy`, `ci` (template copies), `common` (the git-repokit-common subtree at `scripts/`, with git init on fresh scaffolds), `template` (project-shape files: local path → shallow clone → bundled fallback). Composition is best-effort with an end summary. This checklist covers what the hermetic tests can't: **real network** fetches of the actual RepoKit repos, the **ancestor-repo safety guard** behavior in real layouts, and generated-file quality (do the Dockerfiles/workflows actually build/run?).

**SAFETY:** run all scaffolds in throwaway %TEMP% dirs. The `common` component RUNS GIT (init + commit + subtree) in the TARGET dir only — verify you're in a sandbox before invoking. Cleanup via `dz safedel --yes`.

## High-Value Verification (~8 minutes; needs network for HV.2/HV.3)

### HV.1 — Framework basics (offline)
- [ ] **Steps** (PowerShell, in `$env:TEMP\wt1`): `dz new aggregator W --with docker-test,ci` then `dz new aggregator X --with nope`
- [ ] **Expected:** W gets `Dockerfile.test`, `docker-compose.test.yml`, `.github/workflows/{test,release}.yml` with `{name}` substituted and GitHub `${{ }}` untouched; the `nope` run fails clean with the valid-components list and creates NOTHING.

### HV.2 — `--with common` against the REAL repo (network)
- [ ] **Steps:** `dz new aggregator WC --with common` (sandbox!)
- [ ] **Expected:** "[with:common] initialized git repository" note → real subtree fetch → `WC/scripts/` contains the actual repokit-common content (`install-hooks`, `sync-versions.py`, `gh_issue_full.py`...); `git -C WC log --oneline` shows the squashed subtree commit; the install-hooks hint prints.
- [ ] **Why:** the hermetic test uses a local fake remote; this is the only check of the real URL + network path.

### HV.3 — `--with template` against the REAL repo (network)
- [ ] **Steps:** `dz new aggregator WT --with template`
- [ ] **Expected:** "source: https://github.com/DazzleTools/git-repokit-template.git"; LICENSE/CONTRIBUTING (etc.) appear; the scaffold's own README.md is NOT overwritten.
- [ ] **Also:** disconnect network (or use a bogus `new.repokit_template_url` in an isolated config) → the bundled **FALLBACK-MINIMAL** stubs land with the warning.

### HV.4 — The ancestor-repo safety guard (the v0.9.29 bug class)
- [ ] **Steps:** scaffold INSIDE any directory that lives under an existing git repo (e.g. a subdir of your home, which is itself a repo): `dz new aggregator WG --with common`
- [ ] **Expected:** the applier does NOT touch the enclosing repo — it prints "[with:common] initialized git repository" (a fresh repo at WG), and `git -C WG rev-parse --show-toplevel` == the WG path. The ancestor repo's `git status` is unchanged.
- [ ] **Why:** pre-fix, ambient discovery would have subtree'd RepoKit into the ANCESTOR repository.

### HV.5 — Do the generated artifacts actually work?
- [ ] **Steps** (needs Docker): in W from HV.1 — `docker build -f Dockerfile.test -t w-test .` (after `pip`-installable state, i.e. with the scaffold's pyproject) — or at minimum eyeball the Dockerfile/workflow YAML for correctness.
- [ ] **Expected:** builds, runs the generated smoke test. The CI workflow YAML parses (push it to a scratch repo or run `actionlint` if available).

### HV.6 — Config defaults
- [ ] **Steps:** isolated `DAZZLECMD_CONFIG` with `{"new": {"repokit_template_path": "<a local dir with a LICENSE.tmpl>"}}` → `dz new aggregator WL --with template`
- [ ] **Expected:** "source: local path ..." — the local dir wins over the URL; substitution applied.

## What the automated tests DON'T cover
- Real-network subtree/clone of the actual DazzleTools repos (HV.2/3).
- Docker build / Actions-YAML validity of the generated files (HV.5).
- The guard under YOUR real directory layout (HV.4 — the tests simulate it with a fixture ancestor).
- `--with` on `dz new tool` (not wired — aggregator-only this slice; flag absent there by design).

## Cleanup
`dz safedel $env:TEMP\wt1 --yes` (and any WG sandbox). Nothing outside %TEMP% is touched when run as written.
