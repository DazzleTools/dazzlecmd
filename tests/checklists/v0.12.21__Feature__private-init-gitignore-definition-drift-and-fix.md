# Human Test Checklist: `dz private-init` — one gitignore definition, drift reporting, and `--fix`

**Target version:** v0.12.21 (unreleased; the repo is at `0.12.20-alpha`)
**Ships with commit:** TBD — pre-commit
**Companion automated tests:** 53 tests in `tests/test_private_init_gitignore_definition.py`, all red-green audited as anchors. Full suite: 2560 passed, 23 skipped.

## What this is

A vault created before a tool existed cannot learn about that tool on its own. `dz private-init` has always known what a correct `private/` vault should ignore — but it only ever used that knowledge once, when creating a new one. This change makes the same declaration serve three jobs: writing a new vault, judging an existing one, and repairing it.

This checklist covers what the automated tests cannot: whether the drift report is *actually actionable* when you read it, how it renders on a Windows console, and — most importantly — whether `--fix` is safe to point at a real vault that has years of your own rules in it.

Run the High-Value section if you have five minutes. Run Section 3 before you trust `--fix` on anything you care about.

## Prerequisites

1. **A working `dz`** — or run the module directly, which is what these steps do so the checklist works from a checkout without installation:
   `python src/dazzlecmd/projects/dazzletools/private-init/private_init.py`
2. **Git on PATH.**
3. **A throwaway directory** for every destructive step. Nothing here should touch a real vault until Section 4, which is opt-in and explicitly append-only.
4. **Scratch-git rules** — whenever a step builds a git fixture:
   - every git command carries `-C <scratch path>` so it can never land in a real repo;
   - every commit or tag carries `-c user.email=test@example.invalid -c user.name=Test -c commit.gpgsign=false -c tag.gpgsign=false`. On a machine with `commit.gpgsign = true` globally, a bare `git commit` opens an interactive GPG pinentry dialog per commit, which blocks the run and asks whoever is at the keyboard to sign something they did not initiate. **Never change global git config to work around this** — per-invocation `-c` only.

**Reset between sections:** delete the scratch directory and recreate it. No configuration is written outside it.

**Set the scratch path once** (used throughout):

**cmd.exe**
```cmd
set SCRATCH=%TEMP%\pi-check
set DZPI=python src\dazzlecmd\projects\dazzletools\private-init\private_init.py
if exist "%SCRATCH%" rd /s /q "%SCRATCH%"
mkdir "%SCRATCH%\proj\private"
```

**PowerShell**
```powershell
$env:SCRATCH = "$env:TEMP\pi-check"
$DZPI = "src/dazzlecmd/projects/dazzletools/private-init/private_init.py"
if (Test-Path $env:SCRATCH) { Remove-Item -Recurse -Force $env:SCRATCH }
New-Item -ItemType Directory -Force "$env:SCRATCH\proj\private" | Out-Null
```

**POSIX**
```bash
export SCRATCH=/tmp/pi-check
DZPI=src/dazzlecmd/projects/dazzletools/private-init/private_init.py
rm -rf "$SCRATCH"; mkdir -p "$SCRATCH/proj/private"
```

**Build the "old vault" fixture** — a vault carrying the 18-line template verbatim, which is what several real vaults still have:

**POSIX** (cmd.exe / PowerShell: use your editor, or the Python one-liner below)
```bash
printf '# Python\n__pycache__/\n*.py[cod]\n*.so\n\n# Editors\n*.swp\n*~\n*.*~\n.*.swp\n\n# OS\n.DS_Store\nThumbs.db\ndesktop.ini\n\n# Temp files\n*.tmp\n*.bak\n' > "$SCRATCH/proj/private/.gitignore"
git -C "$SCRATCH/proj" init -q
```

**Cross-shell (works everywhere Python does):**
```
python -c "import os,io; p=os.path.join(os.environ['SCRATCH'],'proj','private','.gitignore'); open(p,'w').write('# Python\n__pycache__/\n*.py[cod]\n*.so\n\n# Editors\n*.swp\n*~\n*.*~\n.*.swp\n\n# OS\n.DS_Store\nThumbs.db\ndesktop.ini\n\n# Temp files\n*.tmp\n*.bak\n')"
```
then
```
git -C <SCRATCH>/proj init -q
```

## High-Value Verification (~5 minutes)

### HV.1 — The drift report names what is missing, and it reads as actionable

Validates: `cmd_status` compares both files against the definition and tells you something you can act on.

- [ ] **Steps:** with the old-vault fixture in place, run
  ```
  python <DZPI> --status <SCRATCH>/proj
  ```
- [ ] **Expected:** among the existing status output, two new blocks — `Vault ignores:` reporting **2 pattern(s) missing** and naming `.vscode/` and `.gauntlet/`, and `Project ignores:` reporting **1 pattern(s) missing** and naming `CLAUDE.local.md`. Each block ends with a line telling you how to fix it.
- [ ] **Read it as a stranger would.** Does the report say *which file*? Does it say *what to do*? If you had ten vaults, would this output tell you which ones need attention?
- [ ] **Why this matters:** a drift report nobody can act on is not a report. This is the entire user-facing value of the change.

### HV.2 — `--dry-run` changes nothing

Validates: the preview is genuinely a preview.

- [ ] **Steps:**
  ```
  git -C <SCRATCH>/proj status --short
  python <DZPI> --fix --dry-run <SCRATCH>/proj
  git -C <SCRATCH>/proj status --short
  ```
- [ ] **Expected:** the report says **would add**, and the two `git status` outputs are identical.
- [ ] **Why this matters:** this is the command a cautious person runs first on a vault they care about. If it writes, nobody will trust `--fix` again.

### HV.3 — `--fix` repairs the vault and the project

- [ ] **Steps:**
  ```
  python <DZPI> --fix <SCRATCH>/proj
  python <DZPI> --status <SCRATCH>/proj
  ```
- [ ] **Expected:** the fix reports **added** for both files; the follow-up status reports **up to date with the current definition [OK]** for both.
- [ ] **Why this matters:** report-then-repair is the whole loop. If status and fix disagree about what is missing, neither can be trusted.

### HV.4 — Running `--fix` twice does nothing the second time

- [ ] **Steps:** run `python <DZPI> --fix <SCRATCH>/proj` again, then inspect the file.
- [ ] **Expected:** `nothing to fix [OK]` for both files, and the `.gitignore` is byte-identical to before the second run.
- [ ] **Why this matters:** a repair meant for a fleet of checkouts has to converge. If it appends every time, running it twice corrupts what it was meant to fix.

### HV.5 — Your own rules survive, in order

Validates the single most dangerous property: `--fix` writes to a file you did not write.

- [ ] **Steps:** reset the fixture, then append your own rules *including a negation* before fixing:
  ```
  python -c "import os; p=os.path.join(os.environ['SCRATCH'],'proj','private','.gitignore'); f=open(p,'a'); f.write('\n# my own rules\nsecrets/\n!secrets/README.md\n')"
  python <DZPI> --fix <SCRATCH>/proj
  ```
  then view the file (`type` / `Get-Content` / `cat`).
- [ ] **Expected:** `# my own rules`, `secrets/` and `!secrets/README.md` are all present, unchanged, **and `!secrets/README.md` still comes after `secrets/`**. The new patterns are appended at the end.
- [ ] **Why this matters:** a `!` re-inclusion only works if it follows the rule it re-includes. A repair that reorders lines silently changes what a repository ignores.

### HV.6 — Windows console rendering

- [ ] **Steps:** run `python <DZPI> --status <SCRATCH>/proj` in **cmd.exe** and again in **PowerShell**.
- [ ] **Expected:** `[OK]` renders as literal ASCII in both; no mojibake, no `UnicodeEncodeError`; long Windows paths wrap without mangling the pattern list beneath them.
- [ ] **Why this matters:** this is a Windows-first project, and the console defaults to a codepage that does not do UTF-8.

## Section 1: The report (~5 min)

### 1.1 A current vault reports no drift

- [ ] **Steps:** reset, then create a vault whose `.gitignore` is what `private-init` would write today — the simplest way is to let it: `python <DZPI> <SCRATCH>/fresh` and then `--status` it.
- [ ] **Expected:** both blocks say **up to date with the current definition [OK]**, and no fix hint is printed.
- [ ] **Check:** the fix hint appears *only* when something is missing. An "[OK]" line followed by "To fix..." is a bug.

### 1.2 Drift is reported in declaration order, not alphabetically

- [ ] **Expected:** in HV.1, `.vscode/` is listed **before** `.gauntlet/` — the order they are declared in, not sorted.
- [ ] **Why:** the report should read like the definition, so a maintainer comparing the two can scan them together.

### 1.3 A project with no `.gitignore` at all

- [ ] **Steps:** reset; delete `<SCRATCH>/proj/.gitignore` if present; `--status`.
- [ ] **Expected:** `Project ignores:` reports `CLAUDE.local.md` as missing rather than claiming the project is fine. A file that does not exist has drifted from everything.

### 1.4 No parent git repo

- [ ] **Steps:** build a vault in a directory that is **not** inside any git repository, then `--fix` it.
- [ ] **Expected:** the vault half is handled; the project half prints `no parent git repo found -- skipped`. No traceback.

## Section 2: The definition (~3 min)

### 2.1 A newly created vault ignores what our tools write

- [ ] **Steps:**
  ```
  python <DZPI> <SCRATCH>/fresh
  ```
  then, inside `<SCRATCH>/fresh/private`, ask git directly:
  ```
  git -C <SCRATCH>/fresh/private check-ignore -v .gauntlet/x/run-log.md
  git -C <SCRATCH>/fresh/private check-ignore -v .vscode/settings.json
  ```
- [ ] **Expected:** both report a matching rule. Ask *git*, not your eyes — a pattern that is present but overridden by a later rule looks fine in a text editor and is broken in practice.

### 2.2 The rendered file is readable

- [ ] **Steps:** view the generated `.gitignore`.
- [ ] **Expected:** section comments (`# Python`, `# Editors`, `# OS`, `# Temp files`, `# Agent working state ...`), a blank line between sections, and no duplicate or empty sections.
- [ ] **Judge it:** would you be happy finding this file in your own repository? Is the "Agent working state" comment clear about *why* those entries exist?

## Section 3: `--fix` safety (~10 min) — run this before trusting it on anything real

### 3.1 A file with no trailing newline is not corrupted

- [ ] **Steps:** write a `.gitignore` whose last line has **no newline** (`python -c "open(...,'w').write('secrets/')"`), then `--fix`.
- [ ] **Expected:** `secrets/` is still its own line. The new content starts on a fresh line beneath it.
- [ ] **Why:** naive appending glues the first new line onto the last existing one, silently changing both.

### 3.2 The result ends with a newline

- [ ] **Check:** after any `--fix`, the file's final byte is a newline, so whatever appends next (another tool, another run) starts cleanly.

### 3.3 Only the sections that were missing something are appended

- [ ] **Check:** after fixing the old-vault fixture, the appended text contains `# Editors` and `# Agent working state ...` and **not** `# Python`, `# OS` or `# Temp files`.
- [ ] **Why:** a repair that appends a bare heading for every satisfied section adds noise to every file it touches, and it compounds across a fleet.

### 3.4 A missing file and its parent directory are created

- [ ] **Steps:** point `--fix` at a project whose `.gitignore` does not exist.
- [ ] **Expected:** the file is created containing the parent definition, and a following `--status` reports it up to date.

### 3.5 `--status` on a `private/` that is not a git repo

- [ ] **Steps:** create `<SCRATCH>/plain/private` with a file in it, no `git init`, then `--status`.
- [ ] **Expected:** the existing behaviour is preserved — it reports the directory is not a git repo and suggests `--adopt`. It must not crash on the new drift check, and it should not report drift for a vault it has just told you is not a vault.

### 3.5b Running from *inside* a vault says so

- [ ] **Steps:** `cd` into a project's `private/` directory and run `dz private-init --fix --dry-run` (no path argument).
- [ ] **Expected:** it reports that `private/` does not exist at `<vault>/private` -- **and then** says you appear to be inside a vault already, names the vault and its parent, and prints the exact command for the parent, carrying the same flags you used (`--fix --dry-run`, not a generic verb).
- [ ] **Check the negative:** run the same command in an ordinary directory with no `private/`. The vault hint must **not** appear -- it is for one specific mistake, and a hint that fires everywhere is noise.
- [ ] **Why this matters:** every tool in this family resolves `private/` relative to where it was told to look, so standing in a vault asks about a vault nested in a vault, which never exists. Git works from any subdirectory; this at least explains itself.

### 3.6 A directory named `.gitignore`

- [ ] **Steps:** create a *directory* called `.gitignore` inside the vault, then `--status`.
- [ ] **Expected:** reported as absent (everything drifted), no traceback. Pathological, but a status command that crashes is worse than one that shrugs.

## Section 4: Against a real vault (opt-in, ~5 min)

**Only if you want to.** `--fix` is append-only and never rewrites existing lines, and `git diff` will show you exactly what it added — but this is your own data, so decide deliberately.

### 4.1 Dry-run first, on a vault you care about

- [ ] **Steps:** `python <DZPI> --fix --dry-run <path to a real project>`
- [ ] **Expected:** a list of what *would* be added. Read it. Is any of it wrong for that project?

### 4.2 Apply, then read the diff

- [ ] **Steps:** run without `--dry-run`, then `git -C <the vault> diff -- .gitignore` and `git -C <the project> diff -- .gitignore`.
- [ ] **Expected:** the diff is **pure addition** — no `-` lines except the absence of a trailing-newline marker. If you see a removed line, stop and report it.
- [ ] **Check afterwards:** `git -C <the vault> status --short` no longer lists whatever the new patterns cover.

## What the automated tests DON'T cover

- **Whether the report is useful.** The tests assert that patterns appear in the output; only a person can say whether reading it tells you what to do.
- **Windows console rendering** — codepage, `[OK]` markers, long-path wrapping.
- **Real vaults.** Every automated test builds its fixture in a temp directory. A vault with a decade of accumulated rules, a nested `.gitignore`, or a `!` chain is a different animal.
- **`dz` dispatch.** The tests load the module by path; they do not exercise `dz private-init` through the CLI kit dispatcher.
- **Interaction with `--adopt`** on a vault that is mid-conversion.
- **Whether `.gauntlet/` and `.vscode/` are the *right* entries** — that is a judgment about what tools write, not something a test can settle.

## Reporting issues found

1. Note the section and step number.
2. Capture the exact command and its full output.
3. Save the `.gitignore` before and after, if the step wrote one.
4. File an issue referencing this checklist by filename and the version above.
