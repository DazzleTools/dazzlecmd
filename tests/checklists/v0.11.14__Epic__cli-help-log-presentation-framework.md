## What this is

This document is the human-run companion to the automated tests for the **three-pillar CLI-presentation framework**: `cli_lib` (CLI structure / the `-h` layout), `help_lib` (contextual tips + a detail Continuum), and `log_lib` (output channels + verbosity as a Continuum). The headline change is that `dz kit -h`'s whole body is now generated from a declarative `Section` list (a "higher-level argparse epilog") instead of hand-coded — and **the byte-gate does not cover `dz kit -h`**, so a human must eyeball the live rendering for alignment, codepage, and CRLF correctness. Run it before committing the chunk.

## Prerequisites

1. **Environment:** Windows (primary), with the editable install active so the working tree is what runs (`pip show dazzlecmd` → location is the repo). `dz` and `python -m dazzlecmd` are equivalent entry points.
2. **No config writes** are needed for the `-h` / rendering / API sections — they are read-only. The kit enable/disable regression spot-check (Section 2) uses a throwaway `DAZZLECMD_CONFIG` so your real dotfiles are never touched.
3. **Deterministic test order:** always pass `-p no:randomly` to pytest (there is a pre-existing `pytest-randomly` order-flake in `TestKitDetach`, unrelated to this work).
4. **Reset between sections:** the only stateful section is the kit enable/disable spot-check; it deletes its own temp config at the end (Cleanup).

## High-Value Verification (~5 minutes)

If you only have five minutes, run these. They are the "did the framework actually ship" smoke tests.

### HV.1 — `dz kit -h` renders all five sections, correctly laid out

Validates: the `render_sections`-driven `-h` body (the core D-2 change).

- [ ] **Steps** (cross-shell safe — `dz` only):
  ```
  dz kit -h
  ```
- [ ] **Expected:** five sections in this order, column-aligned at col 17:
  - `  inspect:` (flat — `list / info / focus / reset`)
  - `  management:    \`dz kit management [<kit>]\` ...` (NESTED — `membership` / `loading` / `activation`, each an axis row with two verb rows indented under it, a blank line between axes)
  - `  visibility:    a tool's presence axis ...` (flat — `status / silence / unsilence / hide / unhide / shadow / unshadow`)
  - `  favorite:      favorite <-> unfavorite  a saved shortcut name` (flat — `favorite / unfavorite`)
  - `options:` (header at column 0, the `-h, --help` row at column 2)
- [ ] **Why this matters:** this is the whole point of D-2 — if the generated body is wrong, the headline feature is broken, and the byte-gate would NOT catch it.

### HV.2 — `dz kit -h` is byte-identical to the pre-refactor baseline

Validates: the refactor changed structure, not output (the prime directive).

- [ ] **Steps:**

  **PowerShell:**
  ```powershell
  dz kit -h | Out-File -Encoding utf8 "$env:TEMP\kit_h_now.txt"
  # compare against the committed reference if present, else eyeball against HV.1
  ```

  **POSIX:**
  ```bash
  dz kit -h > /tmp/kit_h_now.txt
  ```
- [ ] **Expected:** no structural difference from HV.1's expected layout. (Maintainers: the design doc records a saved `kit_h_baseline.txt` proven identical 3×.)
- [ ] **Why this matters:** a "pure refactor" that silently drifts the help text is exactly the regression class this checklist exists to catch.

### HV.3 — the two templates are the {grouped, ungrouped} projections

Validates: `management:` exposes its axis as a runnable sub-command; `visibility:` does not.

- [ ] **Steps** (cross-shell safe):
  ```
  dz kit membership -h
  dz kit loading -h
  ```
- [ ] **Expected:** each prints `usage: dz kit <axis> [-h] {warm,cold,on,off} ...` — e.g. `dz kit membership -h` → `{add,remove,on,off}` with `on` glossed `add (universal on-pole synonym)` and `off` → `remove (...)`. `dz kit loading -h` → `{attach,detach,on,off}`.
- [ ] **Why this matters:** the axis-exposed template is only meaningful if the axis is genuinely a sub-command namespace (FQCN: `dz kit membership add`), not just a help heading.

### HV.4 — hoisted special verbs still dispatch (no grammar regression)

Validates: `dz kit <verb>` flat forms and `dz kit <axis> <verb>` resolve to the same handler.

- [ ] **Steps** (cross-shell safe):
  ```
  dz kit attach -h
  dz kit loading attach -h
  ```
- [ ] **Expected:** both print the SAME attach help (same usage + options); `dz kit attach` is the hoisted form of `dz kit loading attach`.
- [ ] **Why this matters:** the help rework touched `kit_verbs.py`; the grammar (verb hoisting) must be unaffected.

### HV.5 — full suite + byte-gate green

Validates: nothing regressed anywhere.

- [ ] **Steps:**
  ```
  python -m pytest tests/ packages/ -p no:randomly -q
  python tests/one-offs/run_byte_gate.py
  ```
- [ ] **Expected:** `1546 passed, 16 skipped`; byte-gate `10 OK, 0 FAIL` (the `dz_tree` line-1 version banner difference is expected/allowed).
- [ ] **Why this matters:** the chunk touches a shared module (`kit_verbs`) imported across the CLI; the suite is the regression backstop.

### HV.6 — the `log_lib` verbosity Continuum gates correctly (API level)

Validates: the keystone — THAC0 verbosity as a `dazzle_lib.Continuum`.

- [ ] **Steps:**
  ```
  python -c "from dazzlecmd._vendor.log_lib.verbosity import shows, rank_of, VERBOSITY_CONTINUUM as V; print('default<=default', shows(0,0)); print('debug<=default', shows(V.rank('debug'), 0)); print('floor silent', shows(0, V.rank('nothing'))); print('named timing', rank_of('timing'))"
  ```
- [ ] **Expected:** `default<=default True`, `debug<=default False`, `floor silent False` (nothing emits at the silence floor), and a numeric rank for `timing`.
- [ ] **Why this matters:** the verbosity Continuum is the foundation D-3 will wire `-v`/`-q` onto; its gate semantics must be right before that.

## Section 1: `dz kit -h` rendering detail (~3 min)

### 1.1 management — the nested / axis-exposed template

- [ ] **Steps:** `dz kit -h`
- [ ] **Expected:** under `management:`, axes appear **coldest-first** (membership, loading, activation). Each axis line is `    <axis>   <warm><-><cold>  (<gloss>)`, e.g. `    membership   add<->remove  (registered vs deregistered + trashed)`. The two verb rows are indented two more spaces (`      add` / `      remove`). A **blank line separates each axis group** (including after the last, before `visibility:`).
- [ ] **Check:** the `<->` arrows are ASCII `<->` (not a Unicode arrow), and `--` dashes are two ASCII hyphens — no mojibake in cmd.exe (codepage 437) or PowerShell (1252).

### 1.2 visibility / inspect / favorite — the flat / brief template

- [ ] **Steps:** `dz kit -h`
- [ ] **Expected:** `inspect:`, `visibility:`, and `favorite:` list their verbs flat (no nested axis line). `inspect:`'s header has **no description**; `visibility:`'s and `favorite:`'s headers do. All verb descriptions align at column 17.

### 1.3 options + footer

- [ ] **Steps:** `dz kit -h`
- [ ] **Expected:** `options:` is at column 0 (not indented like the axis sections); `  -h, --help     show this help message and exit` at column 2; final line `Run 'dz kit <verb> --help' for a specific verb.`

### 1.4 terminal-width independence (the usage line)

- [ ] **Steps:** resize the terminal narrow/wide, rerun `dz kit -h`.
- [ ] **Expected:** the argparse `usage:` block may rewrap with width (that part is argparse's, not ours), but the section body below `Each presence axis ...` is width-independent and unchanged.

## Section 3: per-pillar API behavior (~4 min)

### 3.1 log_lib — channel-spec parsing (named AND int rungs)

- [ ] **Steps:**
  ```
  python -c "from dazzlecmd._vendor.log_lib.channels import parse_channel_spec; print(parse_channel_spec('timing:config')); print(parse_channel_spec('timing:2'))"
  ```
- [ ] **Expected:** both parse without error — `timing:config` resolves the **named** rung, `timing:2` the **integer** rung. (This is why `--show timing:config` will work once D-3 wires it.)

### 3.2 log_lib — per-channel override beats global; opt-in channels start cold

- [ ] **Steps:**
  ```
  python -c "from dazzlecmd._vendor.log_lib.channels import default_channel_overrides, OPT_IN_CHANNELS; o=default_channel_overrides(); print({c:o[c] for c in OPT_IN_CHANNELS})"
  ```
- [ ] **Expected:** each opt-in channel maps to a cold (negative) starting level — opt-in channels are silent until explicitly raised.

### 3.3 help_lib — the detail Continuum coordinate query

> NOTE on the API: `min_detail_rank(contexts)` takes an iterable of **context-name
> strings** (e.g. `{"full", "minimal"}`) and returns the coldest rank `int`.
> `items_for_rank(items, rank)` takes **objects exposing a `.contexts` iterable**
> (e.g. `help_lib.HelpContent`), not `(name, rank)` tuples.

- [ ] **Steps:**
  ```
  python -c "from dazzlecmd._vendor.help_lib.detail import items_for_rank, min_detail_rank; from dazzlecmd._vendor.help_lib.core import HelpContent; mk=lambda i,ctx: HelpContent(id=i, command='c', description='d', contexts=set(ctx)); items=[mk('a',{'minimal'}), mk('b',{'standard'}), mk('c',{'full'})]; print('std', sorted(it.id for it in items_for_rank(items, 0))); print('min_rank', min_detail_rank({'full','minimal'}))"
  ```
- [ ] **Expected:** `std ['a', 'b']` — `items_for_rank(..., 0)` returns the items at-or-below the standard coordinate (minimal + standard, **not** full); `min_rank -1` — `min_detail_rank` returns the **coldest** (minimal) of the declared contexts.

### 3.4 cross-pillar import independence

- [ ] **Steps:**
  ```
  python -c "import dazzlecmd._vendor.help_lib as h, sys; print('log_lib imported by help_lib:', any('log_lib' in m for m in list(sys.modules) if 'help_lib' in m) and 'check-manually')"
  ```
  (Simpler manual check:) grep `help_lib/` for `log_lib` — there should be **no** import.
- [ ] **Expected:** `help_lib` does NOT import `log_lib` (independent siblings); `log_lib` imports `dazzle_lib` (valid down-only); `cli_lib` imports both `help_lib` and `log_lib` but neither imports `cli_lib`.

## What the automated tests DON'T cover

- **`dz kit -h` live-rendering FEEL** — the body is now automated (a golden byte-snapshot in `tests/test_kit_verbs.py`), but the golden compares the LF body string; the byte-gate's 10 commands still don't include `dz kit -h`. What automation still can't judge: how the output renders in a real terminal — Windows codepage (437 cmd / 1252 PS) on the `<->`/`--` glyphs, CRLF vs bare LF on the wire, column-alignment legibility at narrow widths (HV.1/HV.2/Section 1).
- **Windows codepage rendering** — `<->` arrows and `--` dashes in cmd.exe (437) vs PowerShell (1252) vs a UTF-8 terminal.
- **Terminal-width behavior** of the argparse usage block (Section 1.4).
- **The verbosity CLI surface** (`dz -vv` / `-q` / `--show`) — NOT wired yet (that is D-3); this checklist verifies the Continuum at the API level only. A future `v0.11.x__...__verbosity-flags` checklist extends this once D-3 lands.
- **Real-shell `dz` exit codes** and interactive feel of the help output.
