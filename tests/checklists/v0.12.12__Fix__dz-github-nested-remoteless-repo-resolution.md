# Human Test Checklist: `dz github` resolution from nested remote-less repos

**Target version:** v0.12.12-alpha
**Ships with commit:** `fix(0.12.12-alpha): dz github -- resolve the parent project from inside a nested remote-less repo` (TBD at time of writing)
**Companion automated tests:** 35 tests in `src/dazzlecmd/projects/dazzletools/github/tests/test_github_resolution.py` (unit + one real-CLI subprocess test). Full suite at time of writing: 2361 passed, 24 skipped.
**Fixes:** #111

## What this is

`dz github` is meant to be the shortest path from a terminal to a GitHub page: "open issue N of the project I'm standing in." It stopped doing that as soon as you stepped into a project's `private/` directory, because that directory is its own git repository with no remotes -- and the tool read "no GitHub remote here" as "this is not a repository," then guessed that whatever you typed was the *name* of a repository to search for.

This checklist verifies the three behavior changes that fix it, and -- more importantly -- asks a human to judge the things no assertion can: whether the new stderr announcement is the right amount of noise, whether the stdout/stderr split is right for scripting, and whether resolution picks the project a person would actually expect when repositories are nested inside each other.

Run time: ~5 minutes for High-Value, ~20 minutes for everything.

## Prerequisites

1. **Windows, Linux, or macOS.** The fix is cross-platform; the announcement text is ASCII-only by design (see 4.3).
2. **`gh` (GitHub CLI) installed and authenticated.** `gh auth status` should succeed. Without it `dz github` exits early with an install hint.
3. **dazzlecmd v0.12.12-alpha or later.** Check with `dz --version`.
4. **A scratch directory** for the fixtures built below. Nothing in this checklist touches your real repositories except read-only.

### State isolation

This checklist creates throwaway git repositories in a temp directory and never modifies your dotfiles or any real project. Two environment hazards are worth knowing before you build fixtures by hand:

- **GPG signing.** If your global config has `commit.gpgsign = true`, any `git commit` in a fixture will block on a pinentry dialog (Kleopatra on Windows) waiting for your key. Every `git commit` below therefore passes `-c commit.gpgsign=false`. Do not drop that flag.
- **Temp inside a repo.** On some systems `%TEMP%` / `$TMPDIR` sits *inside* another git repository (e.g. a home directory that is itself versioned). That makes a "not a repo" fixture silently *inside* one. The fixture setup below sets `GIT_CEILING_DIRECTORIES` to stop git's upward search at the scratch root. If you skip it, sections 2 and 3 may report a surprising parent.

### Fixture setup

Builds a project containing a remote-less `private/` store, mirroring the reported shape.

**cmd.exe**:
```cmd
set SCRATCH=%TEMP%\dzgh
set GIT_CEILING_DIRECTORIES=%SCRATCH%
rmdir /s /q "%SCRATCH%" 2>nul
mkdir "%SCRATCH%\proj\private\claude\issues"
cd /d "%SCRATCH%\proj"
git init -q
git remote add origin https://github.com/DazzleTools/dazzlecmd.git
cd private
git init -q
cd /d "%SCRATCH%\proj\private\claude\issues"
```

**PowerShell**:
```powershell
$env:SCRATCH = "$env:TEMP\dzgh"
$env:GIT_CEILING_DIRECTORIES = $env:SCRATCH
if (Test-Path $env:SCRATCH) { Remove-Item -Recurse -Force $env:SCRATCH }
New-Item -ItemType Directory -Force "$env:SCRATCH\proj\private\claude\issues" | Out-Null
Set-Location "$env:SCRATCH\proj"
git init -q
git remote add origin https://github.com/DazzleTools/dazzlecmd.git
Set-Location private
git init -q
Set-Location "$env:SCRATCH\proj\private\claude\issues"
```

**POSIX**:
```bash
export SCRATCH="${TMPDIR:-/tmp}/dzgh"
export GIT_CEILING_DIRECTORIES="$SCRATCH"
rm -rf "$SCRATCH"
mkdir -p "$SCRATCH/proj/private/claude/issues"
cd "$SCRATCH/proj"
git init -q
git remote add origin https://github.com/DazzleTools/dazzlecmd.git
cd private && git init -q
cd "$SCRATCH/proj/private/claude/issues"
```

> The fixture points `origin` at a real public repo so `gh` can resolve URLs. No writes are ever made to it.

### Reset between sections

Re-run the fixture setup block. It removes and rebuilds the scratch tree.

## High-Value Verification (~5 minutes)

**If you only have 5 minutes**, run these six. They are the "did the fix actually ship" smoke tests.

### HV.1 -- The reported bug is gone

Validates: an issue number typed from inside `private/` opens that issue, not a repository search.

- [ ] **Steps:** from `<scratch>/proj/private/claude/issues`:
  ```
  dz github -n 61
  ```
- [ ] **Expected:** stdout is exactly `https://github.com/DazzleTools/dazzlecmd/issues/61`. stderr carries one line naming the resolved project.
- [ ] **Must NOT happen:** any list of unrelated repositories (`b612`, `CS61A`, `ud615`), or a `Which repo? [1-10]:` prompt. That was the bug.
- [ ] **Why this matters:** `private/claude/issues/` is where issue drafts get written, so this fires in the one directory you are most likely to want the command.

### HV.2 -- Bare invocation resolves to the parent project

Validates: resolution, not just the digit path.

- [ ] **Steps:** same directory: `dz github -n`
- [ ] **Expected:** `https://github.com/DazzleTools/dazzlecmd` on stdout.
- [ ] **Why this matters:** proves the upward walk is general, not a special case bolted onto numbers.

### HV.3 -- The resolved project is announced

Validates: you are never silently sent to a repository you did not ask about.

- [ ] **Steps:** same directory: `dz github -n 61`
- [ ] **Expected:** stderr contains `Resolved via parent repo: DazzleTools/dazzlecmd (<path>)`.
- [ ] **Why this matters:** the command answered about a *different directory* than the one you are standing in. If that is silent, a person in the wrong folder opens the wrong project and never knows.

### HV.4 -- Standing in the project itself is unchanged and silent

Validates: no announcement noise on the normal path.

- [ ] **Steps:** from `<scratch>/proj` (the project root): `dz github -n 61`
- [ ] **Expected:** stdout as before; stderr has **no** `Resolved via parent repo` line.
- [ ] **Why this matters:** nothing was resolved from elsewhere, so saying so would be noise on every ordinary invocation.

### HV.5 -- A bare word means the same thing as it does at the project root

Validates: resolution is uniform across input classes, not just digits.

- [ ] **Steps:** run the same word from both places and compare.
  ```
  cd <scratch>/proj                      &&  dz github -n roadmap
  cd <scratch>/proj/private/claude       &&  dz github -n roadmap
  ```
- [ ] **Expected:** **identical behavior** -- both do an issue-keyword lookup in the project (`Unknown target 'roadmap'. Trying as issue keyword...`), differing only in that the second prints the `Resolved via parent repo:` line first.
- [ ] **Must NOT happen:** a list of unrelated repositories (`github/roadmap`, `docker/roadmap`, `DevOps-Roadmap`) or a `Which repo? [1-10]:` prompt from the `private/` location. That is the reported bug reached by a word instead of a digit.
- [ ] **Why this matters:** the fix's whole premise is that a command issued from inside `private/` reaches the project that owns it. If one input class still behaves differently, the premise only half holds.

### HV.5b -- The implicit repo finder still works outside a project

Validates: the narrowing in HV.5 did not break `dz github <name>`.

- [ ] **Steps:** from a directory with no enclosing project (e.g. your home directory): `dz github -n preserve`
- [ ] **Expected:** resolves to the repository, e.g. `https://github.com/DazzleTools/preserve`.
- [ ] **Note the boundary:** inside a resolved project, a bare word is an *issue keyword*; with no project to refer to, it is a *repository name*. `dz github repo <name>` is the explicit form and works in both places.
- [ ] **Judgment call -- is this boundary in the right place?** The current rule is unambiguous but not free: you give up implicit repo lookup while standing inside a project. A cleaner-feeling alternative exists if it grates in daily use -- try the issue keyword first and fall back to repo lookup when no issue matches, so both readings work. It was not taken because it spends an extra API call on every miss and makes what a word *means* depend on whether an issue happens to match it, which is harder to predict than the current rule. Worth revisiting only if the current boundary actually gets in your way.

### HV.6 -- Degrades honestly with no GitHub ancestor

Validates: the failure path is a clear message, not a wrong answer.

- [ ] **Steps** (pick your shell) -- build an orphan repo with no GitHub ancestor:

  **cmd.exe**:
  ```cmd
  mkdir "%SCRATCH%\orphan\sub"
  cd /d "%SCRATCH%\orphan"
  git init -q
  cd sub
  dz github -n 61
  ```

  **PowerShell**:
  ```powershell
  New-Item -ItemType Directory -Force "$env:SCRATCH\orphan\sub" | Out-Null
  Set-Location "$env:SCRATCH\orphan"; git init -q; Set-Location sub
  dz github -n 61
  ```

  **POSIX**:
  ```bash
  mkdir -p "$SCRATCH/orphan/sub" && cd "$SCRATCH/orphan" && git init -q && cd sub
  dz github -n 61
  ```
- [ ] **Expected:** non-zero exit, stderr says the remote is not a GitHub URL **and** that no enclosing repository has one either. No URL on stdout.
- [ ] **Why this matters:** a tool that guesses when it cannot resolve is worse than one that says so.

## Section 1: Resolution semantics (~5 min)

### 1.1 A live submodule keeps its own identity

- [ ] **Steps:** from inside a populated submodule that has its own GitHub remote. In a dazzlecmd checkout:
  ```
  cd src/dazzlecmd/projects/core/listall
  dz github -n
  ```
- [ ] **Expected:** `https://github.com/DazzleTools/listall` -- the **submodule**, not the parent project.
- [ ] **Why:** the rule is "nearest enclosing repository that has a GitHub remote." A submodule has one, so the walk stops there. If this returned the parent, the fix would be hijacking submodules.

### 1.2 Page keywords resolve upward too

- [ ] **Steps:** from `<scratch>/proj/private`: `dz github -n issues`, then `dz github -n pr`, then `dz github -n release`
- [ ] **Expected:** `.../issues`, `.../pulls`, `.../releases` on the parent project, each with the announcement on stderr.

### 1.3 `.` means "this project"

- [ ] **Steps:** from `<scratch>/proj/private/claude`: `dz github -n .`
- [ ] **Expected:** the parent project home page. NOT a repository search for a repo named `.`.

### 1.4 Explicit `--remote` is honored at every level

- [ ] **Steps:** from `<scratch>/proj/private`: `dz github -n --remote upstream`
- [ ] **Expected:** fails cleanly (no `upstream` remote exists anywhere in the chain). It must NOT silently fall back to `origin` and succeed -- that would make the flag a lie.

### 1.5 Multi-remote repository

- [ ] **Steps:** find or create a repo with two GitHub remotes, then from inside it: `dz github -n`
- [ ] **Expected:** resolves via `origin` by default; `--remote <other>` selects the other.
- [ ] **Judgment call:** is defaulting to `origin` the behavior you would expect here, or should it prompt?

## Section 2: Scripting behavior (~3 min)

### 2.1 stdout stays clean when piping

The announcement goes to stderr specifically so `-n` output can be consumed by another program.

- [ ] **Steps** (pick your shell), from `<scratch>/proj/private/claude/issues`:

  **cmd.exe**:
  ```cmd
  dz github -n 61 2>nul
  ```

  **PowerShell**:
  ```powershell
  dz github -n 61 2>$null
  ```

  **POSIX**:
  ```bash
  dz github -n 61 2>/dev/null
  ```
- [ ] **Expected:** exactly one line -- the URL. Nothing else.
- [ ] **Judgment call:** is stderr the right home for the announcement, or would you rather it were suppressible with a flag and on stdout by default?

### 2.2 Piping into another command

- [ ] **Steps** (POSIX / PowerShell):
  ```bash
  dz github -n 61 2>/dev/null | tr -d '\r\n' | wc -c
  ```
  ```powershell
  (dz github -n 61 2>$null).Length
  ```
- [ ] **Expected:** a character count matching just the URL -- confirming no stray whitespace or announcement text leaked into stdout.
- [ ] **Note:** strip `\r` as well as `\n`. On Windows (including git-bash) the line ending is CRLF, and `tr -d '\n'` alone leaves a stray byte that makes the count look one too high.

### 2.3 Exit codes

- [ ] **Steps:** run a resolving case and the HV.6 orphan case, checking the exit code each time.

  **cmd.exe**: `dz github -n 61` then `echo %ERRORLEVEL%`
  **PowerShell**: `dz github -n 61; $LASTEXITCODE`
  **POSIX**: `dz github -n 61; echo $?`
- [ ] **Expected:** `0` on success, non-zero on the unresolvable case.

## Section 3: Target classification (~3 min)

### 3.1 Digits are always issue numbers

- [ ] **Steps:** from `<scratch>/proj/private`, try several: `dz github -n 1`, `dz github -n 999`, `dz github -n 0`
- [ ] **Expected:** each produces `.../issues/<N>`. None triggers a repository search or a selection prompt.
- [ ] **Why:** searching GitHub for a repo called "61" returns noise (`b612`, `CS61A`, `ud615`) and never what was meant.

### 3.2 Alphanumeric names containing digits still work as names

- [ ] **Steps:** `dz github -n b612` from anywhere
- [ ] **Expected:** treated as a repository *name* (search/lookup), because it is not all-digits. This is the boundary of the digit rule -- confirm it is where you would want it.

### 3.3 Unknown words fall through to issue keyword search -- from inside `private/`

- [ ] **Steps:** from `<scratch>/proj/private` (NOT the project root -- that path has its own remote and takes a different branch, which would mask a regression here):
  ```
  dz github -n roadmap
  ```
- [ ] **Expected:** `Resolved via parent repo: ...`, then an issue lookup by label or title. On a project with no matching issue, a clear "No issues found matching 'roadmap'" -- never a repository search.

## Section 4: Rendering and real-world use (~4 min)

### 4.1 Actual browser launch

Every automated test uses `-n` to avoid opening windows. A human must confirm the real path works.

- [ ] **Steps:** from `<scratch>/proj/private/claude/issues`, without `-n`:
  ```
  dz github 61
  ```
- [ ] **Expected:** your default browser opens the issue page. The announcement still appears in the terminal.
- [ ] **Check:** the browser opened the **parent project's** issue, not a search page.

### 4.2 Announcement noise, in practice

- [ ] **Steps:** run five or six commands in a row from inside `private/` -- `dz github`, `dz github 1`, `dz github issues`, `dz github pr`, `dz github release`.
- [ ] **Judgment call:** having seen `Resolved via parent repo: ...` five times, does it read as helpful confirmation or as clutter? Options if it grates: shorten it, show it only on the first invocation per session, or gate it behind `-v`.

### 4.3 ASCII-only output on Windows consoles

- [ ] **Steps:** in a **cmd.exe** window (codepage 437, not Windows Terminal with UTF-8), from inside `private/`:
  ```cmd
  dz github -n 61
  chcp
  ```
- [ ] **Expected:** no mojibake (`â€"`, `?`, boxes) in the announcement or in any issue title echoed back. Em dashes in issue titles should render as `--`.
- [ ] **Why:** issue titles come from the GitHub API as UTF-8; the tool decodes them explicitly and downgrades non-ASCII for the console.

### 4.4 Path rendering in the announcement

- [ ] **Steps:** from `<scratch>/proj/private/claude/issues`: `dz github -n`
- [ ] **Check:** the path in `Resolved via parent repo: OWNER/REPO (<path>)` is readable and correctly separated for your platform (backslashes on Windows, forward slashes elsewhere).

### 4.5 Deeply nested starting point

- [ ] **Steps:** create `<scratch>/proj/private/a/b/c/d` and run `dz github -n` from there.
- [ ] **Expected:** still resolves to the parent project. The walk is bounded (10 enclosing repositories), not depth-limited by directory count.

## Section 5: Non-regression (~3 min)

### 5.1 Ordinary repository, no nesting

- [ ] **Steps:** from any normal checkout with a GitHub origin: `dz github -n`, `dz github -n 1`, `dz github -n pr`
- [ ] **Expected:** unchanged from v0.12.11 behavior. No announcement line.

### 5.2 Downward scan from a non-repository parent

- [ ] **Steps:** from a directory that is *not* a repository but whose children are (e.g. `C:\code\dazzlecmd` or any folder holding several checkouts): `dz github -n`
- [ ] **Expected:** the existing "scan subdirectories" behavior still works -- `Found: OWNER/REPO (in ./child/)`, or a numbered prompt if several distinct projects are found.
- [ ] **Why:** the fix inserts an upward walk; it must not have displaced the pre-existing downward one.

### 5.3 `dz github repo <name>` explicit form

- [ ] **Steps:** `dz github -n repo preserve`
- [ ] **Expected:** unchanged -- explicit repository lookup, from anywhere.

## What the automated tests DON'T cover

- **Real browser launch.** Every test uses `-n`. Section 4.1 is the only check that the non-`-n` path works.
- **Real `gh` network behavior.** `gh_browse` is stubbed in unit tests; only the one real-CLI test invokes the binary, and it asserts on resolution rather than on GitHub's response.
- **Windows console codepage.** Tests capture UTF-8 pipes, not a codepage-437 terminal. Section 4.3 is the only mojibake check.
- **Whether the announcement is the right amount of noise.** Section 4.2 is a judgment call no assertion can make.
- **Whether stderr is the right channel** for the announcement (Section 2.1).
- **Multi-remote preference.** Section 1.5 -- defaulting to `origin` is asserted nowhere as *desirable*, only as *current*.
- **Live submodule behavior.** Section 1.1 uses a real populated submodule; the automated tests use a synthetic worktree.
- **Performance feel.** The upward walk spawns a `git rev-parse` per level. Bounded at 10, but nobody has measured how it feels on a slow network drive.

## Cleanup

Remove the scratch tree and unset the isolation variables.

**cmd.exe**:
```cmd
cd /d %USERPROFILE%
rmdir /s /q "%TEMP%\dzgh"
set GIT_CEILING_DIRECTORIES=
set SCRATCH=
```

**PowerShell**:
```powershell
Set-Location $env:USERPROFILE
Remove-Item -Recurse -Force "$env:TEMP\dzgh" -ErrorAction SilentlyContinue
Remove-Item Env:\GIT_CEILING_DIRECTORIES -ErrorAction SilentlyContinue
Remove-Item Env:\SCRATCH -ErrorAction SilentlyContinue
```

**POSIX**:
```bash
cd ~
rm -rf "${TMPDIR:-/tmp}/dzgh"
unset GIT_CEILING_DIRECTORIES SCRATCH
```

Nothing else was modified: this checklist only reads from your real repositories.
