**Target version:** v0.9.49 (dazzlecmd-lib 0.8.49)

**Companion automated tests:** byte-gate (4 OK / 6 FAIL = parked-WIP baseline, unchanged) + full suite 1534 passed / 14 skipped. New regression tests: `tests/test_states.py::TestEntityStateAsPoint::test_kit_presence_space_is_the_multi_axis_product`, `tests/test_states.py::...::test_activation_transitions_declared_lateral`, `tests/test_cli_kit.py::TestKitEnableDisable::{test_enable_disable_enable_round_trips, test_activation_context_reports_lateral_kind}`.

## What this is

The v0.9.48-49 integration made the SH-redesign's multi-axis `ContinuumSpace` production-resident: `KIT_PRESENCE_SPACE` is now the `visibility x activation` PRODUCT, the `dz kit visibility` navigator reads its aligned visibility sub-space, and `dz kit enable`/`disable` run through `ActivationContext` on the generic transition executor. **Both slices are byte-transparent** -- so this checklist verifies the human/real-subprocess gap the byte-gate and mocks can't: that `enable`/`disable`/`visibility status` behave identically when run for real in a terminal, write config correctly, and render cleanly. It is deliberately right-sized -- it does NOT re-test the green unit-covered logic.

## Prerequisites

1. A working `dz` (this build, v0.9.49). Confirm: `dz --version` shows `0.9.49`.
2. **Isolate the config** so you never touch your real `~/.dazzlecmd/config.json`. Every command below assumes `DAZZLECMD_CONFIG` points at a throwaway file.
3. To reset between sections: delete the throwaway config (or `dz kit reset --yes` against it).

Set the isolated config (pick your shell):

**cmd.exe**:
```cmd
set DAZZLECMD_CONFIG=%TEMP%\dz_checklist.json
if exist %DAZZLECMD_CONFIG% del %DAZZLECMD_CONFIG%
```

**PowerShell**:
```powershell
$env:DAZZLECMD_CONFIG = "$env:TEMP\dz_checklist.json"
if (Test-Path $env:DAZZLECMD_CONFIG) { Remove-Item $env:DAZZLECMD_CONFIG }
```

**POSIX**:
```bash
export DAZZLECMD_CONFIG=/tmp/dz_checklist.json
rm -f "$DAZZLECMD_CONFIG"
```

## High-Value Verification (~5 minutes)

### HV.1 -- `dz kit enable` writes config + prints, real CLI

Validates: the rewired `_cmd_kit_enable` -> `ActivationContext` path end-to-end.

- [ ] **Steps:**
  1. `dz kit enable wtf`
  2. View the config (cross-shell below).
- [ ] **Expected:** stdout `Enabled kit: wtf`; the config file now has `"active_kits": ["wtf"]` and no `wtf` under `disabled_kits`.
- [ ] **Why this matters:** if the ActivationContext rewrite changed the config write or the message, this is where it shows.

  View config -- **cmd.exe**: `type %DAZZLECMD_CONFIG%` | **PowerShell**: `Get-Content $env:DAZZLECMD_CONFIG` | **POSIX**: `cat "$DAZZLECMD_CONFIG"` (or `python -m json.tool "$DAZZLECMD_CONFIG"` in any shell).

### HV.2 -- `dz kit disable` is the inverse

Validates: `_cmd_kit_disable` -> `ActivationContext`.

- [ ] **Steps:** `dz kit disable wtf`, then view config.
- [ ] **Expected:** stdout `Disabled kit: wtf`; config has `wtf` under `disabled_kits` and NOT under `active_kits`.
- [ ] **Why this matters:** confirms the disable list-mutation matches the old behavior exactly.

### HV.3 -- enable -> disable -> enable round-trips (the lateral axis, for real)

Validates: the activation axis is a real lateral round-trip through the CLI (not just the unit test).

- [ ] **Steps:** `dz kit enable wtf` ; `dz kit disable wtf` ; `dz kit enable wtf` ; view config.
- [ ] **Expected:** final config has `wtf` in `active_kits`, not in `disabled_kits` -- identical to the post-HV.1 state.
- [ ] **Why this matters:** the whole point of declaring activation as a REVERSIBLE transition -- the round-trip must land exactly back.

### HV.4 -- unknown kit warns but succeeds

Validates: the not-on-disk warning preserved (stderr) + rc 0.

- [ ] **Steps:** `dz kit enable ghost-kit-xyz` (capture stderr).
- [ ] **Expected:** a `Warning: kit 'ghost-kit-xyz' not found ...` line on **stderr**, stdout still `Enabled kit: ghost-kit-xyz`, exit code 0, and `ghost-kit-xyz` recorded in `active_kits`.
- [ ] **Why this matters:** the warning moved before the write in the rewrite -- confirm it still appears and still doesn't block.

### HV.5 -- `dz kit visibility status` navigator unchanged (the slice-1 byte-transparency)

Validates: the navigator still reads the visibility sub-space of the now-multi-axis presence space, byte-identically.

- [ ] **Steps:** pick a real tool (e.g. `dz kit visibility status core:find`).
- [ ] **Expected:** the `presence: <level>` line + `less visible ->` / `more visible ->` suggestion lines render exactly as before the integration (visible by default; the move suggestions name `dz kit visibility ...`). No traceback, no "PRODUCT space refuses cross-axis nav" error leaking through.
- [ ] **Why this matters:** slice 1 routed this through `KIT_PRESENCE_SPACE.axes["visibility"]`; if the product/sub-space wiring were wrong, the navigator would error or change wording here.

### HV.6 -- `dz list` after disable reflects the kit toggle

Validates: enable/disable still actually filter the tool listing (the downstream effect of the config write).

- [ ] **Steps:** `dz kit enable wtf` then `dz list` (note wtf tools present) ; `dz kit disable wtf` then `dz list`.
- [ ] **Expected:** wtf's tools appear when enabled and are gone when disabled. (wtf is opt-in; this is the observable effect of the activation toggle.)
- [ ] **Why this matters:** confirms the rewired write reaches the same discovery/filtering path.

## Section 1: Activation edge cases

### 1.1 disable a not-yet-known kit

- [ ] **Steps:** fresh config; `dz kit disable some-future-kit` ; view config.
- [ ] **Expected:** `Disabled kit: some-future-kit`; config `disabled_kits` contains it; a not-found warning on stderr. (Disable of an unknown kit is allowed -- it pre-records intent.)

### 1.2 idempotent enable (no duplicate)

- [ ] **Steps:** `dz kit enable wtf` twice ; view config.
- [ ] **Expected:** `wtf` appears exactly once in `active_kits` (no duplicate from the second enable).

### 1.3 enable a previously-disabled kit clears the disable

- [ ] **Steps:** `dz kit disable wtf` ; `dz kit enable wtf` ; view config.
- [ ] **Expected:** `wtf` in `active_kits`, absent from `disabled_kits` (enable removes the disable).

## Section 2: Visibility surface unchanged (slice-1 spot checks)

### 2.1 `dz kit visibility status` on a constitutional tool

- [ ] **Steps:** `dz kit visibility status core:safedel` (or another constitutional/always-active tool).
- [ ] **Expected:** the C3-aware navigator still refuses to suggest shadowing a constitutional tool (the "less visible" line notes shadow is refused, not a dead-end suggestion). Identical to pre-integration wording.

### 2.2 `dz kit visibility` overview + a silence round-trip

- [ ] **Steps:** `dz kit visibility silence core:find` ; `dz kit visibility status core:find` ; `dz kit visibility unsilence core:find`.
- [ ] **Expected:** silence sets the level to `silenced`, status reflects it, unsilence restores `visible`. No behavior change from the multi-axis restructure.

## What the automated tests DON'T cover (this checklist's job)

- Real `dz kit enable/disable/visibility status` invocation in a terminal (the tests call handler functions / contexts directly).
- Actual config-file write to disk + its on-disk JSON shape under real conditions.
- The stderr warning rendering + stream separation (stdout vs stderr) in a real shell.
- Windows codepage / ANSI color rendering of the navigator + tree output.
- The end-to-end effect of the toggle on `dz list` discovery (mocks stop at config state).
- That nothing in the multi-axis restructure leaked a `PRODUCT space refuses cross-axis nav` error into a user-facing path.
