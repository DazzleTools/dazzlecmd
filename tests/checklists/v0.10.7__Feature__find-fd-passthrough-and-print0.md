# Human Test Checklist: `dz find` -- fd passthrough (`--`) + `--print0`

**Target version:** v0.10.7
**Ships with commit:** `v0.10.7 feat: find -- fd passthrough (`--`) + --print0`
**Companion automated tests:** 13 in `tests/test_find_passthrough.py` (split_passthrough: 5, build_fd_command passthrough: 6, --print0: 2) + the existing 34 in `tests/test_find_setup.py`.

## What this is

`dz find` wraps `fd`. Two new escape hatches let power users reach fd's full surface without dazzlecmd re-exposing every flag:

- **`--`** -- everything after a literal `--` is appended raw to the `fd` command (for flags `dz find` doesn't surface, e.g. `--strip-cwd-prefix`, `--owner`, `--prune`).
- **`-0` / `--print0`** -- NUL-delimited output, to pipe into `xargs -0` (then `rg`, `sed`, etc.).

The automated tests verify the command-list *building* logic. This checklist verifies the parts only real `fd` + a real shell exercise: that the raw flags actually reach fd, and that NUL-delimited output pipes correctly.

## Prerequisites

1. `fd` (sharkdp/fd) installed and on PATH (`dz find --version` or `fd --version`).
2. A scratch directory with a few files/subdirs to search. Create one:

   **POSIX:** `mkdir -p /tmp/findtest/sub && touch /tmp/findtest/a.txt /tmp/findtest/sub/b.log && cd /tmp/findtest`
   **PowerShell:** `New-Item -ItemType Directory -Force $env:TEMP\findtest\sub; ni $env:TEMP\findtest\a.txt,$env:TEMP\findtest\sub\b.log -Force; cd $env:TEMP\findtest`
   **cmd.exe:** `mkdir %TEMP%\findtest\sub & type nul > %TEMP%\findtest\a.txt & type nul > %TEMP%\findtest\sub\b.log & cd %TEMP%\findtest`

## High-Value Verification (~3 minutes)

### HV.1 -- `--` passthrough reaches fd

Validates: raw args after `--` actually land on the fd command line.

- [ ] **Steps:** `dz find ".txt" -- --strip-cwd-prefix`
- [ ] **Expected:** results print **without** the leading `./` (or absolute-path prefix) that a normal `dz find` shows -- proving `--strip-cwd-prefix` (a flag dz doesn't surface) reached fd.
- [ ] **Why this matters:** if passthrough silently dropped, power users can't reach fd's full surface.

### HV.2 -- `-0` / `--print0` NUL output pipes to `xargs -0`

Validates: NUL-delimited output is real and consumable.

- [ ] **Steps (POSIX):** `dz find ".txt" -0 | xargs -0 -n1 echo FOUND:`
- [ ] **Expected:** one `FOUND: <abs-path>` line per match, with paths containing spaces handled intact (no word-splitting).
- [ ] **Why this matters:** `-0` exists specifically for safe piping; if it emits newlines instead of NULs, the contract is broken.

## Section 1: passthrough details

### 1.1 passthrough flag dz doesn't surface
- [ ] `dz find "" -- --type symlink` -> only symlinks (fd's `--type symlink`, not surfaced by dz).

### 1.2 passthrough can carry its own pattern when dz's is empty
- [ ] `dz find -- "b.*"` -> matches `b.log` (the pattern came from after `--`). Documented caveat: don't put a pattern in **both** places.

### 1.3 `--` at the very end is a no-op
- [ ] `dz find ".txt" --` -> same result as `dz find ".txt"` (empty passthrough).

## Section 2: --print0 details

### 2.1 default (no -0) is newline-delimited
- [ ] `dz find ".txt"` -> human-readable, one path per line.

### 2.2 -0 short flag == --print0 long flag
- [ ] `dz find ".txt" -0` and `dz find ".txt" --print0` produce identical (NUL-delimited) output.

## What the automated tests DON'T cover

- Whether the passthrough flags are **valid fd flags** (dz does not validate them -- fd does; a bad flag surfaces fd's own error).
- Real NUL-byte delimiting in a real pipe (`xargs -0`), and correct handling of paths with spaces/unicode.
- Shell quoting of `--` across cmd.exe / PowerShell / POSIX.
- Interaction of `--print0` with `dz find` actions (open/copy) -- actions still parse the NUL stream.

## Cleanup

- [ ] Remove the scratch dir: `rm -rf /tmp/findtest` (POSIX) / `Remove-Item -Recurse -Force $env:TEMP\findtest` (PowerShell) / `rmdir /s /q %TEMP%\findtest` (cmd).
