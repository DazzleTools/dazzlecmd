## What this is

This is the consolidated Phase 3.5 Tier 1 wrap-up checklist. It exercises end-to-end what the seven commits above shipped: aggregator-decoupling (T1-M1/M2), mode.py parameterization (F1-F8 BLOCKERs), the dirty-tree refuse-or-force gate (T1-E), declarative `aggregator.json` config (T1-M1), the `DZ_APP_NAME`/`DZ_COMMAND` branding env-var injection (issue #74, T1-Z), the cwd-impersonation regression fix (v0.7.52), and the recursive-chain validation (`dz wtf:core:locked`).

Each individual commit was deemed automated-test-sufficient on its own. Several explicitly deferred this checklist on the basis that "one consolidated walkthrough after T1-M lands beats four overlapping fragments." This is that walkthrough.

It is hand-runnable on a Windows + dev-mode editable install where dazzlecmd + dazzlecmd-lib + wtf-windows live side by side under `C:\code\`. The cmd.exe / PowerShell / bash-WSL forms below handle cross-shell concerns; the tool-isolation prerequisites prevent any of the destructive steps from corrupting your real config or real submodules.

## Prerequisites

1. **OS / install state.** Windows 10/11; `dz` and `wtf` are both `pip install -e` editable installs from `C:\code\dazzlecmd\github` and `C:\code\wtf-windows` respectively. dazzlecmd-lib is the editable install under `packages/dazzlecmd-lib/`.
2. **Shells.** Windows Terminal with at least one of cmd.exe, PowerShell 5.1, PowerShell 7, and bash-WSL. The cross-shell sections call out which shell each form is for.
3. **Snapshot first** -- the checklist includes one destructive action (`wtf mode switch` against a real wtf submodule). Take a recovery snapshot before starting:
   ```
   cd C:\code\dazzlecmd\github
   dz git-snapshot save "before T1-J checklist run"
   ```
4. **Config isolation.** Several sections set `DAZZLECMD_CONFIG` to a throwaway path so the checklist run doesn't pollute your real `~/.dazzlecmd/config.json` (active_kits state, etc.). Set a per-section temp config path; reset between sections.
5. **wtf kit enabled.** Section 5 (recursive chain) requires the wtf kit enabled in dazzlecmd. The chain test in v0.7.53 already enabled it; if you've since `dz kit disable wtf`, re-enable for this checklist.

How to reset state between sections:

```
:: cmd.exe
set DAZZLECMD_CONFIG=

# PowerShell
Remove-Item Env:\DAZZLECMD_CONFIG -ErrorAction SilentlyContinue

# bash / WSL
unset DAZZLECMD_CONFIG
```

  ```bash
  # POSIX / bash-WSL
  ```

## What the automated tests DON'T cover

- **Real `dz mode switch` on a real submodule.** Tests use synthetic git fixtures in `tmp_path`. The actual `shutil.rmtree(tool_dir)` -> `git submodule update --init` -> reattach flow against a real submodule with real git config is only exercised by HV.4 + Section 3 + Section 4 here.
- **Cross-shell rendering** of mode-switch and aggregator help. Tests run under Python; they don't catch a shell-specific Unicode issue. Section 7 catches.
- **Real-subprocess env-var flow** -- the test asserts `os.environ["DZ_APP_NAME"]` inside the Python-level dispatcher; spawning a real `.ps1` / bash child is deferred to issue #76.
- **The `_branding.ps1` reference template** doesn't exist yet (deferred to #76).
- **DZ_PROJECT_ROOT** is explicitly deferred (decision recorded; tracking in #76).
- **Performance feel** -- the `git rev-parse` + `git status` calls inside `_check_dirty_tree` add ~10-20ms per mode-switch invocation. Not benchmarked here; if you notice mode-status getting noticeably slower as projects/ grows, file an issue.
- **Network-dependent submodule operations** -- `git submodule add <url>` when offline. Not exercised; would surface its own clear error.
- **Real cross-aggregator chains beyond 3 tiers** -- if you have nested-of-nested aggregators (`dz wtf:something:nested:tool`), the dispatcher's behavior is exercised by the test FQCN suite but not in a real 4-tier scenario.
