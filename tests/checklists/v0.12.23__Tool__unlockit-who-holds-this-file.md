# Human Test Checklist: dz unlockit -- who holds this file or folder, and which window

**Target version:** 0.12.23-alpha
**Ships with commit:** TBD (v0.12.23 feat(unlockit): ...)
**Companion automated tests:** 40 tests in `src/dazzlecmd/projects/dazzletools/unlockit/tests/test_unlockit.py`

## What this is

A short hand pass over what the automated tests cannot see: real windows coming to the front, real Restart Manager and working-directory answers on a live desktop, how the report reads in a terminal, and how an old handle.exe behaves. It takes about 10 minutes on Windows. Testing depth for this release was set deliberately light, so there are only the high-value steps and no detailed sections.

## Prerequisites

1. Windows 10 or 11, with `dz` installed from this version, and a normal (unelevated) prompt unless a step says otherwise.
2. `psutil` installed (`python -c "import psutil"`). Without it, the folder steps report the working-directory check as unavailable. That is expected, but HV.1 then cannot pass.
3. VS Code (`code` on PATH) for HV.1. Any editor whose window title shows the open folder name works the same way.
4. **`--focus` raises real windows on your desktop.** Save work in the editor you test with before HV.1.
5. Create the scratch tree (it is removed in Cleanup):

   **cmd.exe**:
   ```cmd
   mkdir %TEMP%\unlockit-check\held-dir
   echo hello> %TEMP%\unlockit-check\LOCKED-7731.md
   echo hello> %TEMP%\unlockit-check\free.md
   ```

   **PowerShell**:
   ```powershell
   New-Item -ItemType Directory -Force "$env:TEMP\unlockit-check\held-dir" | Out-Null
   "hello" | Set-Content "$env:TEMP\unlockit-check\LOCKED-7731.md"
   "hello" | Set-Content "$env:TEMP\unlockit-check\free.md"
   ```

   **POSIX (Git Bash)**:
   ```bash
   T="$(cygpath -u "$TEMP")/unlockit-check"; mkdir -p "$T/held-dir"
   echo hello > "$T/LOCKED-7731.md"; echo hello > "$T/free.md"
   ```

Exit codes are read with `echo %ERRORLEVEL%` (cmd), `$LASTEXITCODE` (PowerShell) or `echo $?` (bash).

## High-Value Verification (~10 minutes)

### HV.1 -- A folder held by an editor window: find it, raise it, free it

Validates: the working-directory scan, grouping many holder processes under one window, picking the right window by title, `--focus`, and the report turning "Free" once the window closes.

- [ ] **Steps:**
  1. `code "%TEMP%\unlockit-check\held-dir"` (PowerShell: `code "$env:TEMP\unlockit-check\held-dir"`). Wait until VS Code has fully loaded the folder, then minimize that window.
  2. `dz unlockit "%TEMP%\unlockit-check\held-dir"`. In PowerShell use `$env:TEMP`, and in bash `"$TEMP\unlockit-check\held-dir"`. These substitutions apply to every step below.
  3. `dz unlockit "%TEMP%\unlockit-check\held-dir" --focus 1`
  4. Close that VS Code window (or File > Close Folder), wait a few seconds, then repeat step 2.
- [ ] **Expected:**
  - Step 2 prints `In use: deleting it now would fail (sharing violation).` and one group: `[1] window: "... - held-dir - Visual Studio Code"  [minimized]`. Under it are several processes (Code.exe, often python.exe language servers) marked `working directory is here`. Exit code 1. It answers in about a second.
  - Step 3 restores the window and brings it to the front, and prints `focused: "..."`. Exit code 0.
  - Step 4 prints `Free: nothing holds this folder.` Exit code 0.
- [ ] **Why this matters:** it is the whole purpose of the tool. A folder Windows refuses to delete becomes a named window you can go to.

### HV.2 -- A file held open by a process with no window

Validates: Restart Manager detection, and reporting a windowless holder honestly.

- [ ] **Steps:**
  1. In a second prompt, hold the file open for two minutes (the same command works in any shell):
     ```
     python -c "import os,time; h=open(os.path.expandvars(r'%TEMP%\unlockit-check\LOCKED-7731.md')); time.sleep(120)"
     ```
     In PowerShell or bash, `%TEMP%` inside the Python string is still expanded by `expandvars` on Windows.
  2. In the first prompt: `dz unlockit "%TEMP%\unlockit-check\LOCKED-7731.md"`
- [ ] **Expected:** `In use: deleting it now would fail (sharing violation).`, then a line for `python.exe` with `has it open`, exit code 1. The group header says either `no window: python.exe (pid N)` or `<terminal>.exe (pid N): K windows, none names this path`, depending on what launched the second prompt. It must not claim a specific unrelated window.
- [ ] **Why this matters:** the most common real lock is a background process holding one file. A wrong window here would send you to the wrong place.

### HV.3 -- A free file says so

- [ ] **Steps:** `dz unlockit "%TEMP%\unlockit-check\free.md"`
- [ ] **Expected:** `Free: nothing holds this file.`, exit code 0. The file still exists with its content unchanged (`type`, `Get-Content` or `cat` it). The lock check opens the file and must never delete or change it.
- [ ] **Why this matters:** the check works by asking Windows for delete access. If that ever slipped into actually deleting, this is where it would show.

### HV.4 -- `--focus` refuses rather than guesses

- [ ] **Steps:** while HV.2's holder is still running (restart it if its two minutes are up), run `dz unlockit "%TEMP%\unlockit-check\LOCKED-7731.md" --focus`
- [ ] **Expected:** the report, then on stderr `could not focus: ...`. The reason is either that no holder has a window that can be identified, or that the terminal has K windows and none names this path. Exit code 2. No window changes.
- [ ] **Why this matters:** raising a random window of the right program is worse than raising nothing. The user would act on the wrong one.

### HV.5 -- An old handle.exe gives up instead of hanging

Skip if you have no handle.exe. Builds from 2019 (4.22) and 2022 (5.0) are known to hang when not elevated.

- [ ] **Steps:** `dz unlockit "%TEMP%\unlockit-check\LOCKED-7731.md" --handle --handle-exe "<path to handle64.exe>"`
- [ ] **Expected:** within about 20 seconds, the normal report plus `note: --handle: handle64.exe gave no answer in 20s (older builds hang when not elevated)`, or handle's rows marked `(handle.exe)` if your build answers. It never waits longer than about 20 s.
- [ ] **Why this matters:** handle.exe is the tool most people already have. A hang would make unlockit look broken.

## What the automated tests DO cover

| Area | Count |
|---|---|
| Title ranking (whole-segment matching, decorations, ties, lone window) | 7 |
| Process ancestry (reused PIDs, cycles, explorer.exe stop) | 4 |
| Grouping holders by window, self-shell flag, dedupe | 5 |
| Focus attempt chain against a faked Win32 layer | 5 |
| `--focus` choice and CLI exit codes (focus faked) | 6 |
| handle.exe parsing and timeout (faked), status wording | 4 |
| Real probe, Restart Manager, working-directory scan, junction walk, CLI, using the suite's own child processes | 9 |

Every automated test has `focus` patched to fail, so the suite never raises a real window. That is why HV.1 and HV.4 exist.

## What the automated tests DON'T cover

- Real windows coming to the front: Windows' focus-stealing rules depend on what you last typed into.
- Which processes a real editor leaves in a folder, and how soon they let go after the window closes.
- Windows Terminal: anything started in a tab rolls up to `WindowsTerminal.exe`, whose title shows only the active tab, so the tab cannot be named.
- Elevated runs: holders that are services or other users' processes only appear from an elevated prompt.
- How the report reads at your terminal width and code page.

## Reporting issues found

Note the HV number, paste the exact command and full output, and add whether the prompt was elevated. File an issue referencing this checklist and version 0.12.23.

## Cleanup

Stop HV.2's holder (Ctrl-C in its prompt, or let it time out), close any VS Code window still on `held-dir`, then remove the scratch tree:

**cmd.exe**: `dz safedel "%TEMP%\unlockit-check"`
**PowerShell**: `dz safedel "$env:TEMP\unlockit-check"`
**POSIX**: `dz safedel "$(cygpath -w "$TEMP")\unlockit-check"`

If the delete fails, `dz unlockit "%TEMP%\unlockit-check"` will tell you what still holds it.
