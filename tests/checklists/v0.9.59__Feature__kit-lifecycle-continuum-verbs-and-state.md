## What this is

The kit lifecycle is the groupable/continuum machinery surfaced as `dz kit *`: enable/disable (activation), attach/detach (loading→pointer), add/remove (membership), all on one **lifecycle continuum** (`{KitOff..KitOn}`), inspectable as state (`dz kit management`) the same way `dz kit visibility` shows visibility state. This checklist verifies the user-facing behavior the mocks can't: real config writes, real git submodule surgery, the de-duped help rendering, the state views, the detach→attach round-trip, and (new in 0.9.60) the **`[pointer]` marker rendering** — its YELLOW color, column placement, and Windows-codepage behavior in a real terminal. A human runs it before the 0.9.x closeout.

## Prerequisites

1. Windows / Linux / macOS with dazzlecmd installed (`dz` on PATH) and dazzle-lib ≥ 0.6.0.
2. **Config isolation** — point `DAZZLECMD_CONFIG` at a throwaway file so the real `~/.dazzlecmd/config.json` is never touched.
3. **For add/remove/detach (destructive):** use a THROWAWAY kit and take a `dz git-snapshot` first; `dz` is root-anchored (#81), so these touch the installed tree's `projects/`+`kits/`+git. Never run them against a kit you care about. `remove`/`detach` files go to `dz safedel` trash (recoverable).
4. Reset between sections: `dz kit reset --yes` (clears kit config) and restore from the git-snapshot.

  **cmd.exe:** `set DAZZLECMD_CONFIG=%TEMP%\dz_kitlc.json`
  **PowerShell:** `$env:DAZZLECMD_CONFIG = "$env:TEMP\dz_kitlc.json"`
  **POSIX:** `export DAZZLECMD_CONFIG=/tmp/dz_kitlc.json`

## High-Value Verification (~5 minutes)

### HV.1 — `dz kit -h` is the de-duped by-axis hierarchy
- [ ] Run `dz kit -h`.
- [ ] **Expected:** the usage line, then `inspect:` / `management:` / `visibility:` / `favorite:` sections; each verb appears **once**; **no** "positional arguments" restatement block.
- [ ] **Why this matters:** the v0.9.58 fix; if the old 4×-duplicate help is back, the renderer override regressed.

### HV.2 — enable/disable actually filters dispatch
- [ ] `dz kit disable <somekit>` then `dz list`; then `dz kit enable <somekit>` then `dz list`.
- [ ] **Expected:** the kit's tools vanish from `dz list` when disabled, return when enabled. `dz kit management` shows it `disabled (loaded, inactive)` then `active`.
- [ ] **Why this matters:** activation is the warm rung of the continuum; the clinical on/off must work.

### HV.3 — detach → attach round-trip + the `[pointer]` marker (on a throwaway kit)
- [ ] `dz kit detach <throwaway>` → `dz kit list` (the kit still LISTS, now flagged **`[pointer]`** beside `[disabled]`, with a footer legend) → `dz list` (its tools gone) → `dz kit management` (shows `detached (pointer; not loaded)`) → `dz kit attach <throwaway>` → `dz kit list` (the `[pointer]` marker is gone) → `dz list` (tools back).
- [ ] **Expected:** detach makes it a pointer + disabled (files kept on disk) AND visibly marks it `[pointer]` in the list; attach loads + enables AND clears the marker. Round-trips.
- [ ] **Why this matters:** the slice-4 capstone — the loading axis, the implicit detach→disable cascade/attach→enable, AND the now-visible detached state (you can SEE which kits are pointers without `dz kit management`).

### HV.4 — the shortname↔grouped duality
- [ ] `dz kit activation enable <kit>` behaves identically to `dz kit enable <kit>`; likewise `dz kit loading detach` vs `dz kit detach`, `dz kit membership remove` vs `dz kit remove`.
- [ ] **Expected:** both forms do the same thing (same handler).
- [ ] **Why this matters:** the verb-level shortname↔FQCN model.

### HV.5 — `dz kit management` shows the lifecycle position
- [ ] `dz kit management` (all kits) and `dz kit management <kit>` (one).
- [ ] **Expected:** each kit shows `active` / `disabled (loaded, inactive)` / `detached (pointer; not loaded)`, `[always-active]` flagged. `dz kit activation` / `loading` / `membership` show their slice.
- [ ] **Why this matters:** state-on-invoke parity with `dz kit visibility`.

### HV.6 — C3 refusal protects constitutional kits
- [ ] `dz kit remove core` and `dz kit detach core` (core is `always_active`).
- [ ] **Expected:** both refuse with a C3 message; `core` untouched.
- [ ] **Why this matters:** constitutional kits must not be removable/detachable.

## Section 1: Activation (enable / disable / focus)

### 1.1 enable / disable round-trip + config
- [ ] **Steps:** `dz kit disable wtf` → inspect the config file → `dz kit enable wtf` → inspect again.

  **cmd.exe:** `type %DAZZLECMD_CONFIG%`  **PowerShell:** `Get-Content $env:DAZZLECMD_CONFIG`  **POSIX:** `cat "$DAZZLECMD_CONFIG"`
- [ ] **Expected:** `disabled_kits` gains/loses `wtf`; `active_kits` complementary; other config keys preserved.
- [ ] **Check:** `dz kit activation` lists wtf under disabled then active.

### 1.2 enable an unknown kit
- [ ] `dz kit enable nosuchkit` → warns but exits 0 (idempotent, non-fatal).

### 1.3 focus
- [ ] `dz kit focus wtf` → only wtf (+ always-active) enabled; `dz kit management` confirms.

## Section 2: Loading (attach / detach) — pointer kits + the `[pointer]` marker

### 2.1 detach writes the pointer + disables (throwaway kit; git-snapshot first)
- [ ] `dz kit detach <throwaway>` → check `kits/<throwaway>.kit.json` has `"pointer": {"materialized": true}`; `projects/<throwaway>/` still on disk; config shows it disabled.
- [ ] `dz list` — its tools are gone (discovery skip); `dz kit list` — the kit still LISTS.

### 2.2 the `[pointer]` marker in `dz kit list` (NEW in 0.9.60)
- [ ] After detach, `dz kit list` (no arg): the detached kit's row reads `<name>  0 tool(s)  [disabled] [pointer]`, and a footer legend appears: `[pointer] = detached (a pointer; tools not loaded); ` `dz kit attach <name>` ` to reconnect`.
- [ ] `dz kit list <throwaway>` (drill-in): the header reads `Kit: <name> [disabled, pointer]` followed by a `(detached -- a pointer; tools not loaded; ` `dz kit attach <name>` ` to reconnect)` note, then `No tools in this kit.`
- [ ] **Wording:** it says "tools not loaded" (the LOADING axis), NOT "not materialized" -- a detached kit's files ARE still on disk (`materialized: true`); only its tools are unloaded. (Matches `dz kit management`'s phrasing.)
- [ ] **Color (eyeball):** with color on (a real TTY), `[pointer]` renders **YELLOW**; the rest of the row is unaffected and columns stay aligned (the marker is appended at line-end, so it must NOT shift the `tool(s)`/`[status]` columns). Pipe to a file (`dz kit list > out.txt`) and confirm NO raw ANSI escapes leak when not a TTY.
- [ ] **Windows codepage:** on `cmd.exe` (cp437) and PowerShell (cp1252), the marker + legend print cleanly — no mojibake, no `??`, no terminator errors (the text is ASCII-only: `[pointer]`, `--`, backticks).

### 2.3 the `[pointer]` branch in `dz tree` (NEW in 0.9.60)
- [ ] With a detached kit present, `dz tree --show-disabled` (detach implies disable, so the detached kit is hidden by default like any disabled kit): the detached kit appears as its OWN leaf branch `\-- <name> [pointer]` (with a dim ` [disabled]` suffix), and the footer reports `..., N detached pointer kit(s)`.
- [ ] **Expected:** detached kits never appear under a parent kit's tools (they load none) — they are top-level branches, like virtual kits. A tree with no detached kits shows NO `[pointer]` text and NO "detached pointer" footer (regression guard).
- [ ] **`--show-empty` (the detach->attach symmetry).** `dz tree` is tool-centric: a kit with no tools has no branch by default. So a freshly-scaffolded EMPTY kit (e.g. `dz new kit zztmp`) is invisible in plain `dz tree` whether enabled or not. Run `dz tree --show-empty` -> the empty enabled kit shows as a childless branch `+-- zztmp` (no children). Plain `dz tree` (no flag) -> it's absent. This is why a re-attached empty kit "disappears" without `--show-empty`: it's enabled but has no tools. (A re-attached NON-empty kit reappears normally, with its tools.)

### 2.4 attach is the inverse (clears the marker)
- [ ] `dz kit attach <throwaway>` → pointer block gone; kit loads + enabled; `dz list` shows its tools again; `dz kit list` no longer shows `[pointer]` (and the legend disappears once no detached kits remain).
- [ ] **If the throwaway kit is EMPTY** (no tools, e.g. fresh `dz new kit`), after attach it is enabled but has no tools, so plain `dz tree` won't show it -- use `dz tree --show-empty` to see it as a childless branch. (Tool-bearing kits reappear in plain `dz tree` after attach.)

### 2.5 attach a non-pointer / unfetched
- [ ] `dz kit attach <loaded-kit>` → friendly no-op ("not detached"); does NOT enable a merely-disabled kit.
- [ ] (If you can craft a `pointer:{materialized:false}` registry) `dz kit attach` → refuses with the #80 "not yet implemented" fetch message.

### 2.6 dry-run
- [ ] `dz kit detach <throwaway> --dry-run` and `dz kit attach <throwaway> --dry-run` → print the plan, change nothing (and so no `[pointer]` marker appears afterward).

## Section 3: Membership (add / remove)

### 3.1 add a kit from a URL (real git submodule)
- [ ] `dz kit add <git-url>` → submodule added under `projects/<name>`, registry written, tools discovered. (Real network/git — mocks don't cover this.)

### 3.2 remove (recoverable)
- [ ] `dz kit remove <throwaway>` → confirm prompt (or `--yes`); deregisters + safedel-trashes files + drops config refs; prints the re-add hint.
- [ ] **Check:** `dz safedel list` shows the trashed dir (recover with `dz safedel recover last`). For a submodule kit, `.gitmodules`/`.git/config`/`.git/modules` are clean (the v0.9.52 fix); the worktree was kept for safedel (not destroyed).
- [ ] `dz kit remove <throwaway> --dry-run` → plan only, nothing changed.

## Section 4: The CLI surface (groups, help, parity)

### 4.1 nested axis groups
- [ ] `dz kit activation -h`, `dz kit loading -h`, `dz kit membership -h` → each lists its verbs; `dz kit <axis>` (no verb) → that axis's state.

### 4.2 shortname↔grouped parity
- [ ] `dz kit loading attach <kit>` == `dz kit attach <kit>` (same effect); confirm via `dz kit management`.

### 4.3 help readability (eyeball)
- [ ] `dz kit -h` reads cleanly on an 80-col terminal; long verb descriptions (detach/remove) may wrap — judge if acceptable. No color bleed, no trailing whitespace.

## What the automated tests DON'T cover (run these by hand)

- **Real `dz kit add <url>`** — actual `git submodule add` against a live URL (network, auth, submodule init).
- **Real `dz kit remove` of a real submodule** — `.gitmodules`/`.git/modules` cleanup + safedel on the real tree (#81 root-anchoring means it can't be auto-sandboxed).
- **`dz kit -h` rendering** in a real terminal — wrapping, width, color, alignment of the hierarchy.
- **Interactive confirm** on `dz kit remove` (the y/N prompt).
- **safedel recovery** of a removed kit end-to-end.
- **The `[pointer]` marker COLOR + alignment** — the YELLOW rendering on a real TTY, column stability, and no-ANSI-leak when piped (tests run with color OFF, so the YELLOW path and Windows-codepage behavior are human-only).

## Reporting issues found
1. Note the section/step number + exact command + output.
2. Save the relevant config / registry / `.gitmodules` state.
3. File against this checklist + the triggering version.

## Cleanup
- `dz kit reset --yes` (clear kit config); delete the throwaway `DAZZLECMD_CONFIG` file.
- Restore the tree from the `dz git-snapshot` taken in prerequisites (undoes any add/remove/detach).
- `dz safedel list` → recover any test-trashed kit if needed.
