Plus byte-identical golden verification of `dz git` output across 17 invocations.

## What this is

`dz dazzle-update` answers "what do I need to pull, push, or reinstall?" across every GitHub namespace you own. It is a *reporting* tool, so its only real value is being right about state -- which makes the things a mock cannot check (real terminals, real networks, real repos) exactly the things most worth a human's time.

This checklist covers those. Run it before releasing 0.12.7-alpha, or after any change to discovery, fetching, the finding taxonomy, or the renderer. Anyone with the repo installed can run it; nothing here needs project-internal access.

**All previously-known bugs are fixed as of 0.12.7.** Section 9.2 lists them; if any reproduces, it is a regression. The earlier multi-checkout bug is also fixed, so Section 9.1 now verifies the FIX rather than the bug.

**Historical note:** -- Section 9.1 asks you to confirm it still reproduces, so its fix is verifiable later. It is recorded as a strict `xfail` test that will fail the moment it is fixed. Section 9.2 lists three bugs that were fixed after the first draft: if any of those reproduce, it is a regression.

## Prerequisites

1. Windows, macOS, or Linux. Some sections are Windows-specific and marked.
2. `dazzlecmd` 0.12.6-alpha installed; `git` and `gh` on PATH.
3. At least one directory containing several git repos to scan.
4. **A real terminal** for Sections 2 and 3 -- not an IDE console, not a captured pipe. Colour and progress cannot be verified through a pipe by definition.

### State isolation (do this first)

`dz dazzle-update` writes a scan cache and an identity cache under your user config directory. Isolate both before testing, or a test run will overwrite the cache your real runs depend on.

**cmd.exe**:
```cmd
set DU_TEST=%TEMP%\du-checklist
mkdir "%DU_TEST%"
python -c "import json,os; json.dump({'cache_path': os.path.join(os.environ['DU_TEST'],'scan.json'), 'roots':[os.environ['DU_TEST']]}, open(os.path.join(os.environ['DU_TEST'],'cfg.json'),'w'))"
```

**PowerShell**:
```powershell
$env:DU_TEST = "$env:TEMP\du-checklist"
New-Item -ItemType Directory -Force $env:DU_TEST | Out-Null
python -c "import json,os; json.dump({'cache_path': os.path.join(os.environ['DU_TEST'],'scan.json'), 'roots':[os.environ['DU_TEST']]}, open(os.path.join(os.environ['DU_TEST'],'cfg.json'),'w'))"
```

**POSIX**:
```bash
export DU_TEST=/tmp/du-checklist
mkdir -p "$DU_TEST"
python -c "import json,os; json.dump({'cache_path': os.path.join(os.environ['DU_TEST'],'scan.json'), 'roots':[os.environ['DU_TEST']]}, open(os.path.join(os.environ['DU_TEST'],'cfg.json'),'w'))"
```

Then pass `--config <that cfg.json>` to every command below that would otherwise write cache. Sections that deliberately exercise your real layout say so explicitly.

### Reset between sections

Delete the scan cache to force a fresh scan:

| Shell | Command |
|---|---|
| cmd.exe | `if exist "%DU_TEST%\scan.json" del "%DU_TEST%\scan.json"` |
| PowerShell | `if (Test-Path "$env:DU_TEST\scan.json") { Remove-Item "$env:DU_TEST\scan.json" }` |
| POSIX | `rm -f "$DU_TEST/scan.json"` |

## High-Value Verification (~5 minutes)

If you only have five minutes, run these six. They cover the behaviour most likely to be wrong and most damaging if it is.

### HV.1 -- The tool runs and answers the primary question

Validates: end-to-end discovery, join, and rendering against a real layout.

- [ ] **Steps:** `dz dazzle-update`
- [ ] **Expected:** A report within ~2 minutes. First content line after the header is `Summary` showing counts like `N to pull * N to push * ...`. `BEHIND UPSTREAM` is the first detail section.
- [ ] **Why this matters:** If this fails, nothing else in the tool is reachable.

### HV.2 -- Fetching actually happens

Validates: the single most important correctness property. Without a fetch, `behind` is measured against stale refs and every repo reads as current.

- [ ] **Steps:**
  1. Pick a repo you know has unpulled commits on its remote.
  2. Run `dz dazzle-update --no-fetch` and note whether it appears under `BEHIND UPSTREAM`.
  3. Run `dz dazzle-update` (fetch on) and compare.
- [ ] **Expected:** With `--no-fetch` the repo may be absent AND a warning states behind-counts reflect the last fetch. With fetching on, the repo appears with a correct behind-count.
- [ ] **Why this matters:** A scanner that silently reports "current" for repos with waiting work is worse than no scanner.

### HV.3 -- `--fix --dry-run` acts on nothing

Validates: the write path's safety, before anyone runs it for real.

- [ ] **Steps:** `dz dazzle-update --fix --dry-run`
- [ ] **Expected:** Every action line is prefixed `[dry-run]`. A `REFUSED` block lists repos it declined with reasons. Afterwards, `git status` in any listed repo is unchanged and no `pip install` ran.
- [ ] **Why this matters:** `--fix` mutates real repos. If dry-run is not inert, nothing about the write path can be trusted.

### HV.4 -- Colour renders in a real terminal

Validates: ANSI VT enablement on Windows, which no test can verify through a pipe.

- [ ] **Steps:** `dz dazzle-update --cached` in cmd.exe, then PowerShell, then your usual terminal.
- [ ] **Expected:** Section headings are coloured, not literal escape text like `←[91m`. `BEHIND UPSTREAM` is red; `NOT CLONED` is grey.
- [ ] **Why this matters:** Raw escape sequences make the report unreadable and look broken on the platform this tool primarily targets.

### HV.5 -- `--json` is clean and parseable

Validates: the cross-box diffing contract.

- [ ] **Steps** (all shells): `dz dazzle-update --json | python -m json.tool > NUL` (cmd) / `> $null` (PowerShell) / `> /dev/null` (POSIX)
- [ ] **Expected:** Exits 0, no parse error. No colour codes and no progress text contaminate stdout.
- [ ] **Why this matters:** Progress goes to stderr specifically so this works; a regression here silently breaks any consumer.

### HV.6 -- `dz git` is unchanged by the refactor

Validates: that reducing `dz git` to a shim did not alter it.

- [ ] **Steps:** `dz git`, `dz git composition`, `dz git workspace`, `dz git form`, `dz git --json`
- [ ] **Expected:** All succeed. Output matches what 0.12.5 produced, except `--json` now also carries `upstream`, `ahead`, `behind`, `dirty_count`, `untracked_count`.
- [ ] **Why this matters:** `dz git` shipped before this work; a shim regression breaks an existing tool.

## Section 1: Discovery and scoping (~5 min)

### 1.1 Namespaces derive rather than being hardcoded

- [ ] **Steps:** `dz dazzle-update` and read the `Ecosystem` header line.
- [ ] **Expected:** The namespace count matches the number of orgs you belong to plus one for your personal namespace. Compare against `gh api user/orgs --jq ".[].login"`.
- [ ] **Check:** A namespace you joined recently appears without editing any config.

### 1.2 `--scope` narrows to one namespace

- [ ] **Steps:** `dz dazzle-update --scope <one of your orgs>`
- [ ] **Expected:** `NOT CLONED` lists only repos from that namespace.

### 1.3 `--root` accepts an explicit directory

- [ ] **Steps:** `dz dazzle-update --root <a dir with 2-3 repos>`
- [ ] **Expected:** `cloned here` in the header reflects only that directory.
- [ ] **Known gap:** A **misspelled** `--root` produces a valid-looking empty report rather than an error. Confirm this still happens and note it -- it is a known rough edge, not a new bug.

### 1.4 Exclusions are stated, not silent

- [ ] **Steps:** `dz dazzle-update --only excluded`
- [ ] **Expected:** An `EXCLUDED BY POLICY` section naming each excluded path with a reason. Nothing is dropped without appearing here.

## Section 2: Terminal rendering -- Windows-sensitive (~5 min)

Run in a real console. These cannot be verified from a pipe or an IDE.

### 2.1 Colour in cmd.exe and PowerShell

- [ ] **Steps:** Run `dz dazzle-update --cached` in each.
- [ ] **Expected:** Colour renders. No literal `←[` or `\033[` sequences anywhere.

### 2.2 Colour auto-disables when piped

- [ ] **Steps** (pick your shell):

  **cmd.exe**: `dz dazzle-update --cached | findstr BEHIND`

  **PowerShell**: `dz dazzle-update --cached | Select-String BEHIND`

  **POSIX**: `dz dazzle-update --cached | grep BEHIND`
- [ ] **Expected:** No escape sequences in the piped text.

### 2.3 `--color always` forces colour through a pipe; `never` suppresses it

- [ ] **Steps:** Repeat 2.2 with `--color always`, then `--color never`.
- [ ] **Expected:** `always` shows escape sequences even piped; `never` shows none even in a terminal.

### 2.4 `NO_COLOR` is honoured

- [ ] **Steps:**

  **cmd.exe**: `set NO_COLOR=1` then `dz dazzle-update --cached`

  **PowerShell**: `$env:NO_COLOR = "1"` then `dz dazzle-update --cached`

  **POSIX**: `NO_COLOR=1 dz dazzle-update --cached`
- [ ] **Expected:** No colour, despite a real terminal.
- [ ] **Reset:** `set NO_COLOR=` / `Remove-Item Env:\NO_COLOR` / `unset NO_COLOR`

### 2.5 No mojibake and no misaligned columns

- [ ] **Steps:** Read a report with long repo names in a narrow (80-col) window.
- [ ] **Expected:** Pure ASCII throughout -- no `â€"`, no boxes. Names longer than 38 chars end in `~`. The detail column starts at the same offset on every row *including coloured ones* (colour is applied after padding; if a coloured row is shifted, that is a real bug).

## Section 3: Progress display -- needs a real TTY (~3 min)

### 3.1 Progress appears and clears

- [ ] **Steps:** Run a fresh scan (delete the cache first) and watch.
- [ ] **Expected:** A single updating line showing `scanning` / `fetching N/M` / `reading N/M` with repo names. It disappears before the report prints, leaving no residue.

### 3.2 Progress does not contaminate stdout

- [ ] **Steps:** Redirect stdout only: `dz dazzle-update > out.txt` (all shells), then view `out.txt`.
- [ ] **Expected:** Progress appeared on screen during the run but does NOT appear in `out.txt`.

### 3.3 `--no-progress` and `-v`

- [ ] **Steps:** `dz dazzle-update --no-progress`, then `dz dazzle-update -v`
- [ ] **Expected:** `--no-progress` shows none. `-v` prints one line per repo instead of an updating line.

## Section 4: Network behaviour (~10 min)

### 4.1 Parallel fetch completes in reasonable time

- [ ] **Steps:** Time a fresh scan over your real layout.
- [ ] **Expected:** Roughly 1-2 minutes for ~150 repos. Not 10+ minutes, which would indicate fetches serialised.

### 4.2 An unreachable remote does not hang the sweep

- [ ] **Steps:** Add a bogus remote to a throwaway repo, then scan with `--fetch-timeout 5`.
- [ ] **Expected:** The run completes. A warning reports N repos could not be fetched and that their behind-counts may be stale.

### 4.3 `gh` unauthenticated is reported, not hidden

- [ ] **Steps:** In a shell where `gh` is not authenticated (or temporarily unset `GH_TOKEN`), run `dz dazzle-update`.
- [ ] **Expected:** The `Sources` line states namespace listing was skipped and why. It does NOT silently produce a shorter report.
- [ ] **Why this matters:** An unauthenticated `gh` hides private repos. Silence here means an inventory that looks complete and is not.

### 4.4 `--published` queries PyPI

- [ ] **Steps:** `dz dazzle-update --published`
- [ ] **Expected:** The `published` field on the Sources line reports how many resolved. Packages not on PyPI are not errors. A `BEHIND PUBLISHED` section appears only if something is genuinely behind.

### 4.5 Offline degrades rather than crashing

- [ ] **Steps:** Disconnect the network, run `dz dazzle-update --no-fetch`.
- [ ] **Expected:** A report using local data only, with warnings naming each unavailable source.

## Section 5: Filtering, ordering, sorting (~5 min)

### 5.1 `--list-kinds` documents the vocabulary

- [ ] **Steps:** `dz dazzle-update --list-kinds`
- [ ] **Expected:** Every finding kind with its aliases.

### 5.2 `--only` and `--skip`

- [ ] **Steps:** `--only dirty`; then `--only behind --only push`; then `--skip dirty --skip missing`
- [ ] **Expected:** Exactly the requested sections. The `Summary` line still reports full counts (filtering affects display, not the scan).

### 5.3 An unknown kind fails helpfully

- [ ] **Steps:** `dz dazzle-update --only bogus-kind`
- [ ] **Expected:** Exit code 2 and a message pointing at `--list-kinds`. Not a stack trace, and not a silent full report.

### 5.4 Sorting

- [ ] **Steps:** `--sort newest` (default), `--sort oldest`, `--sort name`
- [ ] **Expected:** Row order within each section changes accordingly. Newest-first should put recently-touched repos at the top.

### 5.5 `--all` reveals clean repos

- [ ] **Steps:** `dz dazzle-update --all --only clean`
- [ ] **Expected:** A `CLEAN` section listing scanned repos with nothing to do. Pick a repo you know is clean and confirm it appears -- this is how you tell "scanned and fine" from "never scanned."

## Section 6: Configuration (~5 min)

### 6.1 `--init-config` writes a usable template

- [ ] **Steps:** `dz dazzle-update --init-config --config "%DU_TEST%\cfg2.json"` (adjust per shell)
- [ ] **Expected:** A valid JSON file with roots, namespaces, exclude/include, order, sort, fetch, cache keys.
- [ ] **Known gap:** Using that template immediately produces a warning about an unknown `_comment` key. Confirm and note -- known rough edge.

### 6.2 Discovery precedence

- [ ] **Steps:** Create `.dazzle-update.json` in the current directory with `{"sort": "name"}`. Run without `--config`, then with `--config` pointing elsewhere.
- [ ] **Expected:** The `Sources` line names which config was used. `--config` wins over the project-local file.

### 6.3 Malformed config is reported, not swallowed

- [ ] **Steps:** Write `{not json` to a config file and run with `--config` pointing at it.
- [ ] **Expected:** A clear parse error with location; the run continues on defaults. It must not crash and must not silently ignore the file.

### 6.4 `order` is partial, not a filter

- [ ] **Steps:** Config with `{"order": ["dirty"]}`. Run.
- [ ] **Expected:** `DIRTY` appears first, and **every other section still appears** after it. If naming one kind hides the rest, that is a serious bug -- a config would then quietly stop reporting unpushed work.

### 6.5 `include` beats `exclude`

- [ ] **Steps:** Config with a broad `exclude` pattern and an `include` naming one path inside it.
- [ ] **Expected:** That path is scanned; its siblings remain excluded.

## Section 7: Caching (~5 min)

### 7.1 Replay is fast and states its age

- [ ] **Steps:** Fresh scan, then `dz dazzle-update --cached`.
- [ ] **Expected:** Returns in seconds. A warning reads `REPLAYED from cache, N old -- remote state may have changed since`.
- [ ] **Why this matters:** A cached answer presented as current is the exact failure this tool exists to catch.

### 7.2 `--max-age` refuses stale caches

- [ ] **Steps:** Wait a minute after a scan, then `dz dazzle-update --cached --max-age 5`.
- [ ] **Expected:** Refusal naming the age and the limit, telling you to run fresh. Exit code 2.

### 7.3 Replay reflects current display settings

- [ ] **Steps:** `--cached --only dirty`, then `--cached --sort name`.
- [ ] **Expected:** Both honour the new flags. The cache stores observations, not a frozen rendering.

### 7.4 Missing cache is handled

- [ ] **Steps:** Delete the cache, then `dz dazzle-update --cached`.
- [ ] **Expected:** A clear "no cached scan found" message, not a traceback.

## Section 8: Supply-chain safety -- the #106 class (~8 min)

**Read this section even if you skip the rest.** A false "update available" here does not merely mislead: acting on it installs a stranger's package. It happened on 2026-07-30 -- our `preserve` was renamed to `dazzle-preserve`, a stale install kept the old name, PyPI `preserve` now belongs to an unrelated project, and following the recommendation installed it over our console entry point.

The rule the tool now follows: **a repo's PyPI identity comes from the repo's own metadata, never from the name its stale install happens to carry.**

### 8.1 A renamed dist is reported, and blocks comparison

- [ ] **Steps:**
  1. Find a repo whose declared name differs from its installed name. Check the declaration with `python -c "import sys;sys.path.insert(0,r'<dazzlecmd>/src/dazzlecmd/projects/dazzletools');from _repo_common.discovery import read_declared_dist_name;print(read_declared_dist_name(r'<repo path>'))"`, and the install with `pip list | findstr <name>` (or `grep`).
  2. Run `dz dazzle-update --published --only renamed`.
- [ ] **Expected:** A `RENAMED DIST` row naming BOTH names and where the declared one came from. That repo must NOT appear under `BEHIND PUBLISHED` at all.
- [ ] **If it appears in both, stop and report it** -- that is the exact chain from #106.

### 8.2 A foreign PyPI project is flagged, never recommended

- [ ] **Steps:** `dz dazzle-update --published --only collision`
- [ ] **Expected:** Any package whose PyPI project URLs do not point at one of your namespaces appears under `PYPI NAME COLLISION?` with the URL shown and "do NOT install". A known live example on this machine is `dazzle-opentimestamps-client`, which is a fork of an upstream project and resolves to `github.com/opentimestamps/...`.
- [ ] **Check:** None of those packages also appear under `BEHIND PUBLISHED`.

### 8.3 `--fix` refuses across a name mismatch

- [ ] **Steps:** `dz dazzle-update --published --fix --dry-run`
- [ ] **Expected:** Any renamed or collision-flagged package appears ONLY in the `REFUSED` block, with a reason naming both names and suggesting uninstall-old then install-new. It must never appear as a `[dry-run] ... pip install` line.
- [ ] **Why this matters:** This is the last gate before the tool would execute the wrong install.

### 8.4 Genuine upgrades are still reported

The safety bias is deliberate -- a missed upgrade costs less than a foreign install -- but it must not silence everything.

- [ ] **Steps:** Find a package whose install genuinely trails PyPI and whose names match. Run `dz dazzle-update --published --only published`.
- [ ] **Expected:** It IS reported under `BEHIND PUBLISHED`.
- [ ] **If nothing is ever reported here**, the ownership check may be over-refusing; note it.

## Section 9: Regressions -- these must NOT reproduce

Everything here was a real bug at some point. If any of it comes back, it is a regression.

### 9.1 Multi-checkout attribution (fixed in 0.12.7)

Only applicable if you have a repo checked out as several worktrees or clones.

- [ ] **Steps:**
  1. Identify such a repo (`dz git composition` lists worktrees).
  2. Note each checkout's real branch and dirty state via `git -C <path> status -sb`.
  3. Note which one pip installed: `pip list | findstr <name>` (or `grep`).
  4. Find that repo in the report, and run `dz dazzle-update --fix --dry-run`.
- [ ] **Expected:** The row names the checkout it describes (e.g. `github of 4`). The repo-scoped finding `BEHIND UPSTREAM` reflects the **pip-installed** checkout. Checkout-scoped findings (`NEEDS PUSH`, `NO UPSTREAM`, `DIRTY`) name the checkout that triggered them, which may be a different one.
- [ ] **Critical:** the `--fix --dry-run` action for that repo must target the **pip-installed** path. If it targets a feature-branch worktree, stop -- that is the regression, and running `--fix` for real would merge unrelated material into in-progress work.
- [ ] **Also:** if several checkouts tie (two tracking checkouts both on `main`, neither installed), `--fix` must REFUSE rather than pick one.

### 9.2 Fixed since first draft -- these should NOT reproduce

Earlier drafts of this checklist asked testers to confirm three bugs that have since been fixed. If any of these DO reproduce, that is a regression:

- [ ] **`clean_count` footer**: `N repos clean and current.` must EQUAL the row count of the `CLEAN` section (`--all --only clean`). It previously printed a lower number, often `0`.
- [ ] **Unparseable versions**: a package whose installed version cannot be parsed (e.g. a `v`-prefixed tag) must NOT be reported as stale purely from formatting.
- [ ] **`local_only_branches`**: a branch listed in that config key must never appear under `NO UPSTREAM` or `NEEDS PUSH`. Test with a config containing `{"local_only_branches": ["dev-L6"]}`.

## Section 10: Edge cases (~5 min)

### 10.1 Empty directory

- [ ] **Steps:** `--root` at an empty directory.
- [ ] **Expected:** `0 cloned here`, exit 0, no crash.

### 10.2 Repo with no commits

- [ ] **Steps:** `git init` a fresh directory inside your test root, then scan.
- [ ] **Expected:** Handled without crashing; appears under `NO UPSTREAM`.

### 10.3 Bare repo

- [ ] **Steps:** `git init --bare` inside your test root, then scan.
- [ ] **Expected (known gap):** The bare repo is **not discovered at all** and produces no warning. Confirm and note -- it is a documented limitation of discovery in this version.

### 10.4 Detached HEAD

- [ ] **Steps:** In a throwaway repo, `git checkout --detach HEAD`, then scan.
- [ ] **Expected:** No crash; the repo appears with no branch name rather than a bogus one.

## What the automated tests DON'T cover

- **Real terminal colour**: ANSI VT enablement on Windows consoles cannot be verified through a pipe, which is what a test harness is.
- **Progress on a TTY**: the updating single line and its cleanup only exist when stderr is a terminal.
- **Live network**: parallel fetch timing, real timeouts, an actually-unauthenticated `gh`, PyPI reachability.
- **Real `--fix` execution**: only dry-run is exercised anywhere, by anyone, so far.
- **Live PyPI ownership data**: the ownership check is tested against fixture payloads. Whether real projects declare usable `project_urls` -- and how often the answer is legitimately "unknown" -- can only be seen against the live index.
- **Codepage behaviour**: mojibake on cp437/cp1252 consoles.
- **Column alignment with colour applied**: padding-before-colouring is asserted in code but only visible to an eye.
- **Performance feel**: whether a ~90-second scan feels acceptable, and whether progress makes the wait tolerable.
- **Cross-platform**: everything here was developed on Windows; macOS and Linux paths are untried.
- **Error message quality**: whether refusal reasons actually tell you what to do next.

## Reporting issues found

1. Note the section and step number.
2. Capture the exact command, full output, and your shell.
3. For rendering issues, note the terminal (cmd.exe, PowerShell, Windows Terminal, VS Code) and codepage (`chcp` on Windows).
4. File an issue referencing this checklist and version 0.12.7-alpha.

## Cleanup

Remove the isolated test state:

| Shell | Command |
|---|---|
| cmd.exe | `rmdir /s /q "%DU_TEST%"` |
| PowerShell | `Remove-Item -Recurse -Force $env:DU_TEST` |
| POSIX | `rm -rf "$DU_TEST"` |
