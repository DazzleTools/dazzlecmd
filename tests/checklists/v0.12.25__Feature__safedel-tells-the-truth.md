# Human Test Checklist: safedel tells the truth

**Target version:** dazzlecmd 0.12.25-alpha with dazzlecmd-lib 0.10.37-alpha
**Ships with commit:** `v0.12.25 fix(safedel): refuse when nobody can answer; --yes is the gate; graded exit codes and a last-line verdict`
**Companion automated tests:** 125 new tests -- dazzlecmd-lib `tests/test_core_safedel_truth.py` (92); dazzlecmd `src/dazzlecmd/projects/core/safedel/tests/test_cli_truth.py` (33). Each asserted behaviour was reverted on a scratch copy of the source and shown to turn a test red (61 reversions).

## What this is

On 2026-11-17 `dz safedel <path>` was run by an agent without `--yes`. It prompted, read end-of-file, printed "Aborted." and **exited 0**; the command line that called it carried on as if the delete had happened, and deleted real data. This release changes what the command does when nobody can answer, makes `--yes` the one gate, makes the preview the plan the real run performs, and makes the last line of output and the exit code tell the truth. The automated tests cover the logic with the console, the store and the copy settings injected. This checklist is what a person runs to see it on a real machine: real consoles, real prompts, real links, and the wording of the messages.

## Prerequisites

1. **The right engine.** The command needs dazzlecmd-lib 0.10.37 or later. Check which copy `dz` imports:

   ```
   python -c "import dazzlecmd_lib; print(dazzlecmd_lib.__version__, dazzlecmd_lib.__file__)"
   ```

   If it is older, every `dz safedel` call prints `[safedel: dazzlecmd-lib ... is older than this safedel command needs ...; running the previous command ...]` and this checklist does not apply, except Section 14, which checks exactly that notice.

2. **One scratch folder, and nothing outside it.** Every step works inside a folder you create under your temp directory. Never point a step at a real project or at your home folder.

   **cmd.exe**:
   ```cmd
   mkdir %TEMP%\safedel-check
   cd /d %TEMP%\safedel-check
   ```

   **PowerShell**:
   ```powershell
   New-Item -ItemType Directory -Force "$env:TEMP\safedel-check" | Out-Null
   Set-Location "$env:TEMP\safedel-check"
   ```

   **POSIX / Git Bash**:
   ```bash
   mkdir -p "${TMPDIR:-/tmp}/safedel-check" && cd "${TMPDIR:-/tmp}/safedel-check"
   ```

3. **This checklist writes to your real trash store, and says where.** A delete that succeeds moves the scratch file into the real trash store for that drive (for example `C:\Users\<you>\.safedel-trash`, or `~/.safedel/trash`). That is the point of the tool, and the items are worthless scratch files -- but the batches are real. Each successful delete prints `To recover:  dz safedel recover <batch-name>`: **note each batch name** as you go (there is a list to fill in under Cleanup). Removing those batches afterwards is your choice, made by you at a console with `dz safedel clean`; an agent running this checklist must not run `clean`.

4. **Settings used below.** Unless a step says otherwise, turn copy-first off so the output is the same on every machine, and reset it when a section is done:

   | | cmd.exe | PowerShell | POSIX |
   |---|---|---|---|
   | set | `set SAFEDEL_COPY_FIRST=off` | `$env:SAFEDEL_COPY_FIRST = "off"` | `export SAFEDEL_COPY_FIRST=off` |
   | unset | `set SAFEDEL_COPY_FIRST=` | `Remove-Item Env:\SAFEDEL_COPY_FIRST` | `unset SAFEDEL_COPY_FIRST` |

5. **Making a scratch file** (used throughout as "make `victim.txt`"):

   | cmd.exe | PowerShell | POSIX |
   |---|---|---|
   | `echo scratch> victim.txt` | `Set-Content victim.txt scratch` | `echo scratch > victim.txt` |

6. **"Nobody at the keyboard".** Several steps run the command with its input closed, the way a script or an agent runs it:

   | cmd.exe | PowerShell | POSIX |
   |---|---|---|
   | `dz safedel victim.txt < NUL` | `$null \| dz safedel victim.txt` | `dz safedel victim.txt < /dev/null` |

7. **Reading the exit code** right after a command:

   | cmd.exe | PowerShell | POSIX |
   |---|---|---|
   | `echo %ERRORLEVEL%` | `$LASTEXITCODE` | `echo $?` |

**Reset between sections:** anything left in the scratch folder can simply stay; each section makes the files it needs under new names.

## High-Value Verification (~5 minutes)

**If you only have 5 minutes**, run these five. If any fails, the release is broken.

### HV.1 -- The 2026-11-17 case now refuses, with a non-zero code

Validates: nobody at the keyboard and no `--yes` means nothing moves and the caller is told.

- [ ] **Steps:** make `victim.txt`; run the command with its input closed (Prerequisite 6); read the exit code.
- [ ] **Expected:** the last line of output is exactly `safedel: REFUSED not interactive and --yes was not given`; the exit code is **3**; a line above it says `Nothing was moved. Re-run with --yes to delete.`
- [ ] **Check:** `victim.txt` is still there with its content.
- [ ] **Why this matters:** on 2026-11-17 this exact call printed "Aborted." and returned 0, and the rest of the command line ran.

### HV.2 -- A chained command stops, and `tail` shows the truth

Validates: the two habits that hid the abort -- chaining and trimming output -- no longer hide it.

- [ ] **Steps** (POSIX / Git Bash; cmd.exe and PowerShell forms follow):

  ```bash
  dz safedel victim.txt < /dev/null && echo CONTINUED
  dz safedel victim.txt < /dev/null 2>&1 | tail -1
  ```

  **cmd.exe**: `dz safedel victim.txt < NUL && echo CONTINUED`
  **PowerShell 7**: `$null | dz safedel victim.txt && Write-Host CONTINUED`

- [ ] **Expected:** `CONTINUED` is **not** printed; the `tail -1` form prints `safedel: REFUSED not interactive and --yes was not given`.
- [ ] **Why this matters:** an honest exit code is what makes `&&` safe, and the verdict being last is what survives `| tail -1`.

### HV.3 -- `--yes` stages, names the batch, and the file comes back

- [ ] **Steps:**
  1. make `victim.txt`
  2. `dz safedel --yes victim.txt`
  3. note the batch name from the line `To recover:  dz safedel recover <batch-name>`
  4. `dz safedel recover <batch-name>`
- [ ] **Expected:** step 2's last line is `safedel: STAGED 1`, exit code 0, and the report says `recover <batch-name>`, not `recover last`. Step 4 prints `Recovered: ...victim.txt` and exits 0.
- [ ] **Check:** after step 2 the file is gone; after step 4 it is back with the same content.
- [ ] **Why this matters:** the ordinary path must still work, and with two sessions on one machine "last" can be someone else's deletion.

### HV.4 -- At a real console it asks, and "no" is a refusal

**MANUAL: a person must type.** Run in a real terminal window, not through an agent or a script.

- [ ] **Steps:** make `victim.txt`; run `dz safedel victim.txt`; at `Proceed with deletion? [y/N]:` press Enter. Run it again and type `y`.
- [ ] **Expected:** the first run ends with `safedel: REFUSED declined at the prompt`, exit code 3, file intact. The second stages it (`safedel: STAGED 1`, exit 0).
- [ ] **Why this matters:** the prompt is the pause this tool exists to provide; declining must not look like success.

### HV.5 -- The folder a worktree's link points at is refused

Validates: the target-side guard for the incident's own shape. Windows shown; on POSIX use `ln -s` where the junction is made.

- [ ] **Steps** (PowerShell, from the scratch folder; every git command names its scratch path and commits unsigned):

  ```powershell
  $r = "$env:TEMP\safedel-check\hv5"
  git init -q "$r\proj"
  git -C "$r\proj" -c user.email=t@example.com -c user.name=tester -c commit.gpgsign=false commit -q --allow-empty -m init
  New-Item -ItemType Directory -Force "$r\proj\private" | Out-Null
  Set-Content "$r\proj\private\notes.md" notes
  git init -q "$r\proj\private"
  git -C "$r\proj" worktree add -q "$r\proj__wt" -b wt
  New-Item -ItemType Junction -Path "$r\proj__wt\private" -Target "$r\proj\private" | Out-Null
  dz safedel --yes "$r\proj\private"
  $LASTEXITCODE
  ```

- [ ] **Expected:** exit code **3**; the message names the link (`...proj__wt\private`) and says how to proceed: name the link itself to remove only the link, or pass `--yes delete-through-junction`.
- [ ] **Check:** `hv5\proj\private\notes.md` is still there.
- [ ] **Do not** run `git worktree remove` on this fixture, here or anywhere in this checklist: on git 2.52 for Windows it deletes through the junction. Leave the fixture for Cleanup.
- [ ] **Why this matters:** two real folders were emptied this way on 2026-11-17.

## Section 1: Refusing when nobody can answer

### 1.1 Each way of having no keyboard

- [ ] **Steps:** make `victim.txt`, then run each and read the exit code:

  | Form | cmd.exe | PowerShell | POSIX |
  |---|---|---|---|
  | input closed | `dz safedel victim.txt < NUL` | `$null \| dz safedel victim.txt` | `dz safedel victim.txt < /dev/null` |
  | input from a pipe | `echo y \| dz safedel victim.txt` | `"y" \| dz safedel victim.txt` | `echo y \| dz safedel victim.txt` |

- [ ] **Expected:** exit code 3 for both, file intact. A `y` arriving through a pipe is **not** consent: only a person at a console, or `--yes`, is.

### 1.2 The message is usable

- [ ] **Check:** reading only the last three lines, a newcomer can tell (a) nothing was moved, (b) why, and (c) what to type next.

## Section 2: The prompt (MANUAL)

Run each in a real window. Tick the terminals you have.

- [ ] Windows Terminal (PowerShell or cmd tab)
- [ ] the classic console window (`cmd.exe`)
- [ ] Git Bash (mintty) -- **the one most likely to be misread as "no keyboard"**
- [ ] an editor's integrated terminal (VS Code or similar)
- [ ] Linux or macOS terminal

For each:

- [ ] **Steps:** make `victim.txt`; `dz safedel victim.txt`.
- [ ] **Expected:** the plan is printed, then `Proceed with deletion? [y/N]:` and the cursor waits. If instead it refuses at once with `not interactive and --yes was not given`, that terminal was not recognised -- report it with the terminal's name and version (it fails toward refusing, so nothing is lost, but it is a defect).
- [ ] **Steps:** answer `n`; then run again and press Ctrl+C at the prompt.
- [ ] **Expected:** both end with `safedel: REFUSED declined at the prompt`, exit code 3, file intact.
- [ ] **Steps:** redirect output and run again: `dz safedel victim.txt > out.txt`.
- [ ] **Expected:** the question still appears on screen (it is written to the error stream), and the answer is honoured.

## Section 3: `--yes` and its scopes

### 3.1 `--yes` does not swallow the path after it

- [ ] **Steps:** make `victim.txt`; `dz safedel --yes victim.txt`.
- [ ] **Expected:** `safedel: STAGED 1`, exit 0. (Note the batch name.)

### 3.2 A mistyped scope is an error, not consent

- [ ] **Steps:** make `victim.txt`; `dz safedel --yes dangerous,typo victim.txt`.
- [ ] **Expected:** exit code **2**, a message listing the known scopes, file intact.

### 3.3 A file named like a scope

- [ ] **Steps:** make a file named `dangerous` (same commands as for `victim.txt`); `dz safedel --yes -- dangerous`.
- [ ] **Expected:** staged, exit 0. (Without `--`, `--yes dangerous` reads `dangerous` as the scope and then reports that no path was given.)

### 3.4 `--help` explains it

- [ ] **Steps:** `dz safedel --help` (with any path-less call the help is printed).
- [ ] **Check:** the scopes and the exit codes are listed, and the text is readable at 80 columns.

## Section 4: The preview is the plan

### 4.1 A folder

- [ ] **Steps:**

  **cmd.exe**:
  ```cmd
  mkdir tree\sub
  echo 1> tree\one.txt
  echo 22> tree\sub\two.txt
  echo h> tree\.hidden
  dz safedel --dry-run tree
  ```

  **PowerShell**:
  ```powershell
  New-Item -ItemType Directory -Force tree\sub | Out-Null
  Set-Content tree\one.txt 1; Set-Content tree\sub\two.txt 22; Set-Content tree\.hidden h
  dz safedel --dry-run tree
  ```

  **POSIX**:
  ```bash
  mkdir -p tree/sub && echo 1 > tree/one.txt && echo 22 > tree/sub/two.txt && echo h > tree/.hidden
  dz safedel --dry-run tree
  ```

- [ ] **Expected:** for `tree`: a `kind:` line (`regular_dir`), a `does:` line (`move into the trash`), a `holds:` line (`3 file(s), 1 folder(s)`, a size; on POSIX also `1 hidden`), then `trash store: <path>`. Last line `safedel: DRY-RUN 1 would be staged`, exit 0.
- [ ] **Check:** `tree` is untouched, and no new batch folder appeared in the trash store named on the `trash store:` line.

### 4.2 The real run shows the same plan first

- [ ] **Steps:** `dz safedel --yes tree`.
- [ ] **Expected:** the same `kind / does / holds / trash store` block, then the report, then `safedel: STAGED 1`. (Note the batch name.)

## Section 5: Two items with the same name

- [ ] **Steps:**

  **cmd.exe**: `mkdir a b` then `echo A> a\x.json` and `echo B> b\x.json`
  **PowerShell**: `New-Item -ItemType Directory -Force a,b | Out-Null; Set-Content a\x.json A; Set-Content b\x.json B`
  **POSIX**: `mkdir -p a b && echo A > a/x.json && echo B > b/x.json`

  then, in any shell: `dz safedel --yes a/x.json b/x.json` and read the exit code; then `dz safedel --dry-run a/x.json b/x.json`.
- [ ] **Expected (dazzlecmd-lib 0.10.37 or 0.10.38):** both runs exit **3** with `safedel: REFUSED two or more items share a name ...`, naming both paths and saying to delete them in separate calls.
- [ ] **Check:** both files are still in place with their own content, and no batch was created.
- [ ] **With dazzlecmd-lib 0.10.39 or later this section no longer applies:** the same call succeeds (`safedel: STAGED 2`), because each item gets its own place in the trash. Use `v0.12.28__Feature__safedel-same-names-side-by-side.md` instead.

## Section 6: Links

Windows steps use a junction; on POSIX use a symlink (`ln -s "$PWD/real" link`) and `delete-through-symlink`.

### 6.1 Naming the link removes only the link

- [ ] **Steps** (PowerShell):
  ```powershell
  New-Item -ItemType Directory -Force real | Out-Null; Set-Content real\keep.txt keep
  New-Item -ItemType Junction -Path link -Target (Resolve-Path real) | Out-Null
  dz safedel --yes link
  ```
- [ ] **Expected:** the plan says `does:  remove the link only; what it points at is not touched`; `safedel: STAGED 1`.
- [ ] **Check:** `link` is gone; `real\keep.txt` is still there.

### 6.2 Delete-through needs its scope, and the right one

- [ ] **Steps:** re-create the junction (`New-Item -ItemType Junction -Path link -Target (Resolve-Path real) | Out-Null`), then:
  1. `dz safedel --yes delete-through-symlink link`
  2. `dz safedel --yes delete-through-junction link`
- [ ] **Expected:** step 1 exits **3** and says the path is a junction and which scope to use; nothing moves. Step 2 prints two items in the plan (the folder `real`, "reached through the link", and the link) and ends `safedel: STAGED 2`.
- [ ] **Check:** after step 2 both `link` and `real` are gone, and the batch's `content\real\keep.txt` exists in the trash store. (Note the batch name.)

### 6.3 A scope with nothing to apply to

- [ ] **Steps:** make `victim.txt`; `dz safedel --yes delete-through-junction victim.txt`.
- [ ] **Expected:** exit 3, `no path is a junction or a junction's destination`; file intact.

## Section 7: Copy-first

- [ ] **Steps:** set `SAFEDEL_COPY_FIRST=always` (Prerequisite 4, with `always` in place of `off`); make `victim.txt`; `dz safedel --yes victim.txt`.
- [ ] **Expected:** the plan says `copy and verify (SHA-256), then move into the trash`; the report ends with a `Copy-first:` line naming `<batch>\copy-first`; `safedel: STAGED 1`.
- [ ] **Check:** in the batch folder, `content\victim.txt` and `copy-first\victim.txt` both exist with the same content.
- [ ] **Steps:** also set `SAFEDEL_COPY_FIRST_MAX=1k`; make a file larger than 1 KB (PowerShell: `Set-Content big.bin ("z" * 5000)`; POSIX: `head -c 5000 /dev/zero > big.bin`); `dz safedel --yes big.bin`.
- [ ] **Expected:** exit **3**; the message gives the size, the limit, and both ways forward: `--yes no-copy-first` and `--copy-first-max <size>`. File intact.
- [ ] **Steps:** `dz safedel --yes no-copy-first big.bin`.
- [ ] **Expected:** staged, exit 0, and no `copy-first` folder in that batch.
- [ ] **Reset:** unset both variables.

## Section 8: A path that does not exist

- [ ] **Steps:** make `victim.txt`; `dz safedel --yes victim.txt no-such-file.txt`; then `dz safedel --yes no-such-file.txt`.
- [ ] **Expected:** the first ends `safedel: PARTIAL staged 1, not staged 1`, exit code **4**, and the plan showed the missing path with `nothing -- this path does not exist`. The second ends `safedel: REFUSED nothing to delete ...`, exit code **3**.

## Section 9: `--json`

- [ ] **Steps:** make `victim.txt`; run `dz safedel --json victim.txt` with input closed; then `dz safedel --yes --json victim.txt`. Pipe each through `python -m json.tool`.
- [ ] **Expected:** both outputs are one valid JSON object with no text after it. The first has `"exit_code": 3` and a `verdict` starting `safedel: REFUSED`, and the file is intact. The second has `"exit_code": 0`, `"verdict": "safedel: STAGED 1"`, a `recover_command` naming the batch, and the process exit codes match.

## Section 10: Recovery cannot delete what it did not restore (automated only)

This behaviour is checked by `test_a_batch_without_a_readable_manifest_is_kept`, `test_a_folder_that_still_holds_content_is_kept` and `test_recovery_removes_by_exact_path_not_by_name` in dazzlecmd-lib, on temporary stores. **Do not reproduce it by hand**: it would mean damaging a manifest in your real trash store.

- [ ] Confirm those three tests are in the suite and pass.

## Section 11: `list` and `status` name the real store

- [ ] **Steps:** `dz safedel status`, then `dz safedel list`.
- [ ] **Expected:** the store shown is the one your batches actually went to (the `Trash store:` line from the delete reports), or, when more than one store holds batches, a `Trash stores (N):` list with each path.

## Section 12: Messages, read cold

- [ ] Give the output of HV.1, Section 5 and HV.5 to someone who has not seen this tool. Can they say what happened and what to do next, from the text alone?
- [ ] The same for an AI agent: paste one refusal into a fresh agent session and ask what it would run next. It should run the delete as its own command with `--yes` (or name the link), not reach for `rm`.

## Section 13: Cross-volume (if you have a second drive)

- [ ] **Steps:** make a scratch folder on a drive other than the one that holds your profile, with a file in it; `dz safedel --dry-run <that file>`.
- [ ] **Expected:** the plan warns that the trash store is on another volume and items are copied, not renamed, when no per-volume store is available there. Record what it says. **Known limit:** a folder staged across volumes that contains a junction has the junction's target copied into the trash (nothing is deleted by this); do not test that with a junction that points at real data.

## Section 14: An older engine

Only if you can arrange dazzlecmd 0.12.25 with dazzlecmd-lib 0.10.36 (for example a development checkout of dazzlecmd beside an installed older library).

- [ ] **Steps:** `dz safedel --dry-run victim.txt`.
- [ ] **Expected:** a first line on the error stream: `[safedel: dazzlecmd-lib <version> is older than this safedel command needs (0.10.37 or later); running the previous command. Its exit codes are not graded: pass --yes, and check the result by looking.]`, followed by the previous release's output. The command works; it does not fail with an import error.

## What the automated tests DON'T cover

- **Real consoles.** The tests inject "is there a console". Whether Windows Terminal, the classic console, mintty, an editor's terminal, tmux or an SSH session is recognised is only seen by running Section 2. An agent harness that hosts the shell on a pseudo-console would be read as "a person is here": the command would prompt and wait until the harness times out (a hang, not a loss).
- **Another program holding a file.** One test run in about 70 failed once and could not be reproduced; the suspicion, unconfirmed, is antivirus briefly holding a just-created file so the move failed. If a delete of a file you just created fails with "rename into trash failed", report it with the antivirus product.
- **Cross-volume staging** (Section 13) and the known limit described there.
- **Very large folders.** The plan walks a folder to count what it holds; nobody has timed it on a tree of hundreds of thousands of files.
- **Long paths, non-ASCII names, names with spaces and quotes**, and how the plan's lines wrap in a narrow terminal.
- **Whether the refusals read clearly** to a person and to an agent (Section 12). The tests check that the words are present, not that they help.
- **The copy-first default.** In `auto` mode a script or agent deleting more than 10 MB is refused until it names an override. Whether that pause is welcome or a nuisance in daily use is a judgement only use gives.
