# Human Test Checklist: `dz mode restore` — mode-swap reversibility

**Target version:** v0.9.13 (dazzlecmd) / 0.8.15 (dazzlecmd-lib)
**Ships with commit:** `dz mode restore` functional path (#37); foundation in v0.9.12 (`67c1ad2`)
**Companion automated tests:** `tests/test_mode_origins.py` (13: 8 origins data-layer + 5 cmd_restore round-trip/refusal); `tests/test_states.py` (EMBEDDED-reversible reclassification); `packages/dazzlecmd-lib/tests/test_core_safedel.py` (`recover_folder`).

## What this is

`dz mode switch <tool>` into dev mode destroys the prior on-disk form (an embedded directory or a submodule checkout) and replaces it with a symlink to your local dev repo. `dz mode restore <tool>` is the inverse — it re-materializes the prior form: EMBEDDED content is recovered from the safedel trash; a SUBMODULE is re-cloned. This checklist covers what the automated round-trip can't fully model: real junction/symlink creation on Windows, a real safedel trash round-trip, the dirty-dev warning, and the refusal-message clarity.

**SAFETY:** Only run the switch/restore steps against a **throwaway sandbox tool** you create for this test. NEVER run `dz mode switch`/`restore` against a real submodule or a tool whose dev repo holds uncommitted work you care about.

## Prerequisites

1. A checkout of dazzlecmd at the target version, installed editable.
2. A **sandbox aggregator** dir you can throw away (so `mode_local.json` and the embedded tool live in isolation). Example layout under a temp dir `SBX`:
   - `SBX/projects/core/demo/` containing a `demo.py` and a `.dazzlecmd.json` manifest (name=demo, namespace=core).
   - `SBX/devsrc/` — a separate "dev repo" dir with its own `demo.py`.
3. Run `dz` commands from `SBX` (so `project_root` resolves to the sandbox).

> If building a full sandbox manifest is too fiddly, the automated round-trip in `tests/test_mode_origins.py::test_embedded_dev_then_restore_round_trip` already exercises the mechanism headlessly; this checklist is the by-hand confirmation of the real-terminal feel.

## High-Value Verification (~5 minutes)

### HV.1 — EMBEDDED round-trip (the core mechanic)

- [ ] **Steps:**
  1. From `SBX`: `dz mode switch demo --path ./devsrc` (enter dev mode)
  2. Confirm `projects/core/demo` is now a junction/symlink to `devsrc`.
  3. `dz mode restore demo`
- [ ] **Expected:** after restore, `projects/core/demo` is a real directory again with the **original embedded** `demo.py` content (NOT the devsrc copy); the junction is gone.
- [ ] **Why this matters:** this is the whole feature — entering dev mode is recoverable.

### HV.2 — Origin recorded then cleared

- [ ] **Steps:** after the switch in HV.1 (before restore), open `SBX/mode_local.json`.
- [ ] **Expected:** an `origins` block with `"core:demo": {"prior_state": "embedded", "trash_folder": "<timestamp>", "original_path": "...", "switch_timestamp": "..."}`. After `dz mode restore demo`, the `core:demo` origin is **gone**.
- [ ] **Why this matters:** the record is the bridge between switch and restore; a stale record would mislead a later restore.

### HV.3 — Dirty-dev warning + dev repo untouched

- [ ] **Steps:** while in dev mode, edit `devsrc/demo.py` (uncommitted change). Run `dz mode restore demo`.
- [ ] **Expected:** output notes "your dev work in `<devsrc>` is untouched -- only the symlink here is removed"; after restore, `devsrc/demo.py` STILL has your edit.
- [ ] **Why this matters:** restore must never touch the dev repo's content.

### HV.4 — Refusal: no origin

- [ ] **Steps:** in a fresh sandbox (tool is plain EMBEDDED, never switched): `dz mode restore demo`
- [ ] **Expected:** `No restore origin recorded for 'core:demo'. Nothing to do.` Exit 0. Nothing changes.

### HV.5 — Refusal: not in dev mode

- [ ] **Steps:** switch to dev, restore (now embedded again), then `dz mode restore demo` once more.
- [ ] **Expected:** `Tool 'core:demo' is not in dev mode (current: EMBEDDED ...); restore not applicable.` Exit 0.

### HV.6 — `--dry-run`

- [ ] **Steps:** switch to dev, then `dz mode restore demo --dry-run`
- [ ] **Expected:** prints "Would remove the symlink ..." / "Would recover backup ..." and makes **no** change (still a symlink; origin still present).

## Section 1: Edge cases

### 1.1 Missing trash backup

- [ ] **Steps:** switch to dev, then manually `dz safedel clean` is FORBIDDEN — instead, hand-edit `mode_local.json` to set `origins.core:demo.trash_folder` to a bogus timestamp. Run `dz mode restore demo`.
- [ ] **Expected:** error "backup '<...>' not found in the trash store ... Cannot restore automatically", exit 1, and the symlink is **left in place** (the pre-check fired before removing anything — no half-swap).

### 1.2 SUBMODULE origin (only if you have a sandbox submodule)

- [ ] **Steps:** for a tool that was a submodule, switch to dev then `dz mode restore`.
- [ ] **Expected:** restore re-clones via `git submodule update --init` (no trash recovery); prints "Restored 'core:<tool>' to SUBMODULE."
- [ ] **Skip if** you don't have a safe sandbox submodule — do NOT test against a real one.

## What the automated tests DON'T cover

- Real Windows junction vs symlink rendering and the `is_linked_project` detection on your actual filesystem.
- The dirty-dev warning wording in a real terminal.
- A real submodule re-clone (the automated suite never touches real remotes).
- Refusal-message clarity as a human reads it.

## Cleanup

- Delete the throwaway sandbox dir `SBX` entirely (use `dz safedel SBX` for recoverable removal).
- No real config is touched if you ran everything inside `SBX`.
