## What this is

This checklist verifies the **verb × level read+mutate+decompose arc** end-to-end across the three repos (dazzle-lib → dazzlecmd-lib → dazzlecmd) as a human running real commands in a real terminal. The arc was large and touched dispatch, rendering, the read surface, and the verb registry — the byte-gate proves output parity for 10 captured cases, but a person needs to eyeball the rest (color, alignment, shell rendering, fail-loud messages, the `dz kit -h` menu, and that the three editable installs actually resolve each other). Run it before treating the arc as shippable.

## Prerequisites

1. **Windows** (primary target) — codepage 437/1252 rendering is exactly what mocks miss. A POSIX run is a bonus.
2. **The three repos installed editable** so the working tree is live:
   - `pip install -e C:/code/dazzle-lib --no-deps`
   - `pip install -e C:/code/dazzlecmd-lib --no-deps`
   - `pip install -e C:/code/dazzlecmd/github --no-deps`
   - Classic break: a stale PyPI `dazzle-lib` shadowing the editable one → everything misbehaves. Verify §1.0 first.
3. **Config isolation** — point dz at a throwaway config so your real dotfiles aren't touched:

  **cmd.exe**: `set DAZZLECMD_CONFIG=%TEMP%\dz_arc_test.json`
  **PowerShell**: `$env:DAZZLECMD_CONFIG = "$env:TEMP\dz_arc_test.json"`
  **POSIX**: `export DAZZLECMD_CONFIG=/tmp/dz_arc_test.json`

4. **Reset between destructive sections**: `dz kit reset --yes` (re-reads kit state from manifests). Mutations in §3 below change kit activation — reset after.

If you only have 5 minutes, run these six. If any fail, the arc is broken and the detail sections won't save you.

### HV.1 — the three repos resolve each other (no stale-PyPI shadow)

Validates: the editable install chain (the whole arc is invisible if a stale lib shadows it).

- [ ] **Steps** (cross-shell safe, `python` only):

- [ ] **Expected:** `dazzle_lib.__file__` points at `C:\code\dazzle-lib\...` (NOT site-packages); `dazzlecmd_lib.__version__` is `0.9.13`.

### HV.2 — `dz info <tool>` is byte-stable (the read collapse didn't regress the tool path)

- [ ] **Steps:** `dz info core:find`
- [ ] **Expected:** the tool identity card + a `Current state:` section; the card layout is unchanged from 0.10.x (the tool path delegates to the lib `render_info` verbatim — this is a byte-gate golden).
- [ ] **Why this matters:** SD-A routed reads through `interrogate()`; the tool path must stay byte-identical.

### HV.3 — `dz info <kit>` / `dz info <aggregator>` are level-aware

- [ ] **Steps:** `dz info core` (a kit) then `dz info dazzletools` (or your aggregator name)
- [ ] **Expected:** the KIT card (identity + `Current state:` axis rows) and the AGGREGATOR card (identity) — different field-sets, each level-appropriate, `(none)` for absent fields.
- [ ] **Why this matters:** the headline "every read, level-aware, one surface."

### HV.4 — `dz list` / `dz tree` look exactly as before (S3 coexist)

- [ ] **Steps:** `dz list` then `dz list --show all` then `dz tree`
- [ ] **Expected:** sectioned-by-kit list with `[*]`/`[+]`/`[lib]` markers + footer legend; the tree with kit→tool structure. Pixel-identical to 0.10.x (renderers untouched — byte-gate goldens).
- [ ] **Why this matters:** the list/tree fold settled S3-coexist precisely so these wouldn't change; confirm they didn't.

### HV.5 — bare mutate verbs dispatch (B4-mutate)

- [ ] **Steps:** `dz disable wtf` then `dz list` (confirm wtf's tools vanish) then `dz enable wtf` then `dz list`
- [ ] **Expected:** `dz disable wtf` ≡ `dz kit disable wtf`; the tool list shrinks/grows accordingly. `dz attach`/`dz detach` similarly route to the kit.
- [ ] **Why this matters:** the cross-level bare-verb hoist; mutations must hit the right kit.
- [ ] **Reset after:** `dz kit reset --yes`

### HV.6 — `dz kit -h` menu is intact (B5 derived from the registry)

- [ ] **Steps:** `dz kit -h`
- [ ] **Expected:** the lifecycle verbs (enable/disable, attach/detach, add/remove) grouped by axis, byte-identical to before — but now generated from `VERB_AXES`, not a hand-list.
- [ ] **Why this matters:** B5 single-sourced the menu; a regression here means the derivation drifted.

## Section 2: The read surface (SD-A / interrogate)

### 2.1 `dz info` at every level + `--json`
- [ ] `dz info core:find` (tool) — identity + state; `--json` mirrors the card with a `state` object.
- [ ] `dz info core` (kit) — kit identity + `Current state:` axis rows.
- [ ] `dz info dazzletools` (aggregator) — aggregator identity.
- [ ] `dz info core:find --as tool` — the `--as` pin resolves the level explicitly.
- [ ] Absent fields show `(none)`, not omitted.

### 2.2 State section is registry-driven
- [ ] The `Current state:` rows correspond to the `VERB_AXES` (activation/loading/membership). Disabling a kit (`dz disable wtf`) then `dz info wtf` should reflect the changed activation rung. Reset after.

### 2.3 `dz kit status` (current behavior — NOTE: per the Gate-E decision this per-entity reduction is slated for removal in a follow-up slice)
- [ ] `dz kit status` (bare) — active-kits overview.
- [ ] `dz kit status core` — the per-axis state card. *(Verify it still works today; flag if you find it redundant with `dz info core` — that redundancy is exactly why it's being reduced to info-only.)*

## Section 3: Mutate verbs (B4-mutate)

### 3.1 Bare cross-level verbs route to the kit
- [ ] `dz enable <kit>` / `dz disable <kit>` / `dz attach <kit>` / `dz detach <kit>` each ≡ the `dz kit <verb> <kit>` form.
- [ ] Reset: `dz kit reset --yes`.

### 3.2 Fail-loud at the wrong level
- [ ] `dz enable <a-tool-name>` (a tool, not a kit) → a clear error (activation applies at kit), NOT a silent no-op or a stack trace.
- [ ] An ambiguous bare name (if you can construct a tool and kit sharing a name) → for a MUTATE, fails loud (`AmbiguousLevelError`-style message); for a READ (`dz info <name>`), auto-picks tool>kit>aggregator + notifies.

### 3.3 favorite/unfavorite are context-bound (NOT hoisted — by design)
- [ ] `dz favorite` requires `<short> <fqcn>` (a binding), not a bare kit target. `dz favorite wtf` alone should NOT silently mutate — favorite/unfavorite are deliberately not bare-hoisted.

## Section 4: Decomposition (SD-E / B5) — visual + structural

### 4.1 `dz kit -h` and `dz -h`
- [ ] `dz kit -h` — axis-grouped lifecycle verbs, intact.
- [ ] `dz -h` — top-level help renders; no missing/duplicated commands from the cli.py split.

### 4.2 Rendering parity under color + pipe
- [ ] `dz list` in a color terminal — `[*]` bold-red, `[+]` cyan, `[lib]` green; columns aligned (ANSI codes don't break width math).
- [ ] `dz list | cat` (POSIX) / `dz list | more` (Windows) — color auto-OFF when piped, columns still aligned, no raw escape codes.
