# Human Test Checklist: path-query disclosure, and a pull guard that measures

**Target version:** 0.12.17-alpha
**Ships with commit:** `v0.12.17 fix(dazzle-update): stop answering about somewhere else, and decide pulls by what collides rather than by what is merely present`
**Companion automated tests:** 313 in `src/dazzlecmd/projects/dazzletools/dazzle-update/tests/` — `test_pull_collisions.py` (12, real git), `test_apply_fixes.py` (34), `test_query.py` (90), `test_churn.py` (28). Full suite 2435.

## What this is

Two fixes to `dz dazzle-update`'s write path, both from the same defect class: the tool stating something it had not measured. The first stops a path query from describing a *different* directory's state as though it were yours. The second replaces "is the tree dirty?" — a proxy — with the question git itself answers: does the incoming change touch uncommitted work?

Run this if you use `--fix`, keep worktrees, or have repositories with untracked files sitting around (editor settings, scratch notes, build output).

## Prerequisites

1. dazzlecmd 0.12.17-alpha installed (`dz --version`)
2. A configured `dazzle-update` (`dz dazzle-update --help` runs; a config exists)
3. **A scratch clone you do not mind modifying.** Several steps below run a real `git pull`. Do NOT use a repository holding work you care about.

Set one up (all shells — `dz` and `git` only):

```
git clone https://github.com/DazzleTools/dazzlesum C:\temp\ck-scratch
```

Then roll it back a commit so it is genuinely behind:

```
git -C C:\temp\ck-scratch reset --hard HEAD~3
```

**Reset between sections**: `git -C C:\temp\ck-scratch reset --hard HEAD` then delete any untracked files the step created.

**Cleanup at the end**: see the final section.

## High-Value Verification (~5 minutes)

### HV.1 — An untracked file no longer blocks an unrelated pull

Validates: the reported bug. This is the whole reason 0.12.17 exists.

- [ ] **Steps:**
  1. `cd C:\temp\ck-scratch`
  2. Create an untracked file upstream knows nothing about:
     - **cmd.exe**: `mkdir .vscode & echo {} > .vscode\settings.json`
     - **PowerShell**: `New-Item -ItemType Directory -Force .vscode; '{}' | Out-File .vscode\settings.json`
     - **POSIX**: `mkdir -p .vscode && echo '{}' > .vscode/settings.json`
  3. `dz dazzle-update . --fix --dry-run`
- [ ] **Expected:** a planned `git -C ... pull --ff-only`. **NOT** `BLOCKED ... dirty tree`.
- [ ] **Why this matters:** in 0.12.16 this printed "dirty tree" on a tree with zero dirty files, and refused a fast-forward that would have applied cleanly.

### HV.2 — A real collision still refuses, and names the file

Validates: the guard did not simply get more permissive.

- [ ] **Steps:**
  1. Reset: `git -C C:\temp\ck-scratch reset --hard HEAD`
  2. Find a file the incoming commits modify: `git -C C:\temp\ck-scratch diff --name-only HEAD..@{u}`
  3. Edit one of those files locally (any change).
  4. `dz dazzle-update . --fix --dry-run`
- [ ] **Expected:** `BLOCKED` with `would overwrite uncommitted work: <that filename>`. The filename must be **the actual path**, not a lowercased version of it.
- [ ] **Why this matters:** the refusal has to name what is in the way. "dirty tree" sent you to `git status` to guess.

### HV.3 — Standing somewhere the scan cannot see says so

Validates: the disclosure half. Needs a worktree whose gitdir git cannot follow — skip if you have none.

- [ ] **Steps:** from such a directory, run `dz dazzle-update .`
- [ ] **Expected:** a `NOTE` above the card: `<dir> is NOT among the checkouts below -- it is invisible to the scan, so what follows describes the owning repository, not this directory`
- [ ] **Why this matters:** the card lists the owner's checkouts. Without the note, you read a sibling's branch and counts as yours.

### HV.4 — `--fix` refuses to act from such a directory

- [ ] **Steps:** same directory, `dz dazzle-update . --fix`
- [ ] **Expected:** `refusing to --fix from here: this directory is not one of the repository's known checkouts`, naming where you are, and pointing at naming the repository explicitly.
- [ ] **Why this matters:** it would otherwise pull a *different* checkout and report it as this one's.

### HV.5 — Naming the repository still works from anywhere

- [ ] **Steps:** from any directory, `dz dazzle-update dazzlesum --fix --dry-run`
- [ ] **Expected:** normal behaviour. The HV.4 guard keys off path queries only.
- [ ] **Why this matters:** an over-broad guard would have made `--fix` unusable except from inside a checkout.

### HV.6 — Convergence still settles

- [ ] **Steps:** on a repo genuinely behind and installed editable, `dz dazzle-update . --fix`, answer `y`.
- [ ] **Expected:** pull, then `re-checking ... after pass 1`, then a REINSTALL prompt (the pull staled the install), then `nothing left to fix`.
- [ ] **Why this matters:** the new guard runs inside the convergence loop; a guard that refused on the second pass would stall it.

## Section 1: the pull guard (~10 min)

### 1.1 Untracked file that the pull *does* add

- [ ] **Steps:**
  1. `git -C C:\temp\ck-scratch diff --name-only --diff-filter=A HEAD..@{u}` — note a path
  2. Create that exact path locally as an untracked file with your own content
  3. `dz dazzle-update . --fix --dry-run`
- [ ] **Expected:** refused, naming that path.
- [ ] **Check:** your file's content is untouched.

### 1.2 Untracked file *beside* an incoming one

- [ ] **Steps:** if the pull adds `docs/thing.md`, create `docs/scratch.md` instead.
- [ ] **Expected:** the pull is planned. Same directory is not the same file.

### 1.3 Staged but uncommitted changes

- [ ] **Steps:** edit a file the pull does NOT touch, `git add` it, then `--fix --dry-run`.
- [ ] **Expected:** the pull is planned. Staged and unstaged are both "uncommitted".

### 1.4 Auto-stamp churn

- [ ] **Steps:** in a repo whose commit hook restamps a version file, leave that restamp uncommitted and run `--fix --dry-run`.
- [ ] **Expected:** if the incoming commits touch that file (most version bumps do) → refused, naming it. If not → the pull is planned.
- [ ] **Note:** 0.12.16 refused *both* cases with `auto-stamp churn present`. That message no longer exists.

### 1.5 Many collisions at once

- [ ] **Steps:** modify four or more files that the incoming commits also modify.
- [ ] **Expected:** three paths listed, then `(+N more)`. The count must be present — a silently truncated list reads as the whole answer.

### 1.6 A repository whose state cannot be determined

- [ ] **Steps:** hard to force deliberately; watch for it in the wild.
- [ ] **Expected:** `could not determine whether a pull would collide with local work -- refusing`. Never a pull.
- [ ] **Why:** a failed measurement is not permission.

### 1.7 Diverged and no-upstream are unchanged

- [ ] **Steps:** a branch that is both ahead and behind; a branch with no upstream.
- [ ] **Expected:** `diverged -- needs a merge, not a fast-forward` and `no upstream -- nothing to fast-forward from`. Unchanged from 0.12.16.

## Section 2: rendering and shell behaviour (~5 min)

### 2.1 Long paths in the BLOCKED table

- [ ] **Steps:** trigger 1.1 in a repo with deep paths; narrow your terminal to ~80 columns.
- [ ] **Check:** the reason column does not wrap into unreadable soup; the repo name stays legible.

### 2.2 Non-ASCII filenames

- [ ] **Steps:** create an untracked file with an accented name that the pull also adds.
- [ ] **Expected:** refused, and the filename renders correctly rather than as `caf\303\251`.
- [ ] **Why:** git quotes non-ASCII paths in its normal output; the probe reads them raw.

### 2.3 Case-differing filenames (Windows)

- [ ] **Steps:** the pull adds `docs/Platforms.md`; create `docs/platforms.md` untracked.
- [ ] **Expected:** refused. On a case-insensitive filesystem these are one file.

### 2.4 `--json`

- [ ] **Steps:** `dz dazzle-update --json > out.json` then parse it.
- [ ] **Check:** valid JSON, no prose leaked onto stdout.

## Section 3: performance feel (~2 min)

### 3.1 Bulk `--fix` is not noticeably slower

- [ ] **Steps:** time `dz dazzle-update --fix --dry-run` before and after upgrading.
- [ ] **Expected:** the guard adds roughly 0.1–0.3s per repository **already found behind** — not per repository scanned. On a run that takes 30–60s this should be hard to notice.
- [ ] **Flag it if:** the run got dramatically slower. That would mean the probe is running on repos it should not.

Additionally, `tests/one-offs/thinking/pulllab.py` runs **real `git pull`** across 12 scenarios and scores the old and new guards against what git actually did. Run it to see the scoreboard; it is not part of the suite because it is slower and its findings are already encoded as tests.

## What the automated tests DON'T cover

- Terminal rendering: column widths, wrapping, Windows codepage 437/1252 on the BLOCKED table
- Real interactive prompts (`y`/`n`/`a`/`q`) against real repositories
- Whether the refusal wording actually sends you to the right place
- Worktrees whose gitdir points into WSL — no fixture can create one portably
- Network behaviour during the fetch that precedes the guard
- Performance feel on a large real population
- Whether `(+N more)` is the right cutoff for how people actually read the table

## Reporting issues found

1. Note the section and step number
2. Capture the exact command and its full output
3. Include `git status --porcelain` and `git diff --name-only HEAD..@{u}` from the repository involved — those are the two inputs the guard reasons about
4. File an issue referencing this checklist and version
