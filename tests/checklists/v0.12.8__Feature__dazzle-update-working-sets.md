# Human Test Checklist: dz dazzle-update Working Sets

**Target version:** 0.12.8-alpha (planned)
**Ships with commit:** TBD (feature: working sets -- named overlapping lenses for the ecosystem scanner)
**Companion automated tests:** 43 tests in `src/dazzlecmd/projects/dazzletools/dazzle-update/tests/test_sets.py` (182 for the tool overall), on top of the `_repo_common` suite. Three were added during verification: underscore-comment keys, set warnings surviving `--cached` replay (tester-agent finding), and the scoped lens footer (live user finding).

## What this is

`dz dazzle-update` gained *working sets*: named, user-defined, deliberately overlapping groupings of repos ("dazzle", "wtf", "comfy"...) that act as lenses over the report. A set is defined by four sources -- `namespaces` (glob patterns, the body), `include` (exact repo names, exceptions), `exclude` (small noise), and `declared` (membership derived from kit manifests and tool requirements, zero config). New CLI surface: `--only-set NAME`, `--list-sets`, `in:<set>` row tags, a `SET LENS` disclosure line, per-set health warnings, and two worked examples in `--init-config`.

The rule language was chosen by measurement against a human-adjudicated ground truth of a real 100-repo population, not by argument. This checklist verifies the parts of that behavior only a human at a real terminal can.

## Prerequisites

1. dazzlecmd installed editable (`pip install -e .`), `dz dazzle-update` runnable.
2. All commands here use a **throwaway config** via `--config` pointing at a temp file -- your real config is never touched.
3. A prior scan cache helps (`dz dazzle-update` run at least once); cached-replay tests say so where needed.

**Reset between sections:** delete the temp config file; nothing else is written.

## High-Value Verification (~5 minutes)

**If you only have 5 minutes**, run these 5. Setup for all of them (pick your shell):

**cmd.exe**:
```cmd
set DUCFG=%TEMP%\du-sets-test.json
dz dazzle-update --init-config --config %DUCFG%
```

**PowerShell**:
```powershell
$env:DUCFG = "$env:TEMP\du-sets-test.json"
dz dazzle-update --init-config --config $env:DUCFG
```

**POSIX**:
```bash
export DUCFG=/tmp/du-sets-test.json
dz dazzle-update --init-config --config "$DUCFG"
```

(Substitute `%DUCFG%` / `$env:DUCFG` / `"$DUCFG"` for `<CFG>` below.)

### HV.1 -- The template ships two worked sets

- [ ] **Steps:** `dz dazzle-update --list-sets --config <CFG>`
- [ ] **Expected:** a `dazzle` set (namespaces `DazzleTools/*, DazzleLib/*`, two exact `include` lines, exclude `*/.github`, `declared: yes`) and a `wtf` set (namespaces `djdarcy/wtf-*`, `declared: no`). Rules print aligned and readable.
- [ ] **Why this matters:** the worked examples ARE the documentation of the rule language; if they're absent or garbled, users never learn the schema.

### HV.2 -- The lens filters and DISCLOSES what it hides

- [ ] **Steps:** `dz dazzle-update --only-set wtf --config <CFG>` (add `--cached --max-age 999999` for a no-network replay if a cache exists)
- [ ] **Expected:** only wtf-line repos in every section; a `SET LENS` line stating the set name AND the count of repos with findings hidden by the lens. The count must be non-zero on any real multi-project machine.
- [ ] **Why this matters:** a lens that hides silently is the report describing the question instead of the machine -- the recurring failure class this tool exists to avoid.

### HV.3 -- Overlap renders as a tag

- [ ] **Steps:** same run as HV.2; find `djdarcy/wtf-windows` (or any repo in two sets).
- [ ] **Expected:** the row carries `in:dazzle` -- its OTHER set memberships. The tag for the active lens itself is suppressed (no row says `in:wtf` under `--only-set wtf`).
- [ ] **Why this matters:** overlap-as-lens is the core design claim; the suppression choice is pure UX that no mock can judge.

### HV.4 -- Unknown set name fails loudly, exit 2

- [ ] **Steps:** `dz dazzle-update --only-set nope --config <CFG>`; then check exit code (`echo %ERRORLEVEL%` / `$LASTEXITCODE` / `echo $?`).
- [ ] **Expected:** `unknown set(s): nope`, a list of configured sets, exit code 2. No scan starts (returns instantly, no progress line).
- [ ] **Why this matters:** a typo'd set name silently matching nothing would render an empty report that reads as "all clean".

### HV.5 -- No sets configured = byte-identical old behavior

- [ ] **Steps:** write `{}` to a second temp config; run `dz dazzle-update --config <that file>` and inspect the output.
- [ ] **Expected:** no `SET LENS` line, no `in:` tags anywhere, no set warnings -- indistinguishable from v0.12.7 output.
- [ ] **Why this matters:** the feature must be invisible until asked for; a stray tag on every row is a regression for every existing user.

## Section 1: Health warnings (~5 min)

### 1.1 Glob in include warns but still matches

- [ ] **Steps:** edit the temp config: change the `dazzle` set's include to `["djdarcy/dazzle-*"]`. Run `dz dazzle-update --list-sets --config <CFG>` and then a scan.
- [ ] **Expected:** a WARNING naming the set, the offending glob, and saying globs belong in `namespaces`. The glob still *matches* (config that parses behaves as written).
- [ ] **Check:** the warning appears in BOTH the fresh-scan path and `--cached` replay.

### 1.2 Include over 3 entries warns

- [ ] **Steps:** give a set 4 include entries; run any command.
- [ ] **Expected:** WARNING: "include has 4 entries (healthy is 0-3)".

### 1.3 Malformed set degrades loudly, run continues

- [ ] **Steps:** set `"sets": {"bad": "DazzleTools/*"}` (string, not mapping). Run a scan.
- [ ] **Expected:** WARNING that `'bad'` was skipped; the scan itself completes normally.

## Section 2: Declared membership (~5 min)

### 2.1 Kit-source membership is real

- [ ] **Steps:** with the template config (dazzle has `"declared": true`), run `--only-set dazzle --json` and locate `djdarcy/wtf-windows`.
- [ ] **Expected:** its `sets` array contains `dazzle` -- it earns that from `wtf.kit.json`'s `source` field, not from any pattern in the config.

### 2.2 Tool-requirement membership is real

- [ ] **Steps:** same JSON; locate `djdarcy/DPAPIck3`.
- [ ] **Expected:** `sets` contains `dazzle` -- from `efs-recover/requirements.txt` naming `dpapick3`.

### 2.3 Declaration does NOT leak into non-declared sets

- [ ] **Steps:** same JSON; locate `djdarcy/wtf-privacy`.
- [ ] **Expected:** `sets` is `["wtf"]` only -- never `dazzle`. No manifest declares it, and the wtf set's glob does not feed dazzle.

## Section 3: Interactions (~5 min)

### 3.1 Lens composes with --only/--skip

- [ ] **Steps:** `dz dazzle-update --only-set dazzle --only dirty --config <CFG>`
- [ ] **Expected:** only DIRTY section, only dazzle-set repos; both the `SET LENS` line and the `--only/--skip` hidden-count logic behave (no contradiction between them).

### 3.2 Lens under --cached replay

- [ ] **Steps:** `dz dazzle-update --cached --max-age 999999 --only-set dazzle --config <CFG>`
- [ ] **Expected:** works offline; sets are re-derived from the CURRENT config, not replayed from the cache (edit the config's set rules between two `--cached` runs and confirm membership follows the edit).

### 3.3 --fix scoped by the lens

- [ ] **Steps:** `dz dazzle-update --only-set wtf --fix --dry-run --config <CFG>`
- [ ] **Expected:** planned actions cover ONLY wtf-set repos. (Dry run -- nothing executes.)

### 3.4 Namespace degradation is stated per set

- [ ] **Steps:** with `gh` unauthenticated (or briefly renamed out of PATH), run `--only-set dazzle`.
- [ ] **Expected:** a WARNING that the set's uncloned members cannot be detected -- the lens says its own coverage is incomplete rather than quietly showing fewer rows.

## What the automated tests DON'T cover

- `SET LENS` line rendering, alignment, and colour on a real cmd.exe / PowerShell terminal
- `in:` tag readability when rows already carry many bits (branch, ahead/behind, checkout-of-N)
- The whole-report *feel* of a lens: does `--only-set wtf` actually answer "what does the wtf line need?"
- Live declared-membership derivation timing (manifest globs on every run -- is it perceptibly slow?)
- `--fix` interaction with a lens against real repos (only `--dry-run` is safe to test by hand)
- Whether the worked examples in the template match YOUR machine's population sensibly

## Reporting issues found

2. Capture the exact command, output, and the temp config contents.
3. File an issue referencing this checklist; include `--json` output for membership disputes.
