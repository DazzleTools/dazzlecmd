## What this is

v0.7.46 closes the engine half of the "first-run setup" arc (#33) by promoting `dz setup <tool>` from a documentation hint to a real install surface. Three independent changes compose:

1. **`setup.script` schema field** -- a manifest can point at a file in the tool directory (e.g. `dz_setup.py`) instead of inlining a shell one-liner. The engine infers the interpreter from the extension (`.py` -> python, `.sh` -> bash, `.cmd`/`.bat` -> cmd /c, `.ps1` -> powershell -File) and dispatches.
2. **`runtime.venv` shorthand (4b-T4)** -- the python runner synthesizes the interpreter path from a venv directory + platform convention (Windows `Scripts/python.exe`, POSIX `bin/python`). Path-resolution shorthand only; the engine never creates the venv.
3. **`SetupRequiredError` (4b-T5)** -- the python runner translates "interpreter not found" into an actionable `Run: dz setup <fqcn>` hint when the tool declares a setup block (or "ask the tool's creator" otherwise) instead of letting subprocess raise a bare `FileNotFoundError`.

The Python `--full` template uses all three: scaffolded tools ship with `runtime.venv: ".venv"` + `setup.script: "dz_setup.py"` + an installer-detection script that picks the right Python install path (uv, poetry, pdm, pipenv, conda, pip+pyproject, pip+requirements, or empty-venv fallback) for whatever the user has on disk.

v0.7.47 will add the first-run UX layer (auto-detect missing setup at tool dispatch time and prompt the user). v0.7.48 will validate the API against real-world tools (dazzle-locate32 binary download, comfyui-triton-sageattention-installer, wtf-windows multi-tool aggregator).

### 1.3 -- The 4 supported extensions dispatch via the right interpreter

For each extension, drop a trivial script in a scratch tool dir, set `setup.script` to that filename, and verify `dz setup` runs the right interpreter:

| Ext | Script content | Expected interpreter chain |
|---|---|---|
| `.py` | `print("hi from python")` | `python <abs path>\install.py` |
| `.sh` | `echo hi from bash` | `bash <abs path>/install.sh` |
| `.cmd` | `@echo hi from cmd` | `cmd /c <abs path>\install.cmd` |
| `.bat` | `@echo hi from bat` | `cmd /c <abs path>\install.bat` |
| `.ps1` | `Write-Host "hi from ps"` | `powershell -File <abs path>\install.ps1` |

- [ ] **Check each**: dazzlecmd echos the `Invocation:` line with the right interpreter and the script's `hi from X` message appears in stdout.

## What the automated tests DON'T cover

- **The actual `dz setup` CLI surface end-to-end** -- mocks subprocess.run in tests; the real run-on-disk verification is in HV.4, 5.1-5.4 here.
- **Per-installer detection paths in `dz_setup.py`** beyond pip-requirements. The script is shipped as a rendered template; the unit test exercises only the `requirements.txt`-only path.
- **Real venv creation and pip-install behavior** -- tests stub or skip this; HV.4 + Section 4.2-4.8 cover it.
- **The `SetupRequiredError` -> `dispatch_tool` -> stderr round trip in a real CLI invocation** -- unit tests assert the exception type and message; HV.5 / HV.6 cover the actual stderr output.
- **Cross-shell rendering of the hint text** on Windows Terminal vs cmd.exe vs PowerShell vs bash-WSL. Spot-check at least two shells.
- **Behavior under non-ASCII paths** (e.g. tool directory with spaces or unicode in the path) -- known to vary by subprocess invocation; treat as a separate audit.

**POSIX**:
```bash
dz safedel projects/_hv3 --yes
dz safedel projects/_hv5 --yes
dz safedel projects/_hv6 --yes
dz safedel projects/_s5 --yes
unset DAZZLECMD_CONFIG
```

`dz safedel recover last` undoes a single removal if a directory is needed back. The scratch `DAZZLECMD_CONFIG` file under `%TEMP%`/`/tmp` is harmless to leave behind.
