## What this is

First commit of Tier 1 in the 0.7.x closeout. Closes issue #56 by tracking deliberate `meta_registry.override()` calls and exempting them from the conflict warning, while preserving the warning for unintended name collisions. Ships the two discoverability replacements proposed in the #56 body — `dz info <name>` shadow-status block and `dz tree [shadowed]` marker — so suppressing the warning doesn't blind users to actual shadowing.

This checklist verifies the human-visible behavior the mocks can't cover: real subprocess invocation of `dz info`/`dz tree` showing the new output; cross-shell rendering of the `[shadowed]` marker on Windows codepage 437/1252; the amdead-style scenario (override + reserved-name tool) producing zero spurious stderr noise.

### HV.2 — Warning still fires for unintended conflicts (no override)

## What the automated tests DON'T cover

- **Real `dz` subprocess invocation** with the new shadow output — pytest mocks the engine; only a real `dz info <name>` shows the banner end-to-end with the shadow status block
- **Cross-shell ASCII rendering** of `[shadowed]` and the shadow block on Windows codepage 437/1252 — automated tests run via Python; terminal rendering is human-eyes territory
- **Real amdead-style scenario** end-to-end (an aggregator with `core:setup` + `override("setup", ...)`) — the unit tests simulate the registry state but don't exercise a full subprocess invocation
- **Performance**: the marker check is O(1) per tool but scales with tree depth — a real-sized aggregator should still render snappy. (Subjective: any noticeable lag would point to a regression.)
- **Edge case: tool name == `info` or `tree`**: shadowing the very command being used to inspect shadowing creates a recursive loop. Should print correctly but no automated test exercises this corner.
