# Human Test Checklist: safedel keeps same-named items side by side

**Target version:** dazzlecmd 0.12.28 with dazzlecmd-lib 0.10.39 and dazzle-filekit 0.5.1
**Ships with commit:** `v0.12.28 feat(safedel): same-named items in one call; recover --force-identity`
**Companion automated tests:** dazzlecmd `src/dazzlecmd/projects/core/safedel/tests/test_cli_layout.py` (5); dazzlecmd-lib `tests/test_core_safedel_layout.py` (25).

## What this is

A hand-run pass over the change that lets `dz safedel` delete two things with the same name in one call, and over recovery's new checks. The automated tests use a temporary trash store and never a second drive; this checklist uses the real command, in a scratch folder, on your machine.

**Every step works inside one scratch folder you create and deletes only what it created there.** Do not point any step at real data.

## Prerequisites

1. Check the versions (same in every shell):

   ```
   dz --version
   python -c "import dazzlecmd_lib, dazzle_filekit; print(dazzlecmd_lib.__version__, dazzle_filekit.__version__)"
   ```

   Expected: dazzlecmd 0.12.28; a library version starting `0.10.39`; filekit `0.5.1` or later. **If the library is 0.10.38 or older, stop:** the same-name call is refused there (exit 3), which is the old behaviour.
2. Make a scratch folder and work inside it:

   **cmd.exe**: `mkdir %TEMP%\sd28 && cd /d %TEMP%\sd28`
   **PowerShell**: `New-Item -ItemType Directory -Force "$env:TEMP\sd28" | Out-Null; Set-Location "$env:TEMP\sd28"`
   **POSIX**: `mkdir -p /tmp/sd28 && cd /tmp/sd28`
3. Each section starts from files it creates itself. To repeat a section, recover or re-create its files first.

## High-Value Verification (~5 minutes)

### HV.1 -- Two same-named files in one call are both staged

- [ ] **Steps:**

  **cmd.exe**: `mkdir a b` then `echo AAA> a\x.json` and `echo BB> b\x.json`
  **PowerShell**: `New-Item -ItemType Directory -Force a,b | Out-Null; Set-Content a\x.json AAA; Set-Content b\x.json BB`
  **POSIX**: `mkdir -p a b && echo AAA > a/x.json && echo BB > b/x.json`

  then, in any shell:

  ```
  dz safedel --dry-run a/x.json b/x.json
  dz safedel --yes a/x.json b/x.json
  ```
- [ ] **Expected:** the dry run shows both items, prints `DRY RUN: nothing was changed.` and ends with `safedel: DRY-RUN 2 would be staged`; the real run ends with a line starting `safedel: STAGED 2` and exit code 0. **Note the batch name** the report prints after `dz safedel recover`.
- [ ] **Check:** `a/x.json` and `b/x.json` are gone. `dz safedel list last` shows two entries.
- [ ] **Why this matters:** this exact call used to be refused, and before that it silently lost one of the two files.

### HV.2 -- Both come back, each with its own content

- [ ] **Steps** (same in every shell; use the batch name from HV.1):

  ```
  dz safedel recover <batch name>
  ```
- [ ] **Expected:** two `Recovered:` lines, exit code 0.
- [ ] **Check:** `a/x.json` holds `AAA` and `b/x.json` holds `BB` (view with `type` / `Get-Content` / `cat`).
- [ ] **Why this matters:** staging both is worth nothing if recovery mixes them up.

### HV.3 -- Recovering to another folder keeps them apart

- [ ] **Steps:** repeat the delete from HV.1, then (same in every shell):

  ```
  dz safedel recover <batch name> --to back
  ```
- [ ] **Expected:** `back/a/x.json` holds `AAA` and `back/b/x.json` holds `BB`. Neither overwrote the other.

### HV.4 -- A file changed while in the trash is not recovered silently

- [ ] **Steps:**
  1. Create and delete one file: put the text `original` in `c.txt`, then `dz safedel --yes c.txt`. Note the batch name.
  2. `dz safedel status` names the trash store that holds it. Open `<store>/<batch name>/content/c.txt` in an editor and change its contents so the size differs. (This edits a file you just put in the trash yourself; touch nothing else there.)
  3. `dz safedel recover <batch name>`
- [ ] **Expected:** exit code 1; a message that the manifest recorded one size and the stored file has another, that it was not recovered and is still in the trash, and that `--force-identity` recovers it anyway. `c.txt` is NOT back.
- [ ] **Then:** `dz safedel recover <batch name> --force-identity` -- exit 0, `c.txt` is back with the edited contents, and a `WARNING ... recovering anyway` line was printed.
- [ ] **Why this matters:** recovery should not hand back something other than what was deleted without saying so.

### HV.5 -- The same path twice, and an item inside another

- [ ] **Steps:** make a folder `build` holding `out/a.o`, and a file `notes.txt` (any content). Then (same in every shell):

  ```
  dz safedel --yes notes.txt notes.txt build build/out/a.o
  ```
- [ ] **Expected:** `safedel: STAGED 2` (not 4), with two warnings: one that `notes.txt` was kept once, one that `build/out/a.o` is inside `build`, which carries it.
- [ ] **Check:** is each warning clear about WHICH path it means and why?

## Section 1: Refusals that replaced the same-name refusal

### 1.1 An item inside a link that is also named

- [ ] **Steps** (Windows, PowerShell): `New-Item -ItemType Directory real | Out-Null; Set-Content real\inner.txt I; New-Item -ItemType Junction -Path lnk -Target (Resolve-Path real) | Out-Null`, then `dz safedel --yes lnk lnk\inner.txt`.
  **POSIX**: `mkdir real && echo I > real/inner.txt && ln -s "$PWD/real" lnk`, then `dz safedel --yes lnk lnk/inner.txt`.
- [ ] **Expected:** exit code 3, `safedel: REFUSED ...`, a message that `inner.txt` is inside `lnk`, which is a link. Nothing moved: `lnk` still exists and `real/inner.txt` still holds `I`.
- [ ] **Then:** `dz safedel --yes lnk` alone removes only the link; `real/inner.txt` is untouched.

## Section 2: Across drives (needs a second drive)

### 2.1 One call, two drives

- [ ] **Steps:** create `docs/f.txt` in the scratch folder and another `docs/f.txt` in a scratch folder on a second drive. Delete both `docs` folders in one call with `--yes`.
- [ ] **Expected:** `safedel: STAGED 2`, with a warning that the batch spans 2 drives and that items not on the store's drive are copied there, not moved. In the batch folder, `content/0/docs/f.txt` and `content/1/docs/f.txt` exist.
- [ ] **Check:** `dz safedel recover <batch name>` puts each `docs` folder back on its own drive.
- [ ] **Note:** an item copied from another drive does not keep every timestamp a same-drive move keeps. That limit is known; record what you see.

## Section 3: Old batches

### 3.1 A batch from before this version still recovers

- [ ] **Steps:** `dz safedel list` and pick any batch written before you installed this version that you are willing to recover into a scratch folder; then `dz safedel recover <batch name> --to oldback --dry-run`.
- [ ] **Expected:** the dry run lists each item as `Would recover` to `oldback/<name>` (flat, as before), and creates nothing: `oldback` does not exist afterwards.

## What the automated tests DON'T cover

- A real second drive: the two-root test hands the planner stand-in paths (2.1).
- The real trash stores on this machine, per-volume and central (every HV step).
- How the warnings and refusals read to a person (HV.5, 1.1).
- Recovery of a real pre-0.10.39 batch from your own store (3.1).
- Console rendering of long relative paths in `list` and the delete report.
- Timestamps of an item that crossed drives.

## Reporting issues found

1. Note the section and step number.
2. Capture the exact command and its output, and the batch name.
3. Keep the batch in the trash (do not clean it) so it can be inspected.
4. File an issue referencing this checklist and DazzleLib/dazzlecmd-lib#7.

## Cleanup

Recover or leave the scratch batches as you prefer; they are ordinary trash batches and expire with the rest. Remove the scratch folder when done: `dz safedel --yes <scratch folder>` from its parent folder. If section 1.1 left `lnk` in it, remove that link first with `dz safedel --yes lnk`, so the folder holds no link when it is deleted.
